      Client ID Metadata Document Software Statement Registration
        draft-mcguinness-oauth-cimd-sw-stmt-registration-latest

Abstract

   A companion specification defines a software statement for a Client
   ID Metadata Document (CIMD).  The statement carries no client
   metadata: it binds an issuer's review to the exact bytes of the
   client's own document.  This specification defines how an
   authorization server consumes such a statement in an RFC 7591
   registration request, taking every metadata value from the reviewed
   document rather than from the request.  It also defines how the
   statement's expiry bounds the resulting registration, which RFC 7591
   leaves unbounded, and how a client renews the registration by
   delivering a replacement statement, which also updates the
   registration's metadata.

1.  Introduction

   A software statement (Section 2.3 of [RFC7591]) carries a third
   party's approval of client software into a dynamic client
   registration request.  In [RFC7591], values in the statement take
   precedence over those in the request.  A statement under Section 3 of
   [STATEMENT] carries no client metadata: it names a Client ID Metadata
   Document (CIMD) by its URL and binds the review to that document's
   exact octets.  An [RFC7591] server that verified such a statement
   without implementing this specification would take every metadata
   value from the request, attaching the issuer's approval to
   redirection URIs and keys nobody reviewed.

   [RFC7591] also defines no expiry or renewal for a registration.  A
   registration based on a statement can outlive it, and nothing keeps
   the registration's validity or metadata in line with the issuer's
   decision once the issuer narrows, withdraws, or stops renewing it.

   [STATEMENT] admits a client at request time without registering it.
   This specification is for deployments that register clients through
   [RFC7591] instead, for example to assign their own client identifiers
   or to manage registrations under [RFC7592].  It defines consumption
   of the statement at registration (Section 3), the registration's
   validity (Section 3.2), and its renewal by a replacement statement
   (Section 3.3).  This specification depends on [STATEMENT], which does
   not depend on it.

1.1.  Protocol Overview

   The following non-normative sequence summarizes a statement-governed
   registration:

   1.  The client registers through [RFC7591], carrying a statement in
       the software_statement member.

   2.  The authorization server derives the registration's metadata from
       the reviewed document and records the statement's identity.  The
       registration is valid until the statement's effective expiry
       (Section 3.2).

   3.  The client delivers a replacement statement in a token or pushed
       authorization request under the registration or, if supported, an
       [RFC7592] update request.  The delivery sets the registration's
       validity to the replacement's effective expiry.

   4.  If no replacement arrives, the registration expires and requests
       under it fail.

2.  Conventions and Definitions

   The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT",
   "SHOULD", "SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED", "MAY", and
   "OPTIONAL" in this document are to be interpreted as described in
   BCP 14 [RFC2119] [RFC8174] when, and only when, they appear in all
   capitals, as shown here.

   This specification uses terminology from [RFC6749] (OAuth), [RFC7591]
   (client metadata and software statements), and [CIMD] (Client ID
   Metadata Documents), and the terms defined in Section 2 of
   [STATEMENT].

   This specification defines the following terms.

   Delivery:  Carrying a statement in a request under a statement-
      governed registration, in one of the locations Section 3.3 lists,
      so that it can renew the registration.  A delivery is not a
      runtime presentation.

   Governing Statement:  The statement that bounds a statement-governed
      registration: the one consumed at registration or, after a
      renewal, the replacement that renewed it most recently
      (Section 3.3).

   Statement-Governed Registration:  An [RFC7591] client registration
      created from a statement under this specification (Section 3.2).

3.  Consumption at Registration

   The statement is consumed in the software_statement member of an
   [RFC7591] registration request.  The authorization server validates
   it under Section 3.2 of [STATEMENT] and registers the client under
   its ordinary registration policy.

   The reviewed document takes the role that [RFC7591] gives a
   statement's own values.  An authorization server consuming a
   statement under this specification:

   *  MUST resolve the CIMD at the statement's sub claim, rejecting the
      registration if retrieval does not complete.

   *  MUST validate the document as [CIMD] requires, including that its
      client_id member matches the statement's sub claim, the client
      identifier URL at which the document was resolved.

   *  MUST verify that the digest of the retrieved representation equals
      the statement's cimd_digest claim, rejecting the registration if
      it does not, and MUST derive the registered metadata by parsing
      the same octets it digested, not a second retrieval or a cached
      copy it has not digested.

   *  MUST take every client metadata value from that document, and MUST
      NOT take any client metadata value from the registration request,
      or from any [RFC7592] update request for the registration it
      creates, whether or not the document carries the corresponding
      member:

      -  The registration's metadata changes only by re-derivation from
         the document a replacement statement reviews (Section 3.3).

      -  A request MAY carry metadata, as [RFC7591] clients do, but it
         does not contribute to the registration.

      -  The registered client_id is assigned as [RFC7591] provides, and
         the document's own client_id member is the URL recorded as sub.

   *  MUST reject the registration with the invalid_client_metadata
      error code if the document omits the token_endpoint_auth_method
      member.

   *  MUST reject the registration with the invalid_client_metadata
      error code if the document declares token_endpoint_auth_method of
      none, unless the authorization server registers the client under
      Section 3.1.

   *  MUST reject the registration with the invalid_client_metadata
      error code if any of the document's redirection URIs could be
      claimed by another application on the same device (Section 5.6.3
      of [STATEMENT]), whatever authentication method the document
      declares.

   If the statement's decision is confined to one of the authorization
   server's tenants, by its aud_tenant claim or by the server's trust
   configuration for its issuer (Section 4 of [STATEMENT]), the
   authorization server MUST record that tenant with the registration.
   Tenant restrictions apply to every statement-governed registration as
   follows:

   *  The authorization server MUST treat a request under a
      registration, including a delivery (Section 3.3), made in a tenant
      other than the one the registration is restricted to, as a request
      from a client it has not registered.

   *  The restriction persists across renewals.

   *  A renewal by a replacement whose decision is confined to a tenant
      restricts a registration that carries no tenant restriction to
      that tenant, except a public-client registration, which such a
      statement does not renew (Section 3.1).

   *  A registration created from a statement whose decision is not
      confined to a tenant carries no tenant restriction under this
      specification until such a renewal.

   *  In a tenant where the authorization server requires a tenant-
      scoped decision (Section 3.2 of [STATEMENT]), it MUST treat a
      request under a registration that carries no tenant restriction
      under this specification as a request from a client it has not
      registered unless, once it has authenticated the client against
      the registration and evaluated any replacement the request
      delivers (Section 3.3), the registration is restricted to that
      tenant.

   Unlike runtime presentation (Section 5 of [STATEMENT]), registration
   has no review-only form: the registration is the admission.

   Taking every value from the document prevents metadata substitution.
   At registration a statement is a bearer artifact, so a request-
   supplied value for a member the document omits, such as a jwks member
   beside a document naming only jwks_uri, would give any holder of a
   copy a registration with reviewed branding and the holder's own key.
   Registering a document that omits token_endpoint_auth_method under
   the [RFC7591] default, a shared-secret method, would issue a client
   secret to any holder of a copy.  Software whose document declares
   token_endpoint_auth_method of none and that the server does not
   register under Section 3.1 can instead use runtime presentation if it
   meets the public-client binding requirements of Section 5.6.2 of
   [STATEMENT].

   The retrieval requirements of Sections 3.1 and 5.3 of [STATEMENT]
   apply to retrieving the document as they apply to a runtime
   presentation, and a server can apply the bounds that specification
   describes.  Following the order of Section 5.1 of [STATEMENT], the
   authorization server completes every check that needs no client-
   controlled retrieval before resolving the document.

3.1.  Public Clients

   An authorization server MAY register a client whose reviewed document
   declares token_endpoint_auth_method of none.  Such a registration has
   no client credential.  The registration is bound instead as
   Section 5.6.2 of [STATEMENT] binds a public client at runtime.  A
   server that registers such a client:

   *  MUST reject the registration with the invalid_client_metadata
      error code if the document lists no redirection URI.  Section 3
      already rejects a document listing one that another application
      could claim.

   *  MUST issue tokens under the registration only through the
      authorization code grant and refresh of the grants it opens.

   *  MUST require PKCE [RFC7636] with the S256 method on every
      authorization request under the registration.

   *  MUST require every authorization request under the registration to
      bind a key the client holds, through the dpop_jkt parameter or, at
      the pushed authorization request endpoint, a DPoP proof
      (Section 10.1 of [RFC9449]), and MUST require code redemption and
      every refresh of the resulting grant to prove that key.

   *  MUST NOT issue a registration access token [RFC7592] for the
      registration.

   *  MUST answer a later registration request with the existing
      registration if the request is in a tenant where the registration
      can be used and the request's statement has the same iss and sub
      claims as the governing statement, validates, is not superseded
      under the iat floor of Section 6 of [STATEMENT], and is confined
      to no tenant other than one the registration is already restricted
      to.  If that statement's iat is later than the governing
      statement's, the server evaluates it as Section 3.3 provides for a
      delivery, renewing the registration with it or rejecting the
      request with the codes of Section 5.

   The following hold for such a registration:

   *  It has no [RFC7592] management.

   *  The deliveries that Section 3.3 lists at the token and pushed
      authorization request endpoints need no client authentication
      under it.

   *  A delivery renews it only with a valid replacement.  A statement
      whose decision is confined to a tenant fails the replacement rules
      of Section 3.3 if the registration carries no tenant restriction.

   *  It ceases to be valid only at its effective expiry or on
      withdrawal (Section 3.2), and otherwise ends only by the server's
      own policy.

3.2.  Registration Validity

   An authorization server MUST apply the following validity model to
   every registration it creates from a statement validated under
   Section 3.2 of [STATEMENT], whichever issuer signed it:

   *  The authorization server MUST bind the registration to its
      governing statement, identified by the statement's iss and jti
      claims.  The registration's effective expiry is the governing
      statement's effective expiry (Section 2 of [STATEMENT]).

   *  The registration is valid until that effective expiry.  If the
      server holds a refusal record for the governing statement
      (Section 3.3 of [STATEMENT]), the registration ceases to be valid
      as it does at its effective expiry.  The client learns of the
      withdrawal only from the rejection, and whether the server revokes
      access and refresh tokens already issued under the registration is
      local policy.

   *  Once the registration ceases to be valid without a replacement
      (Section 3.3), the authorization server MUST reject authorization,
      token, and pushed authorization requests and [RFC7592] update
      requests under the registration, other than a request carrying a
      replacement, which Section 3.3 evaluates before this rejection.

   *  The authorization server SHOULD retain a registration that has
      ceased to be valid for a later renewal (Section 9.4).

   An authorization server stores with each statement-governed
   registration the governing statement and its iss, jti, sub, and iat
   claims, any claim by which a withdrawal mechanism locates that
   statement (such as status), the registration's effective expiry, and
   any tenant the registration is restricted to.

   A server that uses a withdrawal mechanism for the governing
   statement's issuer SHOULD consult it for that statement at each token
   request under the registration, as Section 5.7.1 of [STATEMENT]
   provides for refresh.

   A server that records a required issuer for a tenant (Section 4 of
   [STATEMENT]) MUST reject an authorization, token, or pushed
   authorization request, or an [RFC7592] update request, in that tenant
   under any registration for software in a covered namespace unless,
   once any replacement the request delivers has been evaluated
   (Section 3.3), a current statement from the required issuer governs
   the registration.  This rule applies whatever tenant the registration
   was created in and whenever the requirement was configured.  Without
   this rule, withholding the required issuer's statement would keep
   such a registration in use after the issuer withdrew or stopped
   renewing its decision.  A registration governed by another issuer's
   statement cannot satisfy the requirement.

   Rejections under a registration that is not valid, and under the
   required-issuer rule, take the following form:

   *  At the token and pushed authorization request endpoints, the
      client is first authenticated against the registration, and a
      request that fails that authentication is rejected with
      invalid_client, as for an unknown client.  Otherwise the request
      is rejected with statement_required (Section 8.1 of [STATEMENT]).

   *  An [RFC7592] update request is rejected with
      invalid_software_statement.

   *  An authorization request is rejected with statement_required in
      the authorization error response (Section 4.1.2.1 of [RFC6749]),
      or with invalid_request if it carries the software_statement
      parameter, as Section 8.4 of [STATEMENT] provides.  The
      authorization server redirects with the error only after
      validating the request's redirect_uri against the registration.
      If the redirect_uri does not validate against the registration,
      the authorization server MUST NOT redirect and reports the error
      to the resource owner instead.

   [RFC7592] read and delete requests are not rejected.

   If an authorization server creates a confidential-client registration
   that permits no grant obtaining tokens without an authorization
   request or refresh token, such as the client credentials grant or an
   assertion grant, and for which it does not support [RFC7592] update
   requests, it MUST publish the pushed_authorization_request_endpoint
   metadata value.  That registration's client could otherwise renew
   only while it holds a refresh token (Section 3.3).

   The registration_expires_at member is a NumericDate (Section 2 of
   [RFC7519]) giving the latest time the registration remains valid or,
   for a registration that has ceased to be valid, the time it ceased.
   The authorization server:

   *  MUST return registration_expires_at in the [RFC7591] registration
      response and in the response to any request that renews the
      registration or carries its governing statement (Section 3.3).

   *  SHOULD return it in any other [RFC7592] read or update response it
      supports.

3.3.  Renewal

   A client renews a statement-governed registration by delivering a
   replacement statement in one of the following:

   *  The software_statement parameter of a token request under the
      registration, authenticated as the registered client under the
      registration's own method.

   *  The software_statement parameter of an authenticated pushed
      authorization request [RFC9126] under the registration.

   *  The software_statement member of an authenticated [RFC7592] update
      request, if the deployment offers registration management.

   A statement carried in one of these locations under a statement-
   governed registration is a delivery.  A registration created without
   a statement is not statement-governed: a statement neither renews nor
   alters it and is not a delivery.  The server applies a reviewed
   change to such a registration, if at all, through its own
   registration policy, deriving metadata only from a reviewed document
   (Section 3).  Nor does runtime presentation (Section 5 of
   [STATEMENT]) alter any registration's metadata.

   A statement with the governing statement's iss and sub and an iat no
   later than the governing statement's iat is not a replacement.  The
   authorization server treats a delivered statement as follows:

    +=======================================+=========================+
    | Statement delivered                   | Treatment               |
    +=======================================+=========================+
    | The governing statement itself,       | The request carries no  |
    | identified by its iss and jti         | replacement             |
    +---------------------------------------+-------------------------+
    | In an [RFC7592] update request, any   | The request carries no  |
    | statement with the governing          | replacement             |
    | statement's iss and sub and an iat no |                         |
    | later than the governing statement's  |                         |
    +---------------------------------------+-------------------------+
    | At the token or pushed authorization  | Superseded under the    |
    | request endpoint, any other statement | iat floor of Section 6  |
    | with the governing statement's iss    | of [STATEMENT].  The    |
    | and sub and an earlier iat            | request is rejected     |
    |                                       | with statement_required |
    +---------------------------------------+-------------------------+
    | A statement with the governing        | A replacement,          |
    | statement's iss and sub and a later   | evaluated below         |
    | iat                                   |                         |
    +---------------------------------------+-------------------------+
    | Any other statement, such as one with | Fails the replacement   |
    | another iss or sub                    | rules below             |
    +---------------------------------------+-------------------------+

                                  Table 1

   A request that carries no replacement leaves the registration
   unchanged, and the request proceeds only while the registration
   remains valid (Section 3.2).  An [RFC7592] update request repeats,
   unmodified, the statement that a registration, read, or update
   response returned (Section 3.2.1 of [RFC7591]; Section 2.2 of
   [RFC7592]), which can be older than the governing statement after a
   token or pushed authorization request has renewed the registration.
   While the registration is valid, its governing statement is current,
   even after a later statement has raised the iat floor of Section 6 of
   [STATEMENT], and satisfies any requirement the server has for a
   current statement on refresh.

   An [RFC7592] read or update response returns the governing statement
   as its software_statement member.

   The replacement MUST satisfy the following:

   *  It validates under the validation rules of Section 3.2 of
      [STATEMENT], including its audience if it carries one, and is not
      superseded under the iat floor of Section 6 of [STATEMENT].

   *  The iss and sub claims equal those of the governing statement.

   *  The iat claim is later than that of the governing statement.

   *  Its document declares token_endpoint_auth_method of none if and
      only if the governing statement's document does.

   *  For a public-client registration that carries no tenant
      restriction, its decision is not confined to a tenant
      (Section 3.1).

   For a replacement, the authorization server MUST do the following:

   *  Obtain the CIMD at the replacement's sub as Section 3 requires.

   *  Verify that the digest of the retrieved octets equals the
      replacement's cimd_digest.

   *  Re-derive the registration's metadata from those same octets,
      under the rules of Section 3.

   Renewing on the statement alone would leave in the registration a
   key, redirection URI, or scope that the new review removed.

   On success, the replacement becomes the governing statement: the
   authorization server MUST replace the stored governing statement and
   its claims (Section 3.2), the effective expiry, and the
   registration's metadata with the replacement's, and apply any tenant
   restriction it adds (Section 3), in a single atomic update, and
   concurrent deliveries resolve to the most recently issued statement.

   Access issued under the registration after that update, including on
   refresh of a grant issued before it, MUST fall within the re-derived
   metadata, as Section 5.7.1 of [STATEMENT] requires of a refreshed
   grant.

   When a request under a registration that has ceased to be valid
   contains a replacement, the authorization server MUST authenticate
   the client against the retained registration and evaluate the
   replacement before applying the rejection of Section 3.2.  A valid
   replacement restores the registration.  An omitted or invalid
   replacement does not.

   When a request under an expired registration carries no replacement,
   its rejection (Section 3.2) MUST NOT by itself cause the
   authorization server to revoke refresh tokens as it does on detecting
   refresh-token replay (Section 4.14.2 of [RFC9700]).

   A request whose replacement fails the rules above is rejected whether
   or not the registration has expired.  At the token and pushed
   authorization request endpoints, such a request is rejected with
   statement_required, or with temporarily_unavailable if a retrieval
   needed to check the replacement did not complete for a reason other
   than the size bound of Section 3.1 of [STATEMENT].  At the client
   configuration endpoint, it is rejected with the codes of Section 5.
   A rejected delivery leaves the governing statement unchanged.

   A registration request is not a delivery: it never renews an existing
   registration, except a public-client registration (Section 3.1).

4.  Repeated Registration

   One unexpired statement can be consumed more than once, subject to
   the bounds Sections 12.2 and 12.3 of [STATEMENT] describe and the
   server's registration policy.  The safe default is one registration
   per (iss, sub) at one authorization server.  On repeated consumption,
   except for a public-client registration, local policy can reject the
   request, treat it as idempotent, or create another registration.  A
   repeated public-client registration is answered with the existing
   registration as Section 3.1 provides.  An idempotent response MUST
   NOT return the existing registration's credentials, such as its
   registration_access_token member.

5.  Error Responses

   A rejection this specification defines, at a client registration
   endpoint or at the client configuration endpoint of [RFC7592], uses
   the error response of Section 3.2.2 of [RFC7591], with the HTTP
   status code that section specifies, except that an authorization
   server SHOULD respond with HTTP status code 503 to a request it
   rejects with the temporarily_unavailable error code.

   Rejections of a registration management request for other reasons use
   the responses [RFC7592] specifies.  Rejections at other endpoints use
   the error responses of Section 8 of [STATEMENT], and registration
   expiry is reported as Section 3.2 defines.

   An authorization server rejecting a registration request, or a
   registration management request for a reason this specification
   defines, uses the following error codes:

   invalid_software_statement:  The statement is malformed, fails
      signature or claim validation for a reason
      unapproved_software_statement does not cover, or is expired,
      refused by a refusal record, or superseded under the iat floor of
      Section 6 of [STATEMENT].  The code also applies when the digest
      of the retrieved document does not match the statement's
      cimd_digest claim, and when a replacement delivered at the client
      configuration endpoint, or a statement in a repeated public-client
      registration request evaluated as a replacement (Section 3.1),
      fails a replacement-specific rule of Section 3.3 that this section
      assigns no other code, such as a sub claim that differs from the
      governing statement's or a change in whether the document declares
      token_endpoint_auth_method of none.  It also applies to an
      [RFC7592] update request rejected under Section 3.2.

   unapproved_software_statement:  The statement is valid but not
      acceptable here: its issuer is not configured, its aud excludes
      this server, its sub is outside the client identifier namespaces
      the issuer can attest, its aud_tenant is not this request's tenant
      or is absent when required, its issuer is confined to another
      tenant, or its statement_uses excludes this use.  This code is
      also used if a statement this server requires is absent from a
      registration request.

   invalid_client_metadata:  Any of the following holds for the reviewed
      document:

      *  It contains duplicate member names (Section 3.2 of
         [STATEMENT]).

      *  It fails validation as [CIMD] requires, including a client_id
         member that does not match the statement's sub (Section 3).

      *  It carries metadata this server's policy refuses.

      *  It exceeds the server's size bound (Section 3.1 of
         [STATEMENT]).

      *  It cannot be obtained for a reason other than a retrieval that
         did not complete (Section 5.3 of [STATEMENT]).

      *  It omits token_endpoint_auth_method (Section 3).

      *  It declares token_endpoint_auth_method of none and the server
         does not register it under Section 3.1.

      *  It declares token_endpoint_auth_method of none and lists no
         redirection URI (Section 3.1).

      *  It carries a redirection URI another application could claim
         (Section 3).

   temporarily_unavailable:  A retrieval the request needs did not
      complete, for a reason other than the size bound of Section 3.1 of
      [STATEMENT].

6.  Example

6.1.  Renewing a Statement-Governed Registration

   The following is a non-normative example of a registered client,
   whose client_id is s6BhdRkqt3, renewing its registration by
   delivering a replacement statement on an ordinary refresh,
   authenticated under its registered private_key_jwt method (line
   breaks for display purposes only):

   POST /token HTTP/1.1
   Host: as.example
   Content-Type: application/x-www-form-urlencoded

   grant_type=refresh_token
   &refresh_token=tGzv3JOkF0XG5Qx2TlKWIA
   &client_id=s6BhdRkqt3
   &client_assertion_type=urn%3Aietf%3Aparams%3Aoauth%3A
   client-assertion-type%3Ajwt-bearer
   &client_assertion=eyJhbGciOiJFUzI1NiIsImtpZCI6IjIwMjYtMDgifQ...
   &software_statement=eyJ0eXAiOiJzb2Z0d2FyZS1zdGF0ZW1l...

   The authorization server validates the replacement and re-derives the
   registration's metadata (Section 3.3), returning the new validity
   boundary in the registration_expires_at member of the token response.
   After expiry, the same request without a replacement would fail with
   statement_required (Section 3.2).

7.  Authorization Server Metadata

   This specification defines the following authorization server
   metadata [RFC8414] value:

   software_statement_registration_validity_supported:  OPTIONAL.
      Boolean value indicating whether the authorization server supports
      this specification.  If omitted, the default value is false.  A
      value of true does not imply support for runtime presentation.

8.  Deployment Considerations

   This section gives guidance to operators.  It adds no requirement.

8.1.  Renewal Cadence

   An issuer outage longer than a statement-governed registration's
   remaining lifetime takes the registration out of service
   (Section 3.2) until the client delivers a replacement (Section 3.3).
   The lifetimes an issuer chooses set the renewal cadence (Section 13.3
   of [STATEMENT]).  A deployment ought to have clients renew well
   before effective expiry, and ought to weigh that cadence against how
   quickly a narrowed or withdrawn review needs to take effect.

9.  Security Considerations

   The security considerations in Section 14 of [STATEMENT] and
   Section 5 of [RFC7591] apply.

9.1.  Statements at Registration

   A statement consumed at registration is a reusable bearer artifact
   until it expires.  Its audience, lifetime, and statement_uses claim
   (Section 3 of [STATEMENT]) and the registration policy of Section 4
   limit what a stolen statement can create.

   Under the one-registration default (Section 4), whoever first
   registers with a copy of a statement holds that registration and its
   registration access token, and can keep the software's publisher from
   registering at that server.  Such a holder cannot authenticate as the
   client if the reviewed document's authentication method requires a
   key the document carries.

   If the publisher's statement permits presentation and the server
   supports it, the publisher's software can still be admitted through
   runtime presentation (Section 5 of [STATEMENT]).  Otherwise, recovery
   requires intervention by the server's operator or a registration
   policy other than the one-registration default.  This specification
   defines no way to displace such a registration.

   A public-client registration (Section 3.1) has no credential to take
   and is answered idempotently, so its first registrant gains nothing
   over later ones.  Any holder of a copy can use it.  Authorization
   codes under it reach only the reviewed redirection URIs, and its
   grants are bound to keys that installations hold.  A holder of a copy
   therefore gains what it would gain at runtime, including the exposure
   Section 14.4 of [STATEMENT] describes for a holder that controls the
   user agent.

9.2.  Credential Theft and Renewal

   Renewal proves possession of the registration's credential and the
   currency of a statement sharing the governing statement's iss and
   sub, not that the renewing party is the reviewed software.  An
   attacker holding a stolen client credential can renew indefinitely
   with the newer statements distributed to every deployment of the
   software.  A public-client registration's renewal proves only that
   the replacement is current.  No protection is lost, since any party
   can already use that registration.

   Deployments ought to pair statement-governed registrations with
   credential rotation, sender-constrained client authentication, and
   the bounds that Sections 12.2 and 12.3 of [STATEMENT] and Section 4
   describe, and ought to treat a credential compromise as requiring re-
   registration rather than renewal.  Runtime presentation (Section 5.6
   of [STATEMENT]) binds every presenter to the reviewed document,
   through a key the document carries or its reviewed redirection URIs,
   and so does not have this limitation, though the redirection binding
   does not hold against a party that controls the user agent.

9.3.  Registration Fraud and Impersonation

   Open registration permits client_name, logo_uri, and client_uri
   values that imitate trusted software on consent screens (Section 5 of
   [RFC7591]).  Requiring a statement replaces self-asserted branding
   with issuer-reviewed values, though content served at a URL the
   document carries, such as a logo, can change after review
   (Section 14.1 of [STATEMENT]).  Servers that render such values on
   consent screens ought to prefer those from a reviewed document and to
   apply heightened scrutiny to registrations that claim user-visible
   branding without a statement.

   Requiring a statement also means a removed client cannot register
   again under a new identity without another issuer decision.  A client
   that misleads the issuer's review can obtain a genuine statement for
   fraudulent metadata, so a statement is only as reliable as the
   issuer's verification.

9.4.  Observable State

   A retained expired registration is distinguishable from an unknown
   client (Section 3.2).  At the token and pushed authorization request
   endpoints, only a requester that authenticates as the registration's
   client can observe this, except for a public-client registration.  At
   the authorization endpoint, anyone who sends an authorization request
   naming the client and one of its registered redirection URIs learns
   of the lapse from the statement_required redirection.  If an observer
   knows the governing statement's exp, a lapse before it shows that the
   server either holds a refusal record for the statement or caps the
   lifetime it honors for the issuer.

   These disclosures are accepted because a client that cannot learn why
   it was refused cannot act.  Beyond a lapse and its timing, they
   reveal nothing of the server's issuer trust configuration
   (Section 8.6 of [STATEMENT]).  Publishing
   software_statement_registration_validity_supported discloses that
   statement-governed registrations expire there, which a client needs
   to know before registering.

10.  Privacy Considerations

   The privacy considerations in Section 15 of [STATEMENT] and Section 6
   of [RFC7591] apply.  A registration request reveals to the
   authorization server the same information as a runtime presentation.

11.  IANA Considerations

11.1.  OAuth Dynamic Client Registration Metadata Registry

   This specification requests registration of the following value in
   the IANA "OAuth Dynamic Client Registration Metadata" registry
   established by [RFC7591].  An authorization server returns this
   member in a registration response:

   Client Metadata Name:  registration_expires_at

   Client Metadata Description:  Latest time at which a statement-
      governed registration remains valid, as a NumericDate.  A
      withdrawal can end it earlier.  Returned in a client registration
      response, in a registration management response, and in the token
      or pushed authorization request response to a request that renews
      the registration or carries its governing statement.

   Change Controller:  IETF

   Specification Document(s):  This specification, Section 3.2

11.2.  OAuth Parameters Registry

   This specification requests registration of the following parameter
   in the IANA "OAuth Parameters" registry established by [RFC6749], for
   the responses to requests that renew a statement-governed
   registration or carry its governing statement:

   Parameter Name:  registration_expires_at

   Parameter Usage Location:  token response, pushed authorization
      request response

   Change Controller:  IETF

   Specification Document(s):  This specification, Section 3.2

11.3.  OAuth Authorization Server Metadata Registry

   This specification requests registration of the following value in
   the IANA "OAuth Authorization Server Metadata" registry established
   by [RFC8414]:

   Metadata Name:  software_statement_registration_validity_supported

   Metadata Description:  Boolean value indicating whether the
      authorization server supports this specification, under which
      every registration it creates from a Client ID Metadata Document
      software statement is governed by this specification's validity
      and renewal rules.

   Change Controller:  IETF

   Specification Document(s):  This specification, Section 7
