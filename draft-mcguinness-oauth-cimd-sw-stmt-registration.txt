Abstract

   RFC 7591 does not define how long a registration based on a software
   statement remains valid or how that statement is renewed.  This
   specification defines how an authorization server consumes a software
   statement for a Client ID Metadata Document in a registration
   request, taking every metadata value from the reviewed document; how
   the statement's expiry bounds the resulting registration; and how a
   client renews the registration with a replacement statement.  It
   builds on the companion specification that defines the statement and
   its runtime consumption.

1.  Introduction

   [RFC7591] defines no expiry or renewal procedure for a dynamic client
   registration.  A software statement (Section 2.3 of [RFC7591]) can
   carry a reviewer's approval into a registration request, but the
   registration can outlive the statement and the review it represents,
   leaving an organization that reviews client software no interoperable
   way to keep that review current at the authorization servers that
   relied on it.

   [STATEMENT] defines the statement, its validation, issuer trust
   configuration, and runtime consumption.  This specification defines
   what registration adds: taking the registration's metadata from the
   reviewed document (Section 3), bounding its validity by the statement
   (Section 3.1), and renewing it with a replacement statement
   (Section 3.2).  It does not register software whose document declares
   token_endpoint_auth_method of none, which [STATEMENT] admits by
   runtime presentation instead, or whose document lists a redirection
   URI another application could claim (Section 3).  It depends on
   [STATEMENT]; [STATEMENT] does not depend on it.

1.1.  Protocol Overview

   The following non-normative sequence summarizes a statement-governed
   registration:

   1.  The client registers through [RFC7591], carrying a statement in
       the software_statement member.

   2.  The authorization server derives the registration's metadata from
       the reviewed document and records the statement's identity and
       effective expiry; the registration is valid until that effective
       expiry (Section 3.1).

   3.  The client delivers a replacement statement in an authenticated
       token or pushed authorization request or, where supported, an
       [RFC7592] update request, extending the registration's validity
       to the replacement's effective expiry.

   4.  If no replacement arrives, the registration expires and requests
       under it fail.

2.  Conventions and Definitions

   The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT",
   "SHOULD", "SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED", "MAY", and
   "OPTIONAL" in this document are to be interpreted as described in
   BCP 14 [RFC2119] [RFC8174] when, and only when, they appear in all
   capitals, as shown here.

   OAuth terminology is defined by [RFC6749].  Client metadata and
   software statement terminology is defined by [RFC7591].  Client ID
   Metadata Document terminology is defined by [CIMD].  Issuer, Runtime
   Presentation, Effective Expiry, and Refusal Record are defined by
   [STATEMENT].

   This specification defines the following terms.

   Delivery:  Carrying a statement in a request under a statement-
      governed registration, in one of the locations Section 3.2 lists,
      so that it can renew the registration.  A delivery is not a
      runtime presentation.

   Governing Statement:  The statement that bounds a statement-governed
      registration: the one consumed at registration or, after a
      renewal, the replacement that renewed it most recently
      (Section 3.2).

   Statement-Governed Registration:  An [RFC7591] client registration,
      at a server advertising
      software_statement_registration_validity_supported with a value of
      true, whose validity is bound to a software statement's effective
      expiry and renewed by replacement statements (Section 3.1).

3.  Consumption at Registration

   The statement is consumed in the software_statement member of an
   [RFC7591] registration request.  The authorization server validates
   it under the validation rules of [STATEMENT] and registers the client
   under its ordinary registration policy.

   In [RFC7591], values in a software statement take precedence over
   those in the request; a statement under [STATEMENT] carries no client
   metadata, so the reviewed document takes that role.  An authorization
   server consuming a statement under this specification:

   *  MUST resolve the Client ID Metadata Document at the statement's
      sub, rejecting the registration where retrieval does not complete;

   *  MUST validate the document as [CIMD] requires, including that its
      client_id member matches the client identifier URL it is held for,
      which is the statement's sub;

   *  MUST verify that the digest of the retrieved representation equals
      cimd_digest, rejecting the registration where it does not, and
      MUST derive the registered metadata by parsing the same octets it
      digested, not a second retrieval or a cached copy it has not
      digested;

   *  MUST take every client metadata value from that document, and MUST
      NOT take any client metadata value from the registration request,
      or from any [RFC7592] update request for the registration it
      creates, whether or not the document carries that member:

      -  the registration's metadata changes only by re-derivation from
         the document a replacement statement reviews (Section 3.2);

      -  a request MAY carry metadata, as [RFC7591] clients do, but it
         does not contribute to the registration; and

      -  the registered client_id is assigned as [RFC7591] provides, and
         the document's own client_id member is the URL recorded as sub;

   *  MUST reject the registration with invalid_client_metadata where
      the document omits token_endpoint_auth_method, since the [RFC7591]
      default is a shared-secret method that [CIMD] forbids, and
      registering under it would issue a client secret to any holder of
      a copy of the statement;

   *  MUST reject the registration with invalid_client_metadata where
      the document declares token_endpoint_auth_method of none, since
      such software is admitted instead, where the server supports it,
      by runtime presentation, which binds each installation to the
      reviewed redirection URIs and a key it holds (see the public-
      client presentation rules of [STATEMENT]); and

   *  MUST reject the registration with invalid_client_metadata where
      any of the document's redirection URIs could be claimed by another
      application on the same device (see the public-client presentation
      rules of [STATEMENT]), whatever authentication method the document
      declares.

   Registration has no review-only form, as runtime presentation does
   ([STATEMENT]), because the registration is the admission.

   Taking every value from the document prevents metadata substitution.
   At registration a statement is a bearer artifact, so a request-
   supplied value for a member the document omits, such as a jwks beside
   a document naming only jwks_uri, would give any holder of a copy a
   registration with reviewed branding and its own key.

   The retrieval is client-controlled and reachable before any client is
   registered, so the external-retrieval protections and resource bounds
   of [STATEMENT] apply to it as to a runtime presentation.  The
   authorization server completes every check of [STATEMENT] that needs
   no client-controlled retrieval, including the signature and the
   identifier scope of sub, before resolving the document, as it does
   for a presentation.

3.1.  Registration Validity

   An authorization server that advertises
   software_statement_registration_validity_supported as true MUST apply
   the following validity model to every registration it creates from a
   validated software statement, whichever issuer signed it, so that a
   client can rely on the signal (Section 8) before it registers:

   *  it MUST record the governing statement's iss, jti, sub, and iat,
      and any claim by which a withdrawal mechanism locates it, such as
      status, with the registration, and the registration's effective
      expiry, which is the governing statement's effective expiry
      ([STATEMENT]), what a renewal extends, and what
      registration_expires_at reports;

   *  the registration is valid until that effective expiry;

   *  once the effective expiry passes without a replacement
      (Section 3.2), it MUST reject authorization, token, and pushed
      authorization requests and [RFC7592] update requests under the
      registration, other than the revalidation requests Section 3.2
      permits, since the remedy is a replacement statement:

      -  it rejects them with statement_required ([STATEMENT]), but
         rejects an [RFC7592] update request with
         invalid_software_statement, since the governing statement is
         expired or refused;

      -  [RFC7592] read and delete requests remain available so that a
         client can learn its registration's state and end it; and

      -  at the token and pushed authorization request endpoints, it
         first authenticates the client against the retained
         registration and rejects a request that fails that
         authentication with invalid_client, as for an unknown client;
         and

   *  it SHOULD retain the expired record so that it can process a later
      authenticated revalidation (Section 9.4); since a valid
      replacement restores the registration (Section 3.2), no grace
      period is needed.

   At the authorization endpoint, the rejection is returned in the
   authorization error response [RFC6749], so that a client can tell a
   lapsed registration from a policy it will never satisfy.  The
   authorization server redirects with it only after validating the
   request's redirect_uri against the retained registration; where it
   cannot, it MUST NOT redirect and reports the error to the resource
   owner instead.  The client then delivers a replacement in a pushed
   authorization request (Section 3.2).

   The effective expiry is an upper bound.  Where the server holds a
   refusal record for the governing statement ([STATEMENT]), the
   registration ceases to be valid as it does at its effective expiry,
   and Section 3.2 is the recovery path; the client learns of the
   withdrawal only from the rejection.  The disposition of outstanding
   grants is local policy.

   A server applying this model that uses a withdrawal mechanism for the
   governing statement's issuer SHOULD consult it for that statement at
   each token request under the registration, as [STATEMENT] provides
   for refresh, so that a withdrawal reaches the registration and not
   only runtime grants.

   An authorization server advertising this model MUST publish
   pushed_authorization_request_endpoint, since Section 3.2 otherwise
   leaves a client whose only grant type is the authorization code, and
   which holds no refresh token, with no way to renew.

   A server applying this model MUST return a registration_expires_at
   member, a NumericDate (Section 2 of [RFC7519]) giving the latest time
   the registration remains valid, in the [RFC7591] registration
   response and in the response to any request that renews the
   registration or carries its governing statement (Section 3.2), and
   SHOULD return it in any [RFC7592] read or update response it
   supports.  For a registration that has ceased to be valid, the value
   is the time it ceased.  A client cannot compute this boundary from
   the statement alone, because the server can cap the lifetime it
   honors for the issuer ([STATEMENT]).

   A server that omits the signal or advertises false does not bound
   registrations by statement expiry but still consumes the statement as
   Section 3 requires.

3.2.  Revalidation

   A client renews a statement-governed registration by delivering a
   replacement statement in one of the following:

   *  the software_statement parameter of a token request under the
      registration, authenticated as the registered client under the
      registration's own method;

   *  the software_statement parameter of an authenticated pushed
      authorization request [RFC9126] under the registration; or

   *  the software_statement member of an authenticated [RFC7592] update
      request, where the deployment offers registration management.

   The update request carries the complete client metadata that
   [RFC7592] requires, which the server does not take (Section 3).

   A statement with the governing statement's iss and sub and an iat no
   later than the governing statement's iat, such as the governing
   statement itself, is not a replacement.  A client offers one in an
   ordinary [RFC7592] update request, which repeats the statement a
   registration, read, or update response returned unmodified
   (Section 3.2.1 of [RFC7591]; Section 2.2 of [RFC7592]), even after a
   token or pushed authorization request has renewed the registration,
   and may offer the governing statement again after losing the response
   to the request that made it governing.  The authorization server
   leaves the registration unchanged and treats the request as carrying
   no replacement: the request proceeds while the registration is valid
   and is rejected as Section 3.1 provides once it is not.

   An [RFC7592] read or update response returns the governing statement
   as its software_statement member.

   The replacement MUST:

   *  validate under the validation rules of [STATEMENT], including its
      audience where it carries one;

   *  carry the governing statement's iss and sub; and

   *  have an iat later than the governing statement's iat.

   For a replacement, the authorization server MUST:

   *  obtain the Client ID Metadata Document at the replacement's sub by
      retrieval, as Section 3 requires;

   *  verify that the digest of those octets equals the replacement's
      cimd_digest; and

   *  re-derive the registration's metadata from those same octets,
      under the rules of Section 3.

   Renewing on the statement alone would leave the registration carrying
   metadata the new review never covered, so a removed key, redirection
   URI, or scope would survive its own withdrawal.

   On success, the replacement becomes the governing statement: the
   authorization server MUST replace the recorded identity, iat,
   effective expiry, and derived metadata with the replacement's in a
   single atomic update, and concurrent deliveries resolve to the most
   recently issued statement.

   Access issued under the registration after that update, including on
   refresh of a grant issued before it, MUST fall within the re-derived
   metadata, as [STATEMENT] requires of a refreshed grant.

   When a request under an expired registration contains a replacement,
   the authorization server MUST authenticate the client against the
   retained registration and evaluate the replacement before applying
   the expiry rejection.  A valid replacement therefore restores the
   registration; an omitted or invalid replacement does not.

   The rejection of a request under an expired registration that carries
   no replacement (Section 3.1) MUST NOT by itself trigger the refresh-
   token family revocation of [RFC9700]; the client recovers by
   delivering a valid replacement.

   A request whose replacement fails the rules above is rejected whether
   or not the registration has expired, so that the client learns of the
   failure at once and can tell a bad replacement from a missing one.
   It is rejected with statement_required at the token and pushed
   authorization request endpoints, or with temporarily_unavailable
   there where a retrieval needed to check the replacement did not
   complete for a reason other than the size bound of [STATEMENT], and
   with the codes of Section 6 at the registration management endpoint.
   A rejected delivery leaves the governing statement unchanged.

   A registration request without an [RFC7592] registration access token
   creates a new registration and never renews an existing one.

4.  Statements from a Registered or Admitted Client

   A client an authorization server already has, whether registered
   through [RFC7591] or admitted under its Client ID Metadata Document
   URL as its client_id, can still carry a statement.  Runtime
   presentation ([STATEMENT]) does not alter a registration's metadata.
   A statement carried under a registration from an issuer the server
   does not accept for that client is rejected as Section 6 defines.

   For a statement-governed registration, a statement from the governing
   issuer is a delivery under Section 3.2.  While the registration is
   valid, its governing statement is current, even after a later
   statement has raised the iat floor of [STATEMENT], and satisfies any
   requirement the server has for a current statement on refresh.

   Where the registration is not statement-governed, a statement neither
   renews nor alters it; the server applies a reviewed change, if at
   all, through its own registration policy, deriving metadata only from
   a reviewed document (Section 3).

5.  Repeated Registration

   One unexpired statement can be consumed more than once, within the
   bounds of [STATEMENT]; the safe default is one registration per (iss,
   sub) at one authorization server.  On repeated consumption, local
   policy can reject the request, treat it as idempotent, or create
   another registration; [RFC7591] defines no duplicate-registration
   protocol.  An idempotent response MUST NOT return the existing
   registration's credentials, such as its registration_access_token,
   since a repeated request can come from any holder of a copy of the
   statement.

6.  Error Responses

   A rejection this specification defines, at a registration endpoint or
   at the registration management endpoint of [RFC7592], uses the error
   response of Section 3.2.2 of [RFC7591], with the HTTP status code
   that section specifies.  An authorization server SHOULD respond to a
   request it rejects with temporarily_unavailable with HTTP status code
   503.

   Rejections of a registration management request for other reasons,
   such as an invalid registration access token, an unknown client, or a
   request the client is not permitted to make, use the responses
   [RFC7592] specifies.  Rejections at other endpoints use the error
   responses of [STATEMENT], and registration expiry is reported as
   Section 3.1 defines.

   An authorization server rejecting a registration request, or a
   registration management request carrying a failing replacement, uses
   the following error codes:

   invalid_software_statement:  The statement is malformed, fails
      signature or claim validation, or is expired, refused by a refusal
      record, or superseded under the iat floor of [STATEMENT]; or the
      digest of the retrieved document does not match its cimd_digest.

   unapproved_software_statement:  The statement is valid but not
      acceptable here: its issuer is not configured, its aud excludes
      this server, its sub is outside the issuer's scope, its aud_tenant
      is not this request's tenant or is absent where required, or its
      statement_uses excludes this use.  This code is also used where a
      statement this server requires is absent.

   invalid_client_metadata:  The reviewed document:

      *  contains duplicate member names ([STATEMENT]);

      *  carries metadata this server's policy refuses;

      *  exceeds the server's size bound ([STATEMENT]), so that retrying
         cannot succeed;

      *  omits token_endpoint_auth_method (Section 3);

      *  declares token_endpoint_auth_method of none (Section 3); or

      *  carries a redirection URI another application could claim
         (Section 3).

   temporarily_unavailable:  A retrieval the request needs did not
      complete, for a reason other than the size bound.

7.  Example

7.1.  Revalidating a Statement-Governed Registration

   The following non-normative example shows a registered client,
   client_id s6BhdRkqt3, renewing its registration by delivering a
   replacement statement on an ordinary refresh, authenticated under its
   registered private_key_jwt method (line breaks are for display
   purposes only):

   POST /token HTTP/1.1
   Host: as.example
   Content-Type: application/x-www-form-urlencoded

   grant_type=refresh_token
   &refresh_token=tGzv3JOkF0XG5Qx2TlKWIA
   &client_id=s6BhdRkqt3
   &client_assertion_type=urn%3Aietf%3Aparams%3Aoauth%3A
   client-assertion-type%3Ajwt-bearer
   &client_assertion=eyJhbGciOiJFUzI1NiIsImtpZCI6IjIwMjYtMDgifQ...
   &software_statement=eyJ0eXAiOiJzb2Z0d2FyZS1zdGF0ZW1l...

   The authorization server validates the replacement, matches its iss
   and sub to the governing statement, re-derives the registration's
   metadata, and atomically extends the registration's validity,
   returning the new boundary in the registration_expires_at member of
   the token response.  After expiry, the same request without a
   replacement would fail with statement_required (Section 3.1).

8.  Authorization Server Metadata

   This specification defines the following authorization server
   metadata [RFC8414] value:

   software_statement_registration_validity_supported:  OPTIONAL.
      Boolean value indicating whether every registration the
      authorization server creates from a validated software statement
      is governed by the validity and revalidation rules of Section 3.1
      and Section 3.2.  If omitted, the default value is false.  A value
      of true does not imply support for runtime presentation.

9.  Security Considerations

9.1.  Statements at Registration

   A statement consumed at registration is a reusable bearer artifact
   until it expires.  Its audience, lifetime, and statement_uses claim
   ([STATEMENT]) and the bounds of Section 5 limit what a stolen
   statement can create.

   Under the one-registration default (Section 5), whoever first
   registers with a copy of a statement holds that registration and its
   registration access token, and can keep the software's publisher from
   registering at that server.  Such a holder cannot authenticate as the
   client where the reviewed document's authentication method requires a
   key the document carries.

   Where the publisher's statement permits presentation and the server
   supports it, the publisher's software can still be admitted through
   runtime presentation ([STATEMENT]), which binds every presenter to
   the reviewed document; otherwise, recovery requires the server's
   operator to intervene or a registration policy other than the one-
   registration default.  This specification defines no way to displace
   such a registration.

9.2.  Renewal Authenticates the Credential

   Renewal proves possession of the registration's credential and the
   currency of a statement sharing the governing iss and sub, not that
   the renewing party is the reviewed software.  An attacker holding a
   stolen client credential can renew indefinitely with any current
   statement for that software, since such statements circulate to every
   deployment of it.

   Deployments should pair statement-governed registrations with
   credential rotation, sender-constrained client authentication, and
   the repeated-consumption limits of [STATEMENT] and Section 5, and
   should treat a credential compromise as requiring re-registration
   rather than renewal.  Runtime presentation ([STATEMENT]) does not
   have this limitation, because it binds every presenter to the
   reviewed document.

9.3.  Registration Fraud and Impersonation

   Open registration permits client_name, logo_uri, and client_uri
   values that imitate trusted software on consent screens (Section 5 of
   [RFC7591]).  Requiring a statement replaces self-asserted branding
   with issuer-reviewed values.  Servers that render such values on
   consent screens should prefer those from a reviewed document and
   should apply heightened scrutiny to registrations that claim user-
   visible branding without a statement.

   Requiring a statement for registration also means each new client
   identity needs another issuer decision, so a discarded client cannot
   return at no cost.  Neither requirement makes metadata true: a client
   that misleads review can obtain a genuine statement for fraudulent
   metadata, so a statement is only as reliable as the issuer's
   verification.

9.4.  Observable State

   A retained expired registration is distinguishable from an unknown
   client, because recovery requires the server to authenticate the
   registration and evaluate a replacement before rejecting.  At the
   token and pushed authorization request endpoints, only a requester
   that authenticates as the registration's client can observe this, and
   what it learns is the state it must act on.

   At the authorization endpoint, anyone who can send an authorization
   request naming the client and one of its registered redirection URIs
   receives the statement_required redirection (Section 3.1), and so
   learns that the registration has lapsed.  Where an observer knows the
   governing statement's exp, a lapse before it shows that the server
   either holds a refusal record for the statement or caps the lifetime
   it honors for the issuer.

   The disclosures above are accepted for the reason [STATEMENT] gives
   for its own statement_required refusal: a client that cannot learn
   why it was refused cannot act.  Servers publishing
   software_statement_registration_validity_supported also disclose that
   statement-derived registrations expire there, which a client needs to
   know before registering.  Beyond a lapse and its timing, these
   disclosures reveal nothing of the server's issuer trust
   configuration, which [STATEMENT] keeps from unauthenticated
   requesters.

10.  Privacy Considerations

11.  IANA Considerations

11.1.  OAuth Dynamic Client Registration Metadata Registry

   This specification requests registration of the following client
   metadata member, returned by an authorization server in a
   registration response:

   Client Metadata Name:  registration_expires_at

   Client Metadata Description:  Latest time at which a statement-
      governed registration remains valid, as a NumericDate.  A
      withdrawal can end it earlier.  Returned in a client registration
      response, in a registration management response, and in the token
      or pushed authorization request response to a request that renews
      the registration or carries its governing statement.

   Change Controller:  IESG

   Specification Document(s):  This specification, Section 3.1

11.2.  OAuth Parameters Registry

   This specification requests registration of the following parameter
   in the IANA "OAuth Parameters" registry established by [RFC6749], for
   the responses to requests that renew a statement-governed
   registration or carry its governing statement:

   Parameter Name:  registration_expires_at

   Parameter Usage Location:  token response, pushed authorization
      request response

   Change Controller:  IESG

   Specification Document(s):  This specification, Section 3.1

11.3.  OAuth Authorization Server Metadata Registry

   This specification requests registration of the following value in
   the IANA "OAuth Authorization Server Metadata" registry established
   by [RFC8414].

   Metadata Name:  software_statement_registration_validity_supported

   Metadata Description:  Boolean value indicating whether registrations
      created from validated software statements are governed by the
      statement validity and revalidation rules of this specification.

   Change Controller:  IESG

   Specification Document(s):  This specification, Section 8
