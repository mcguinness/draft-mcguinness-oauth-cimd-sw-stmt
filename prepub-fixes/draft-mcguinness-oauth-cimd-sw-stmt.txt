             Client ID Metadata Document Software Statement
               draft-mcguinness-oauth-cimd-sw-stmt-latest

Abstract

   A Client ID Metadata Document carries a client's own claims, which
   can change at any time.  This specification defines a software
   statement in which a trusted party records its review of the exact
   bytes of such a document, and how an authorization server enforces
   that review when it admits the client at request time, without a
   registration.  The client presents the statement in a token or pushed
   authorization request, or publishes it where the reviewed document
   points.  Possession of the statement alone does not complete a grant:
   the presenter is also bound to the reviewed document.  Because the
   document remains the metadata, one review is portable across the
   authorization servers that trust its issuer.  A companion
   specification covers RFC 7591 registration.

1.  Introduction

   A Client ID Metadata Document [CIMD] identifies a client by a URL and
   supplies its metadata from a document the client controls.  That
   metadata is the client's own claim and can change at any time.  An
   organization that reviews client software has no interoperable way to
   record its review of a particular version of the document, or to have
   an authorization server it has never dealt with enforce that review.

   This specification profiles the software statement (Section 2.3 of
   [RFC7591]) for that purpose.  A statement names the client by its
   document URL and binds the review to the document's exact octets by a
   digest (Section 3.1).  An authorization server that trusts the
   statement's issuer (Section 4) admits the client at request time on
   the reviewed document, and no other, without creating a registration
   (Section 5), so one review is portable across every authorization
   server in the statement's audience.

   This specification serves deployments in which a party other than the
   client decides which software can connect, such as a marketplace or
   registry that vouches for software to authorization servers it does
   not operate, or an enterprise that approves software for its users at
   a service run by someone else.  It also serves server-hosted
   software, such as an agent, that uses the client_credentials grant.
   Admission grants no access to resources: the authorization server's
   policy, and the resource owner's authorization where a grant involves
   one, still govern what it issues.

   Presentations by a native application whose redirection URIs another
   application on the device could claim are review-only (Section 5.4.1)
   until an extension binds an installation key that a third party
   vouches for (Section 11).

   A statement records approval of a client configuration, not of the
   software's code or behavior (Section 14.1).  Possession of a
   statement alone admits nothing: the presenter is bound to the
   reviewed document (Section 5.4), though for a public client that
   binding does not hold against a party that controls the user agent
   (Section 14.4).

   This specification does not define how a client obtains a statement.
   [REGISTRATION] builds on this specification, which does not depend on
   it, to define consumption of the same statement in an [RFC7591]
   registration request.  Section 7 relates this specification to other
   work.

1.1.  Protocol Overview

   The following non-normative sequence summarizes runtime admission:

   1.  Using its Client ID Metadata Document URL as client_id, the
       client presents its statement in a token request or, for a
       redirect flow, a pushed authorization request, or publishes it at
       the software_statements_uri its document names (Section 5.1,
       Section 5.2).

   2.  The authorization server validates the statement (Section 3.2),
       resolves the reviewed document (Section 5.5), and verifies the
       sender constraint against it (Section 5.4).

   3.  The request proceeds under that document's metadata, without a
       registration.

   4.  The state on which the rest of the grant depends persists as an
       establishment (Section 5.6).

2.  Conventions and Definitions

   The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT",
   "SHOULD", "SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED", "MAY", and
   "OPTIONAL" in this document are to be interpreted as described in
   BCP 14 [RFC2119] [RFC8174] when, and only when, they appear in all
   capitals, as shown here.

   This specification uses terminology from [RFC6749] (OAuth), [RFC7591]
   (client metadata and software statements), and [CIMD] (Client ID
   Metadata Documents).

   This specification defines the following terms.

   Trusting Authorization Server:  An authorization server that consumes
      a software statement, at runtime under this specification or at
      registration under [REGISTRATION].

   Runtime Presentation:  The consumption of a validated software
      statement presented in a token request or pushed authorization
      request, or pulled from where the client's document points
      (Section 5.2), without creating a client registration.

   Establishment:  The durable state a successful runtime presentation
      creates for the grant it opens, or that a replacement accepted on
      refresh gives that grant, enumerated in Section 5.6.

   Recorded Statement:  The statement an establishment records: the one
      presented or pulled to create it or, after a refresh accepts a
      replacement, the replacement most recently accepted for it
      (Section 5.6.1).

   Proven Key:  The key an establishment is bound to: the key whose
      possession the presenter proves during runtime presentation
      (Section 5.4), the key it binds under Section 5.4.1, or, for a
      statement pulled at the authorization endpoint, the key proved at
      code redemption (Section 5.2).

   Effective Expiry:  The earlier of a statement's exp and its iat plus
      the maximum statement lifetime the trusting authorization server
      honors for its issuer (Section 4).  A statement is expired once
      its effective expiry has passed.

   Refusal Record:  State an authorization server holds when it has
      learned that a statement ceased to be acceptable before its
      expiry, whether from a withdrawal mechanism it uses for the issuer
      (Section 3.3) or from its own operator.

   Current Statement:  A statement whose effective expiry has not passed
      and that matches no refusal record.  The iat floor (Section 6)
      separately limits which current statements a server accepts.

   Review-Only:  Describes a presentation, or a pulled statement, that
      the authorization server evaluates but that admits nothing
      (Section 5.4.1).

   iat Floor:  For a trusting authorization server, the greatest iat
      claim value among the statements it has accepted for a given iss
      and sub, per tenant on a multi-tenant server (Section 6).

3.  The Software Statement

   The software statement is a compact JWT [RFC7519] protected by JWS
   [RFC7515].  Although [RFC7591] permits a MAC, a statement issued
   under this specification MUST use an asymmetric digital signature,
   and the none algorithm and symmetric algorithms MUST NOT be used.
   Issuers and trusting authorization servers follow [RFC8725].

   The JOSE header MUST include the kid header parameter, identifying
   the signing key in the issuer's statement key set (Section 4), and
   the typ header parameter with the value software-statement+jwt
   (Section 3.11 of [RFC8725]).  Extensions can add claims.  An
   incompatible revision would use a new typ value.

   A statement asserts that its issuer evaluated the Client ID Metadata
   Document whose content the digest identifies, and vouches for that
   document.  The JWT payload contains the following claims.

   iss:  REQUIRED.  The issuer's identifier, a URL using the https
      scheme with no query or fragment component.  For an issuer that is
      an authorization server, it is its issuer identifier as defined by
      [RFC8414].

   sub:  REQUIRED.  The exact client identifier URL of the Client ID
      Metadata Document the issuer reviewed.

   aud:  OPTIONAL.  One or more authorization server issuer identifiers
      ([RFC8414]) restricting which authorization servers can accept the
      statement.  If the claim is absent, any authorization server that
      trusts the issuer for the subject can accept it (Section 4).

   aud_tenant:  OPTIONAL.  A tenant identifier at a trusting
      authorization server, as [IDJAG] defines the claim, naming the
      tenant in which the statement's decision applies.  A statement
      whose decision is confined to one of a server's tenants MUST carry
      an aud claim naming exactly one authorization server and, unless
      that server confines the issuer to the tenant through its own
      trust configuration (Section 4), an aud_tenant claim naming the
      tenant.

      The absence of aud_tenant does not mean that the statement applies
      in every tenant (Section 13.2).

   statement_uses:  OPTIONAL.  A JSON array identifying the permitted
      uses of the statement: registration ([REGISTRATION]) and
      presentation (Section 5).  If the claim is absent, only
      presentation is permitted.  A delivery renewing a registration
      ([REGISTRATION]) is a registration use.  A refresh replacement
      (Section 5.6.1) and a pulled statement (Section 5.2) are
      presentation uses.

   iat:  REQUIRED.  A NumericDate value, which MUST be an integer,
      giving the time the statement was issued.  An issuer MUST ensure
      that the iat claim values of its statements for a given iss and
      sub increase strictly, whichever of its signing nodes signs
      (Section 5.6.1, Section 6).

   exp:  REQUIRED.  A NumericDate value giving the expiration time.

   jti:  REQUIRED.  A unique identifier for the statement within the
      issuer's namespace.

   cimd_digest:  REQUIRED.  The metadata digest (Section 3.1) of the
      Client ID Metadata Document the issuer evaluated.

   status:  OPTIONAL.  The status claim as [STATUSLIST] defines it, by
      which a statement locates itself in a Status List Token.  Only a
      withdrawal mechanism that uses the claim processes it.  This
      specification does not (Section 3.3).

   A statement issued under this specification MUST NOT contain a claim
   named in the IANA "OAuth Dynamic Client Registration Metadata"
   registry, and a trusting authorization server MUST NOT take client
   metadata from a statement's claims.

   [CIMD] permits a Client ID Metadata Document to carry a
   software_statement member.  A trusting authorization server MUST NOT
   consume a statement of this profile from that member, and MUST NOT
   treat that member as satisfying any requirement of this
   specification.  Statements of other kinds in the member are out of
   scope for this specification.

   An authorization server implementing this specification MUST reject a
   statement of this profile in an [RFC7591] registration request with
   the unapproved_software_statement error code (Section 3.2.2 of
   [RFC7591]), unless it consumes the statement as [REGISTRATION]
   specifies.  The server's configured statement key set (Section 4)
   verifies the statement, so a generic registration path would
   otherwise attach the issuer's review to metadata the request supplies
   (Section 14.3).

3.1.  Metadata Digest

   The metadata digest is the unpadded base64url-encoded SHA-256 hash
   [RFC6234] of the retrieved representation body after removal of
   content coding.  The body is not transcoded, normalized, or re-
   serialized.  Any byte order mark or trailing newline is included.

   Retrieval for digest purposes follows [CIMD] and MUST NOT use content
   negotiation: the retrieving party sends the Accept header field that
   [CIMD] specifies for retrieving the document, or Accept: application/
   json if it specifies none, and no other variant selection.  Equal
   digests show that the issuer and the trusting authorization server
   obtained the same octets, so any condition that makes retrieval
   depend on who is asking defeats the comparison.

   A trusting authorization server MUST treat a response exceeding its
   configured size bound (Section 8.7 of [CIMD]) as a retrieval failure
   rather than digesting what it read.  For a runtime presentation, the
   request is rejected with invalid_client rather than
   temporarily_unavailable (Section 8), except on refresh-token use, for
   which Section 5.6.1 takes precedence.

   A server MUST NOT compare a digest against any representation other
   than one it retrieved itself or stored under this section.  A 304 Not
   Modified response shows that stored octets, and their digest, are
   still current only if it carries a strong entity tag that matches the
   one stored with them under strong comparison (Section 8.8.3.2 of
   [RFC9110]).  Otherwise, the server retrieves the body again.

3.2.  Validating a Statement

   Before accepting a statement, a trusting authorization server MUST
   ensure the following:

   *  The typ JOSE header parameter has the value software-
      statement+jwt.

   *  The signature verifies under a key trusted for the exact iss
      value, obtained as Section 4 requires.

   *  Every required claim of Section 3 is present and of the correct
      type.

   *  The statement is not expired, and its iat is not unreasonably far
      in the future according to the server's clock-skew policy.

   *  If the statement carries aud, a value in it exactly matches one of
      the server's audience identifiers that its trust configuration
      permits the statement's issuer to name (Section 4).

   *  If the statement carries aud_tenant, aud carries exactly one value
      and aud_tenant identifies the tenant this request belongs to,
      resolved before the statement is evaluated, by the server's own
      means or from a signed assertion it has validated, and never from
      a value the client chooses.

   *  If the server requires a tenant-scoped decision for the request,
      the statement carries aud_tenant, or the server's trust
      configuration confines the statement's issuer to the request's
      tenant (Section 4).

   *  If the server's trust configuration confines the statement's
      issuer to a tenant, the request belongs to that tenant.

   *  The use being made of the statement is one it permits: a use its
      statement_uses claim names or, if the claim is absent,
      presentation (Section 3).  A value the server does not recognize
      names no use it serves.

   *  The sub claim is a client identifier URL conforming to [CIMD] and
      falls within the client identifier namespaces for which this
      server accepts the issuer (Section 4).

   *  Any claim the server does not recognize, and any client metadata
      claim (Section 3), is ignored.

   *  The JWT validation guidance in [RFC8725] has been applied.

   A trusting authorization server that hosts more than one tenant MUST
   evaluate every tenant-specific check, such as the aud_tenant claim
   and a required issuer (Section 4), against the tenant that scopes
   what it issues on the statement, never selected by a value the client
   chooses.

   A trusting authorization server MUST reject a statement for which it
   holds a refusal record (Section 3.3).  A server that uses a
   withdrawal mechanism for the statement's issuer SHOULD consult it
   before accepting the statement for a new admission, within the
   caching and freshness rules that mechanism defines.

   A trusting authorization server resolving the reviewed document MUST
   reject a document containing duplicate object member names.  Parsers
   interpret such names differently despite an identical digest.

   Rejections outside a registration endpoint use Section 8.

3.3.  Withdrawal

   An issuer can end a decision before the statement's exp by
   withdrawing the statement.  Unlike OAuth token revocation
   ([RFC7009]), a withdrawal revokes no issued token: a server holding a
   refusal record refuses new admissions and refresh under the statement
   (Section 5.6.1, Section 14.7).

   How a trusting authorization server learns of a withdrawal is a
   withdrawal mechanism.  This specification requires no withdrawal
   mechanism and defines none.  Extensions define how a mechanism
   applies to these statements (Section 11).

   A refusal derived from a withdrawal mechanism lasts until a later
   authoritative result from that mechanism supersedes it, or until an
   expiry the mechanism itself defines for the withdrawal.  A server
   MUST NOT retain such a refusal once it is superseded or expired in
   that way.  A failure to consult the mechanism, or cached evidence
   that has lapsed, neither supersedes nor expires a refusal.

   A withdrawal constrains and never relaxes.  A statement for which no
   withdrawal mechanism reports a withdrawal, or for which the server
   cannot consult the mechanism it uses (Section 13.4), is bounded by
   its effective expiry as it would be otherwise, and a server MUST NOT
   treat any withdrawal mechanism as grounds to accept a statement past
   its effective expiry.

   An issuer that uses a withdrawal mechanism and issues a replacement
   narrower than the statement it replaces SHOULD withdraw the earlier
   statement.  A replacement is narrower if the document it names no
   longer carries a key, redirection URI, or scope the earlier document
   carried, if its aud, aud_tenant, or statement_uses is narrower, or if
   its remaining lifetime is shorter.

   Without that withdrawal, a trusting authorization server that has not
   yet seen the replacement, or at which the replacement does not
   validate, accepts the earlier statement until it expires.

4.  Issuer Trust Establishment

   A trusting authorization server accepts statements only from
   configured issuers.  Trust is established out of band.  This
   specification defines no in-band issuer discovery or trust decision.

   For each trusted issuer, a trusting authorization server records at
   least the following:

   *  The exact iss identifier it will accept.

   *  The source of that issuer's statement signing keys, which is never
      a jwks_uri metadata value: either the software_statement_jwks_uri
      in the issuer's authorization server metadata (Section 10),
      discovered from the configured iss as [RFC8414] describes, or, for
      an issuer that is not an authorization server, a statement key set
      URL recorded in this trust configuration.

   *  The signing algorithms it will accept from the issuer.

   *  The client identifier namespaces the issuer can attest through
      sub.

   *  The audience identifiers the issuer can name.

   *  Any tenant to which it confines the issuer's decisions.

   *  For each of its tenants, any client identifier namespaces for
      which the issuer is a required issuer, one whose current statement
      the server requires in that tenant for software in those
      namespaces.

   *  The maximum statement lifetime it will honor, which sets each
      statement's effective expiry.

   *  Its own policy on repeated consumption of one statement
      (Section 6).

   A statement key set whose URL is recorded in trust configuration is
   subject to rules corresponding to those Section 10 sets for
   software_statement_jwks_uri: its URL MUST use the https scheme, a
   trusting authorization server MUST validate the certificate of the
   host serving it, and the issuer MUST NOT place in it a key from any
   other JWK Set it publishes, or sign anything other than statements
   under this specification with its keys.

   Whichever route supplies it, a trusting authorization server MAY
   reuse a retrieved statement key set only within ordinary HTTP caching
   bounds and a maximum reuse period of its own choosing, and MUST NOT
   let the issuer's cache directives alone determine how long a removed
   key continues to verify.  If retrieving the key set does not
   complete, the authorization server rejects the request with
   temporarily_unavailable, except that a pull for a request opening a
   new grant proceeds as Section 5.2 describes.

   These inputs, not the signature alone, define acceptance.  A trusting
   authorization server MUST derive trust from this local configuration
   and MUST NOT derive it from an iss, jku, x5u, or other key-location
   value carried in a presented statement.

   A server that records, for one of its tenants, client identifier
   namespaces for which a configured issuer's decision is required
   (Section 13.1) MUST NOT admit software in a covered namespace in that
   tenant without a current statement from the required issuer, whatever
   its policy for clients it has not reviewed.  The requirement also
   applies on refresh (Section 5.6.1).  Without this rule, a holder
   could evade the required issuer's withdrawal by withholding that
   issuer's statement or by presenting or publishing only a broader one,
   such as a marketplace listing.

   A required issuer configured for software whose presentations are
   review-only (Section 5.4.1) excludes that software from the tenant.
   The server rejects a request for such software in that tenant with
   unauthorized_client.

4.1.  Multi-Tenant Issuers

   If an issuer reviews software for several customers whose decisions
   are each trusted independently, it MUST issue under a distinct iss
   value for each customer, so that each customer's decisions and iat
   floor (Section 6) stay separate.

5.  Runtime Presentation

   A client presents its statement in a request (Section 5.1) or
   publishes it where its document points (Section 5.2).

5.1.  Presentation Request

   A client presents a software statement by including the following
   parameter in a token request or a pushed authorization request:

   software_statement:  REQUIRED for presentation.  The software
      statement (Section 3).  It is consumed as a runtime presentation,
      a refresh replacement (Section 5.6.1), or, if [REGISTRATION] is
      implemented, a delivery under that specification.  A request
      carrying the parameter in any other role is rejected with
      invalid_request.

   A request making a runtime presentation, or carrying a refresh
   replacement (Section 5.6.1), MUST include the client_id parameter,
   even if the client authenticates, and its value, the client's Client
   ID Metadata Document URL, MUST exactly equal the statement's sub
   claim.  If the client_id parameter is absent, the authorization
   server rejects the request with invalid_request.  If the two differ
   in a runtime presentation, the authorization server MUST reject the
   presentation with the invalid_client error code.  A refresh
   replacement whose sub differs is rejected as Section 5.6.1 provides.
   The effective client_id is the statement's sub, and the authorization
   server assigns none.

   The request carries the proof that Section 5.4 requires.  A
   successful presentation establishes the client for the request and
   for the grant state derived from it (Section 5.6).

   At the token endpoint, a runtime presentation is valid on a request
   using any one of the following grants:

   *  The client_credentials grant.

   *  The JWT or SAML 2.0 assertion grant (Section 2.1 of [RFC7523] and
      Section 2.1 of [RFC7522]).

   *  Another grant whose specification provides for runtime
      presentation under this specification.

   Authorization-code redemption and refresh-token use continue an
   existing grant (Section 5.6, Section 5.6.1).  A request that asks an
   authorization server to issue a software statement, rather than to
   consume one, MUST NOT carry the software_statement parameter.

   An authorization server that does not implement this specification
   ignores the parameter (Sections 3.1 and 3.2 of [RFC6749]).

5.1.1.  Authorization Endpoint

   Presentation in an authorization request MUST use a pushed
   authorization request [RFC9126].  A pulled statement needs no pushed
   authorization request (Section 5.2).  The pushed authorization
   request endpoint processes the statement and its proof as Section 5.3
   describes.  The subsequent authorization request MUST use a client_id
   parameter exactly equal to the establishment's sub and MUST NOT
   include the software_statement parameter.

5.2.  Pulled Statements

   This specification defines the following client metadata member:

   software_statements_uri:  OPTIONAL.  URL, in a Client ID Metadata
      Document, at which the client publishes software statements about
      itself.  The member has no meaning in a registration request.  The
      URL MUST use the https scheme.  A request to it returns a JSON
      object whose software_statements member is an array of statements
      (Section 3), each a string in JWS compact serialization.  The
      metadata digest covers this member (Section 3.1).

   An authorization server that supports pulled statements MAY retrieve
   this URL when it resolves the document of a client that presented no
   statement.  In retrieving this URL, the server MUST send a GET
   request with Accept: application/json and MUST NOT automatically
   follow redirects.  It MUST accept a new representation only from a
   200 response with a JSON media type, and can instead reuse a stored
   representation that a 304 Not Modified response revalidates
   (Section 15.4.5 of [RFC9110]).

   Both the document and this URL are retrieved before any statement
   exists to validate, so the ordering of Section 5.3 applies from the
   first statement verified onward.

   The server considers only statements that meet all of the following
   conditions:

   *  The sub claim equals the document's client identifier.

   *  The statement validates under Section 3.2 and permits presentation
      (Section 3).

   *  The cimd_digest claim equals the digest of the document the server
      resolved.

   *  The iat floor of Section 6 does not supersede it.

   The server ignores the rest.

   If the server's trust configuration requires an issuer for this
   client (Section 4), it applies only that issuer's statement, and if
   none remains, the client is not reviewed.  Otherwise, if more than
   one statement remains, the server keeps only the statement with the
   latest iat from each issuer and applies any one of those.  A pulled
   statement the server does not apply does not advance the iat floor.

   Having selected a statement, the server continues from step 4 of
   Section 5.3, with the pulled statement in place of a presented one
   and the document already resolved.  The selection above satisfies the
   client_id rule of step 2.

   The presenter of a pulled statement is bound as for a presented
   statement (Section 5.4), at the point the request allows, as the
   following table shows for every case except the review-only documents
   described after it.  In the table, a public client is one whose
   reviewed document declares token_endpoint_auth_method of none, and a
   confidential client is one whose document declares another method:

    +===============+=====================+==========================+
    | Where the     | Confidential client | Public client            |

   if retrieving the statements, or a statement key set needed to verify
   one (Section 4), did not complete, and with statement_required
   otherwise.  A retrieval failure is never a withdrawal.

5.3.  Presentation Processing

   On receiving a presentation, the authorization server proceeds as
   follows, rejecting as Section 8 defines at the first failure:

   1.  Validate the statement (Section 3.2), completing every check that
       does not require a client-controlled network retrieval before
       performing any such retrieval.

   2.  Verify the statement requirements of Section 3, the iat floor of
       Section 6, and the client_id rule of Section 5.1.

   3.  Resolve the reviewed document (Section 5.5), which is the first
       step requiring a client-controlled retrieval.

   4.  Verify the sender constraint against that document (Section 5.4),
       then evaluate the request against its metadata (Section 5.5).

   5.  On success, create the establishment (Section 5.6).

   Every retrieval this specification causes, of the Client ID Metadata
   Document, a jwks_uri it names, or the statements its
   software_statements_uri names, inherits the server-side request
   forgery protections of [CIMD].  A trusted signature does not make a
   URL safe: the authorization server MUST apply its URL, redirect,
   address-range, transport, and content-type policy independently to
   every referenced location.

   If a retrieval fails, the authorization server MUST reject the
   request and MUST NOT fall back to a weaker proof.  A failed pull of
   statements for a request that opens a new grant is the exception: it
   leaves the client unreviewed, as Section 5.2 describes.

   A retrieval does not complete only when it times out, its connection
   fails, or the response has a 429 (Too Many Requests) status code
   (Section 4 of [RFC6585]) or a 5xx status code, and only then does
   this specification assign temporarily_unavailable.  Any other failure
   to obtain an acceptable representation, such as another 4xx status
   code or a body that is not a JSON object, is final: a document is
   treated as failing validation, a key set as carrying no acceptable
   key, and a statements location as publishing no statement.

5.4.  Sender Constraint

   This specification requires a reviewed document to declare its client
   authentication method.  The authorization server MUST reject a
   presentation under a reviewed document that omits the
   token_endpoint_auth_method member.  It treats a statement pulled for
   such a document as review-only (Section 5.4.1).

   A presentation under a document carrying a redirection URI another
   application could claim is review-only whatever its authentication
   method (Section 5.4.1).  The rejection above still applies to such a
   presentation, as does the rejection of a presentation opening a new
   grant at the token endpoint for a client whose reviewed document
   declares token_endpoint_auth_method of none (Section 5.4.1), but the
   sender-constraint requirements of the next two paragraphs do not.

   A runtime presentation MUST be sender-constrained by a key the
   statement attests or, under Section 5.4.1, by the key the presenter
   binds there.  The presenter proves possession of that key through the
   applicable client authentication method or a DPoP proof [RFC9449].
   If a request carries both, the key its client authentication proves
   is the proven key.  The proof MUST be bound to the current request
   and validated with the replay protections of that mechanism.

   Except as Section 5.4.1 provides, the proven key MUST appear in the
   jwks or at the jwks_uri of the reviewed document (Section 5.5).  If
   the reviewed document declares a client authentication method in its
   token_endpoint_auth_method member ([CIMD]), the presenter MUST use
   that method.  The authorization server MUST reject a presentation
   without such a proof, or whose proven key the reviewed document does
   not carry.

   A key at the document's jwks_uri is retrieved at presentation time.
   If that retrieval does not complete (Section 5.3), the presentation
   is rejected with temporarily_unavailable.  A server MAY reuse a
   retrieved key set only within ordinary HTTP caching bounds and a
   maximum reuse period of its own choosing, and MUST NOT let the
   client's cache directives alone determine how long a removed key
   continues to verify (Section 14.2).

5.4.1.  Public Clients

   Software distributed to end users cannot hold a key its reviewed
   document carries: a key shipped in every copy identifies the
   software, not the installation.  Such a document declares
   token_endpoint_auth_method of none and carries no key material.

   An authorization server MUST reject, with the invalid_client error
   code, a presentation that opens a new grant at the token endpoint
   (Section 5.1) from a client whose reviewed document declares
   token_endpoint_auth_method of none.  Such a presentation opens no
   redirect and has nothing to bind it.  A statement pulled for such a
   client at the token endpoint is instead review-only (Section 5.2).

   A presentation is review-only if the reviewed document carries any
   redirection URI that another application on the same device could
   claim: a non-https URI, such as a private-use scheme or an http
   loopback redirection URI (Sections 7.1 and 7.3 of [RFC8252]), or an
   https URI whose host is a loopback address or localhost.  One such
   URI makes every presentation and pulled statement for the document
   review-only, whatever authentication method the document declares.
   The application that claims such a URI receives the code, so neither
   the reviewed redirection URIs nor a key shipped in every copy of the
   software can bind the presenter.

   A review-only presentation or pulled statement creates no
   establishment, admits nothing, and does not advance the iat floor of
   Section 6.  The authorization server proceeds as it would for the
   same Client ID Metadata Document client presenting no statement
   (Section 12.5).

   The statement of a review-only presentation, or a review-only pulled
   statement, MUST NOT satisfy a policy requiring reviewed software.  If
   the server's policy requires reviewed software, it rejects a review-
   only client with unauthorized_client.

   If the client's reviewed document declares token_endpoint_auth_method
   of none and none of its redirection URIs is one another application
   could claim, a presentation at the pushed authorization request
   endpoint is bound instead by its reviewed redirection URIs.  For such
   a presentation, the authorization server:

   *  MUST require PKCE [RFC7636] with the S256 method.

   *  MUST require the presenter to bind a key it holds, through the
      dpop_jkt parameter or, at the pushed authorization request
      endpoint, a DPoP proof (Section 10.1 of [RFC9449]), and records
      that key as the proven key of the establishment (Section 5.6).

   *  MUST NOT require that key to appear in the reviewed document.

   A statement pulled for such a client at the pushed authorization
   request endpoint or the authorization endpoint (Section 5.2) is bound
   the same way, under the same requirements, if the request uses PKCE
   with the S256 method and binds a key as those requirements provide.
   Otherwise the pulled statement is review-only.

   The reviewed redirection URIs, not the proven key, bind such a
   presentation (Section 14.4).  The proven key identifies the
   installation the grant belongs to.

5.5.  Reviewed Metadata

   Having validated the statement, and before verifying the proof
   (Section 5.3), the authorization server MUST obtain the Client ID
   Metadata Document at the statement's sub, only by retrieval or from
   octets it has already digested for that identifier, and compare its
   digest with the cimd_digest claim.  If octets it already holds do not
   match, it retrieves the document once more before treating the
   mismatch as a change.

   Octets the authorization server already holds serve for that
   comparison only within a maximum reuse period of its own choosing, as
   a key set does (Section 5.4).  The authorization server MUST NOT let
   the client's cache directives alone determine how long held octets
   continue to match a statement.  Without this rule, a key the document
   carries inline would continue to verify after the publisher removes
   it.

   A match means the served document is the reviewed one, and its
   members are the client's metadata for the request.  The server takes
   those members from the octets whose digest matched, not from another
   retrieval or a copy it has not digested.  A mismatch means the
   document changed after review, and the authorization server MUST NOT
   treat the changed document as reviewed.  It rejects the presentation
   with invalid_client or, by local policy, proceeds without the
   statement.  If it proceeds, it applies its policy for Client ID
   Metadata Document clients it has not reviewed to the current document
   and creates no establishment for the statement.

   The request is evaluated against the reviewed metadata as against any
   client's registered metadata ([RFC6749], [CIMD]): any requested grant
   type, response type, or scope MUST fall within it.  A document that
   omits scope sets no ceiling on scope beyond the server's own policy.

5.6.  Grant Lifecycle

   A successful presentation creates an establishment comprising the
   following:

   *  The validated sub.

   *  The statement identity (its iss and jti), its iat and effective
      expiry, and any claim by which a withdrawal mechanism locates it,
      such as status.

   *  The authorization server's own tenant the grant was opened for, if
      it hosts more than one.

   *  The reviewed metadata and the digest it matched (Section 5.5).

   *  The issuer trust decision.

   *  The sender-constraint mechanism and proven key.

   *  Whether the proven key is set at code redemption, for a statement
      pulled at the authorization endpoint for a confidential client
      (Section 5.2).

   The establishment persists while the grant depends on it.  The
   authorization server MUST bind the resulting request_uri,
   authorization code, refresh token, and other grant continuation state
   to the establishment, as applicable (Section 12.4).

   A replacement accepted on refresh MUST apply only to the grant
   refreshed (Section 5.6.1).  Any other grant, request_uri, or
   authorization code bound to the same establishment keeps the state
   its request was evaluated against.

   A token request that redeems an authorization code opened by a
   presentation:

   *  MUST have a client_id parameter exactly equal to the
      establishment's sub, even if the client authenticates.

   *  MUST demonstrate possession of the establishment's proven key
      under the same sender-constraint mechanism or, for a confidential
      client whose statement was pulled at the authorization endpoint
      (Section 5.2), authenticate with the key that becomes the proven
      key.

   *  MUST NOT carry the software_statement parameter.

   A redemption carrying a statement is rejected with invalid_request.
   A wrong client identifier or failed key binding is rejected with
   invalid_grant.  The prohibition on carrying a statement covers
   redemption of a code bound to an establishment.  A registered client
   redeeming its own code can deliver a replacement statement under
   [REGISTRATION], which that specification calls a delivery and which
   is not a presentation.

   Expiry after presentation does not by itself invalidate an
   establishment already bound (Section 5.6.1).

5.6.1.  Refresh

   On refresh-token use, the authorization server proceeds as follows:

   1.  Proven key.  The authorization server:

       *  MUST verify possession of the establishment's proven key under
          the same sender-constraint mechanism.

       *  MUST, except for an establishment created under Section 5.4.1,
          verify that the document currently served at the
          establishment's sub still carries that key, in its jwks or at
          its jwks_uri, within the reuse bounds of Section 5.4.

       If a retrieval needed to check the key did not complete
       (Section 5.3), the server rejects the refresh with
       temporarily_unavailable.  If either check otherwise fails,
       including when the document does not carry the key, cannot be
       obtained, or exceeds the size bound of Section 3.1, it rejects
       the refresh with the invalid_grant error code.  It completes
       these checks before evaluating any replacement.

   2.  Need for a current statement.  The authorization server MAY, by
       local policy, additionally require a current statement, and
       SHOULD require one once the establishment's recorded statement
       has expired (Section 14.7).  The recorded statement satisfies
       that requirement while it is unexpired and no refusal record
       covers it, even after a later statement has raised the iat floor
       of Section 6.  A replacement is needed when a refusal record
       covers the recorded statement, or when the server requires a
       current statement, by local policy or under a required issuer
       (Section 4), and the recorded statement has expired.

       If the authorization server holds a refusal record for the
       establishment's recorded statement, it MUST reject a refresh
       without a presented or pulled replacement (step 3) satisfying
       this section, whatever its policy on requiring a current
       statement otherwise.  A server that uses a withdrawal mechanism
       for the recorded statement's issuer SHOULD consult it for that
       statement at each refresh.

       If a required issuer (Section 4) covers the establishment's sub
       in the establishment's tenant, the authorization server MUST
       reject a refresh with statement_required, or with
       temporarily_unavailable if a retrieval needed to obtain or check
       a replacement did not complete, unless the recorded statement or
       a replacement satisfying this section is a current statement from
       that issuer.  A grant recorded under another issuer's statement
       cannot meet this, so its client opens a new grant by
       presentation.

       The authorization server applies these two rejections after
       obtaining and evaluating any replacement under steps 3 and 4.

   3.  Obtaining a replacement.  A client can offer a replacement on any
       refresh, in the software_statement parameter of the refresh
       request.  A statement with the recorded statement's iss and jti
       is not a replacement: if the client offers it again, the server
       rechecks it as the recorded statement under steps 1 and 2.  When
       a replacement is needed and the request carries none, a server
       that supports pulled statements (Section 5.2) pulls, however the
       establishment was created, and takes as the replacement the
       newest statement with the recorded statement's iss and sub among
       those that section considers.  If the newest is the recorded
       statement itself, nothing is replaced, and the refresh is
       evaluated against the recorded statement.  A reviewed grant never
       continues under the policy for clients the server has not
       reviewed.

   4.  Validating the replacement.  If the refresh has a replacement,
       the following requirements apply to it:

       *  It MUST validate under Section 3.2, including its audience if
          it carries one.

       *  The iss and sub claims MUST equal those of the recorded
          statement.

       *  The iat claim MUST be later than that of the recorded
          statement.

       *  The cimd_digest claim MUST name the document currently served
          at that sub, which the server confirms by retrieval or by
          revalidating octets it holds.

       *  The replacement MUST authorize the establishment's proven key
          (Section 5.4) or, for an establishment created under
          Section 5.4.1, name a document that still satisfies that
          section.

   5.  Access.  The refreshed access MUST fall within the metadata of
       the document an accepted replacement names or, without one, the
       establishment's reviewed metadata.

   6.  Update.  If a replacement is accepted, the refreshed grant's
       statement identity, iat, effective expiry, any claim by which a
       withdrawal mechanism locates the statement, reviewed metadata and
       the digest it matched, and trust decision become those of the
       replacement (Section 12.4) in a single atomic update, and
       concurrent replacements resolve to the most recently issued
       statement.  Without one, the grant's state is unchanged.

   A refresh whose replacement fails step 4, or that needs a replacement
   and obtains none, leaves the grant's state unchanged.  It is rejected
   with temporarily_unavailable if a retrieval needed to obtain or check
   the replacement, such as the pull of step 3, did not complete
   (Section 5.3) for a reason other than the size bound of Section 3.1,
   and otherwise with statement_required, including when a completed
   pull yields no replacement.

   Refresh never rotates the establishment's key.  A client that needs a
   new key performs a new presentation.

6.  Repeated Consumption of One Statement

   A statement attests client software, identified by sub, not its
   runtime instances.  This specification defines no instance
   identifier.  One unexpired statement is therefore consumable more
   than once: at each trusting authorization server in its audience, in
   more than one establishment at that server (Section 12.3), and, if
   the server registers clients ([REGISTRATION]) and its policy permits,
   in more than one registration there.

   A trusting authorization server MUST retain, per iss and sub claims
   and, on a multi-tenant server, per tenant, the greatest iat claim
   value among the statements it has accepted, as its iat floor.  A
   statement is accepted for the floor once the server admits a client
   on it, applies it as a replacement, or registers a client with it.
   The server MUST reject a statement whose iat claim is earlier than
   the retained iat, whether it arrives as a replacement, a new
   registration, or a new presentation.  A client holding a superseded,
   broader statement therefore cannot defer a narrowing by opening a
   fresh registration or establishment with it.  The server retains the
   iat floor at least as long as the maximum statement lifetime it
   honors for that issuer.

   A multi-tenant server also keeps any bound on establishments
   (Section 12.3) per tenant.

   The first presentation of a replacement that establishes the client
   supersedes its predecessor for new admissions by every instance of
   the software at that server (Section 13.3).  Grants the predecessor
   already opened continue under Section 5.6.1.

   Software whose instances authenticate as the client with keys of
   their own, which the reviewed document does not carry, can neither
   prove nor register those keys (Section 5.4, [REGISTRATION]) and
   depends on the attested-key extension of Section 11.

7.  Relationship to Other Work

   This section is non-normative.

7.1.  Client Attestation

   A software statement and a client attestation [ABCA] are both signed
   third-party assertions.  A statement attests client software and the
   metadata its issuer evaluated.  A client attestation attests a
   running instance and the key it holds, and is presented with a proof
   bound to the request.

   Neither assertion grants access nor substitutes for the other.
   Runtime presentation therefore always requires a sender constraint
   (Section 5.4).  Binding a presenter attestation defined elsewhere is
   an extension (Section 11).

7.2.  Identity Assertions

   A statement records that a named party reviewed software, not that a
   particular customer currently permits that software to act in its
   tenant.  A tenant-scoped decision (aud_tenant) authorizes no
   particular user or transaction.  When a customer's identity provider
   mediates a grant, as with a cross-domain identity assertion [IDJAG],
   it issues assertions per grant only for clients the customer permits.
   A statement serves when the issuer is not in the request path, or
   when a customer wants a portable record of what its review covered.

7.3.  OpenID Federation

   A trust mark [OPENID-FED] is also a signed third-party assertion
   about an entity, but it is resolved through a federation in which
   both parties enroll.  A statement needs no federation: a trusting
   authorization server configures its issuer directly (Section 4), and
   the statement binds the exact octets of the client's own document
   rather than metadata the federation resolves.

8.  Error Responses

   A rejection uses the error response and HTTP status codes specified
   for the endpoint where it occurs:

   *  At the token endpoint, Section 5.2 of [RFC6749] applies.

   *  At the pushed authorization request endpoint, Section 2.3 of
      [RFC9126] applies.

   *  At the authorization endpoint, Section 4.1.2.1 of [RFC6749]
      applies.

   At the token and pushed authorization request endpoints, an
   authorization server SHOULD respond with HTTP status code 503 to a
   request it rejects with the temporarily_unavailable error code.
   [REGISTRATION] defines rejections at a registration endpoint and how
   registration validity is reported.

8.1.  Requiring a Current Statement

   This specification defines the following error code:

   statement_required:  A current software statement is required and
      none was supplied or pulled, or the one supplied or pulled is
      expired, refused by a refusal record (Section 3.3), or superseded
      under the iat floor of Section 6.  The code also applies when a
      statement offered as a replacement on refresh (Section 5.6.1), or
      at the token or pushed authorization request endpoint under
      [REGISTRATION], does not satisfy the requirements for one.  The
      client recovers by obtaining a statement issued more recently.

   A refresh-token request rejected for lacking a current statement that
   this specification requires uses statement_required in place of
   invalid_grant.

8.2.  Presentation

   A presentation rejected at the token or pushed authorization request
   endpoint for a reason this specification defines uses the following
   error codes:

   invalid_client:  The statement or the client cannot be established,
      in any of the following cases:

      *  The statement is malformed, or fails signature or claim
         validation (Section 3.2) for a reason other than expiry or a
         refusal record.

      *  The statement is valid but not acceptable here: its issuer is
         not configured, its aud excludes this server, its sub is
         outside the client identifier namespaces the issuer can attest,
         its aud_tenant is not this request's tenant or is absent when
         required, its issuer is confined to another tenant, or its
         statement_uses excludes this use.

      *  The request's client_id differs from the statement's sub
         (Section 5.1).

      *  The reviewed document cannot be obtained for a reason other
         than a retrieval that did not complete (Section 5.3), fails
         validation as [CIMD] requires, contains duplicate member names
         (Section 3.2), or exceeds the server's size bound
         (Section 3.1).

      *  The document's digest does not match cimd_digest and the server
         does not proceed without the statement (Section 5.5).

      *  The request fails the sender constraint, including a
         presentation under a document that omits
         token_endpoint_auth_method and one opening a new grant at the
         token endpoint under a document declaring
         token_endpoint_auth_method of none (Section 5.4,
         Section 5.4.1).

      *  The server's bound on establishments is reached (Section 12.3).

   statement_required:  The statement is expired, refused by a refusal
      record, or superseded, or a required statement is absent,
      including one from an issuer required for the tenant (Section 4).

   unauthorized_client:  The request exceeds the reviewed document's
      grant types or response types (Section 5.5), the document carries
      metadata this server's policy refuses, or the client is review-
      only and this server requires reviewed software (Section 5.4.1).

   invalid_scope:  The request exceeds the reviewed document's scope
      (Section 5.5), or the document carries a scope this server's
      policy refuses.

   temporarily_unavailable:  A retrieval the presentation needs did not
      complete, for a reason other than the document size bound
      (Section 3.1).

   invalid_request:  The presentation omits client_id, or the request
      carries software_statement in a role Section 5.1 does not permit.

   A request rejected for another reason, such as an assertion grant
   whose assertion is invalid (Section 3.1 of [RFC7523]), uses the error
   code its grant or endpoint assigns.

8.3.  Code Redemption and Refresh

   A token request that redeems an authorization code opened by a
   presentation is rejected with invalid_request or invalid_grant as
   Section 5.6 provides, and with invalid_client if the server's bound
   on establishments is reached (Section 12.3).

   Under an establishment, a refresh-token request rejected for a reason
   this specification defines uses the following error codes:

   statement_required:  A current statement or a replacement that
      Section 5.6.1 requires is not supplied or a completed pull yields
      none, or the one supplied or pulled fails the requirements of
      Section 5.6.1 or the iat floor of Section 6.

   invalid_grant:  The checks of step 1 of Section 5.6.1 fail for a
      reason other than a retrieval that did not complete.

   temporarily_unavailable:  A retrieval needed to obtain or check the
      replacement, or to check the proven key, did not complete, for a
      reason other than the document size bound (Section 3.1).

   unauthorized_client or invalid_scope:  The refreshed access would
      exceed the reviewed document's metadata or this server's policy,
      as for a presentation.

   invalid_request:  The request carries a replacement but omits
      client_id (Section 5.1), or carries software_statement in a role
      Section 5.1 does not permit.

   None of these rejections indicates refresh-token replay ([RFC9700]).
   A refresh-token request rejected for another reason, such as an
   expired or revoked refresh token, uses the error codes of Section 5.2
   of [RFC6749].  This specification does not change how an
   authorization server detects refresh-token replay.

8.4.  Authorization Endpoint

   At the authorization endpoint, if reviewed software is required
   (Section 5.4.1, Section 5.2), a review-only client is rejected with
   unauthorized_client, and a client whose pull of statements, or
   retrieval of a statement key set needed to verify one (Section 4),
   did not complete (Section 5.3) is rejected with
   temporarily_unavailable.

   Apart from those two cases, at the authorization endpoint, if the
   authorization server requires a statement for a client it has not
   admitted on one, it MUST return the statement_required error code in
   the authorization error response (Section 4.1.2.1 of [RFC6749]).

   The authorization server redirects with the error only after
   resolving the client's Client ID Metadata Document and validating the
   request's redirect_uri against it.  If the authorization server
   cannot resolve the document, it MUST NOT redirect, and it reports the
   error to the resource owner instead.

   An authorization request carrying the software_statement parameter
   (Section 5.1.1) is rejected with invalid_request in place of any
   other code of this section.  The authorization server redirects with
   that error only after validating the request's redirect_uri: for a
   client identified by its Client ID Metadata Document URL, against
   that document as the preceding paragraph requires, and for a
   registered client, against its registered redirection URIs
   (Section 4.1.2.1 of [RFC6749]).

8.5.  Proof Mechanism Errors

   If the proof mechanism defines an error of its own for a proof it
   does not accept, such as invalid_dpop_proof for a DPoP proof that
   fails the checks of Section 4.3 of [RFC9449] or use_dpop_nonce for a
   nonce challenge (Section 8 of [RFC9449]), the request is rejected
   with that error in place of the code this specification assigns to a
   failed sender constraint.

   A proof that its mechanism accepts but that proves a key other than
   the one this specification requires, such as a key the reviewed
   document does not carry or one other than the establishment's proven
   key, is not an invalid proof: it fails the sender constraint, and is
   rejected with the code this specification assigns to that failure.

8.6.  Error Descriptions

   The authorization server can return non-sensitive diagnostics in the
   error_description parameter to a client it has authenticated, but
   MUST NOT reveal details of its issuer trust configuration
   (Section 4), such as the client identifier namespaces an issuer can
   attest, to an unauthenticated requester.

   If a statement is refused by a refusal record rather than merely
   expired, and the client is authenticated, the authorization server
   ought to indicate that a statement issued more recently is required.

9.  Examples

   The examples in this section are non-normative.

9.1.  Presenting at the Token Endpoint

   The following is an example of a client presenting a statement at the
   token endpoint of a server holding no record for the client (line
   breaks for display purposes only).  The reviewed document, which is
   not shown, names a jwks_uri, the private_key_jwt authentication
   method, the client_credentials grant type, and a scope that includes
   tools.read, so the client authenticates with a key that document
   carries.  The client_id is the statement's sub.

   POST /token HTTP/1.1
   Host: as.example
   Content-Type: application/x-www-form-urlencoded

   grant_type=client_credentials
   &scope=tools.read
   &client_id=https%3A%2F%2Fclient.example%2Fapp
   &client_assertion_type=urn%3Aietf%3Aparams%3Aoauth%3A
   client-assertion-type%3Ajwt-bearer
   &client_assertion=eyJhbGciOiJFUzI1NiIsImtpZCI6IjIwMjYtMDgifQ...
   &software_statement=eyJ0eXAiOiJzb2Z0d2FyZS1zdGF0ZW1l...

   The authorization server validates the statement, retrieves the
   document its digest names, verifies the client assertion against a
   key from that document's jwks_uri, and checks that the requested
   scope falls within the document's scope.  It keeps no registration.

9.2.  Publishing a Statement for Servers to Pull

   The following is an example of a Client ID Metadata Document that
   names where its statements are published:

   {
     "client_id": "https://client.example/app",
     "redirect_uris": ["https://client.example/cb"],
     "token_endpoint_auth_method": "private_key_jwt",
     "jwks_uri": "https://client.example/jwks.json",
     "software_statements_uri":
       "https://client.example/statements.json"
   }

   A request to that URL returns the statements, here one:

   {
     "software_statements": [
       "eyJ0eXAiOiJzb2Z0d2FyZS1zdGF0ZW1lbnQrand0Iiwi..."
     ]
   }

   An authorization server receiving an ordinary authorization request
   with this client_id resolves the document, retrieves the statements,
   and keeps the one from a trusted issuer whose cimd_digest matches the
   document it retrieved.  It completes the binding when the client
   authenticates with private_key_jwt at code redemption (Section 5.2).

9.3.  Statement Header and Payload

   The following is an example of the JOSE header and payload of a
   statement over the document in the previous example, served exactly
   as shown there and ending in a single newline:

   {
     "typ": "software-statement+jwt",
     "alg": "ES256",
     "kid": "2026-10"
   }

   {
     "iss": "https://issuer.example",
     "sub": "https://client.example/app",
     "aud": ["https://as.example"],
     "statement_uses": ["presentation"],
     "iat": 1790812800,
     "exp": 1793404800,
     "jti": "c2a907b34d28",
     "cimd_digest": "vBIuTBeHfYmEC8CPwbfa2a9XciuKfGTEGf-qGij4N_Q"
   }

   The statement names one audience and permits only runtime
   presentation, as omitting statement_uses would.  It carries no client
   metadata: the document its cimd_digest names supplies it.

10.  Authorization Server Metadata

   This specification defines the following authorization server
   metadata [RFC8414] values:

   software_statement_jwks_uri:  REQUIRED for an authorization server
      that issues statements under this specification.  URL of a JWK Set
      containing only the keys with which it signs them.  The URL MUST
      use the https scheme, and a trusting authorization server MUST
      validate the server's certificate when retrieving it.

      The keys in this set MUST NOT appear in the JWK Set at the
      server's jwks_uri metadata value, and the server MUST NOT sign
      anything other than statements under this specification with them.
      As a result, a key that signs another artifact, such as a Status
      List Token or a software statement of another profile, cannot
      verify a statement (Section 14.3).

   software_statement_signing_alg_values_supported:  REQUIRED for an
      authorization server that issues statements under this
      specification.  A JSON array containing the asymmetric JWS alg
      values that the authorization server can use to sign them.  The
      array MUST NOT contain none or a symmetric algorithm.  An
      authorization server that only accepts software statements does
      not publish it.

   software_statement_pull_supported:  OPTIONAL.  Boolean value
      indicating whether the authorization server retrieves statements
      from a client's software_statements_uri member when admitting a
      client that presented none (Section 5.2).  If omitted, the default
      value is false.

11.  Extension Points

   The following extensions are left to separate specifications:

   *  Attested keys: a client attestation [ABCA], including one from an
      attester the reviewed document names, vouching for a key that
      document does not carry (Section 6).

   *  Statement conveyance within a client attestation, rather than as a
      request parameter.

   *  Runtime presentation on grants other than those Section 5.1 names,
      such as token exchange.

   *  Partial review, by which an issuer vouches for particular members
      rather than a whole document (Section 3).

   *  Withdrawal mechanisms (Section 3.3), such as Token Status List
      [STATUSLIST].

12.  Implementation Considerations

   This section gives guidance to implementers.  It adds no requirement.

12.1.  Caching and Reuse of Retrieved Content

   A server can revalidate octets it holds with a conditional request
   rather than retrieving them again (Section 3.1).

   Successful retrievals can be cached within the document's caching
   directives.  A failure is followed by back-off rather than caching,
   which [CIMD] forbids.  A response from a software_statements_uri
   ought to be cached no longer than the document is, and can be
   revalidated with a conditional request, as the document can
   (Section 5.2).

12.2.  Retrieval and Processing Bounds

   An authorization server can bound the retrieval and processing work
   of Section 14.6 as follows:

   *  Rate-limit presentations per statement identity, per subject, and
      per source, and pulls (Section 5.2) per client identifier and per
      source, before spending retrieval or storage on a new
      presentation.

   *  Refuse a presentation that would create a new establishment,
      before spending retrieval or storage on it, once a bound on
      establishments (Section 12.3) is reached.

   *  Bound JWT size and parsing work, concurrent retrievals, response
      size, and response time.

   *  Bound the size of a software_statements_uri response and the
      number of statements examined separately from the document's.
      Several issuers' statements outgrow a document-sized bound, and a
      host can pad the array.

   *  Discard pulled statements from unconfigured issuers before
      verifying any signature.

12.3.  Bounding Establishments

   A trusting authorization server can bound the number of
   establishments, and any registrations ([REGISTRATION]), derived from
   one issuer's statements about one piece of software, identified by
   iss and sub claims.  How it counts toward a bound is local policy.
   Two choices keep a bound effective:

   *  State that anyone holding a copy of a statement can create does
      not count: a pushed authorization request and its unredeemed code,
      which anyone holding a copy of a public client's statement can
      approve with their own account, or a registration under which no
      access token has been issued.  Otherwise a holder of a copy could
      exhaust the bound for the software's other instances.

   *  A count persists across replacements: an establishment created for
      a refreshed grant does not add to it.

   For software admitted under Section 5.4.1, a server can also bound
   establishments per resource owner, so that one user cannot exhaust a
   bound the software's other users share.

   A request refused at a bound is rejected with invalid_client
   (Section 8.2).  The authorization server ought to state that reason
   in error_description, and the client can retry once earlier
   establishments are released.

12.4.  Grant State

   An authorization server can reuse an establishment across
   presentations that resolve to the same sub, statement, tenant,
   sender-constraint mechanism, and proven key, and can discard it once
   no request_uri, authorization code, refresh token, or other
   continuation state references it (Section 5.6).  A server does not
   share an establishment whose proven key is set at code redemption
   (Section 5.2) until that key is set.

   A server that shares an establishment among grants applies a
   replacement accepted on refresh by giving the refreshed grant its own
   establishment (Section 5.6.1).

12.5.  User Interface, Audit, and Logging

   An authorization server ought not to present the review in a review-
   only presentation to the user as an assurance about the presenter
   (Section 5.4.1).  It can record the statement's issuer for audit and
   inventory.

   Authorization servers ought to avoid logging software statements,
   which are sensitive in transit and at rest.  A statement names
   reviewed software and, if it carries an audience, that software's
   intended relationships.

13.  Deployment Considerations

   This section gives guidance to operators and issuers.  It adds no
   requirement.

13.1.  Configuring Issuer Trust

   Trust configuration ought to constrain each issuer to the client
   identifier namespaces it is expected to attest (Section 3.2), for
   example URLs under the domains of the software publishers it serves.
   Without such a scope, a compromised or over-broad issuer can mint
   acceptable statements about any client software.

   When a trusting authorization server configures an issuer whose
   decisions are confined to one of its tenants, as a customer's own
   issuer is, it ought to record with that configuration the client
   identifier namespaces for which the issuer's decision is required in
   that tenant (Section 4).

13.2.  Audience and Tenant Claims

   An issuer ought to name an audience and, for a statement whose
   statement_uses claim permits registration, to omit the aud claim only
   if it accepts that any server trusting the issuer can register the
   software on the strength of a copy ([REGISTRATION]).

   An issuer ought to omit the aud_tenant claim from a statement whose
   review applies wherever its aud reaches, such as a marketplace
   listing.  The claim is also unnecessary if the authorization server
   has one tenant, or if the server's trust configuration confines the
   issuer to a tenant, as it can for an issuer that does not know the
   tenant's identifier.

13.3.  Statement Lifetime and Renewal

   Short lifetimes tighten an issuer's control and increase renewal
   traffic.  At a server that registers clients under [REGISTRATION],
   the lifetime also sets the registration's renewal cadence.  A fleet
   of statements issued together expires together, so issuers ought to
   stagger expiries or renew ahead of the boundary.

   A changed document is always served before a statement over it
   exists.  Until the new statement exists, a presentation under the
   earlier one fails the digest comparison (Section 5.5), and at
   registration a mismatch is fatal ([REGISTRATION]).  The statement's
   lifetime bounds how stale an unobserved review can become.

   Instances need the most recently issued statement from a shared
   source rather than a copy fixed at build or install time (Section 6).

13.4.  Withdrawal Practice

   What a server does when it cannot consult a withdrawal mechanism it
   relies on is local policy (Section 3.3).  Refusing makes issuer
   availability a precondition for every request the statement governs.
   Proceeding leaves a withdrawn statement acceptable until it expires.

   A refusal that the server's operator entered, rather than one derived
   from a withdrawal mechanism, persists on the operator's own terms.

   Withdrawal does not replace lifetime: an issuer chooses exp assuming
   no trusting authorization server uses a withdrawal mechanism.

14.  Security Considerations

   The security considerations of [CIMD] and Section 5 of [RFC7591]
   apply.

14.1.  Assurance Provided by a Statement

   A statement binds an issuer's review to the octets of a Client ID
   Metadata Document, which describes an OAuth client configuration.  It
   does not bind the software's code, dependencies, or behavior.
   Software can change while its document stays the same, and the
   statement remains acceptable until it expires or is withdrawn
   (Section 3.3).  Assurance about the software itself rests on the
   issuer's review process.  Any change to the document's octets,
   including one that changes no metadata value, makes statements over
   the earlier octets fail the digest comparison (Section 5.5).  The
   digest covers a URL the document carries, such as logo_uri, but not
   the content served at it, which can change after review.

14.2.  Statement Theft and Replay

   A copied statement admits nothing without the sender constraint
   (Section 5.4).  Except under Section 5.4.1 (Section 14.4), admitting
   only keys the reviewed document carries also prevents a downgrade to
   a key the issuer did not review.  An extension admitting attested
   keys (Section 11) has to address downgrade itself.

   Attesting a jwks_uri attests the location, not its contents: a
   compromised key host can add keys that satisfy the proof without a
   digest change.  If that matters, an issuer attests jwks inline and
   accepts that rotation changes the digest.  A server reusing a cached
   key set (Section 5.4) also accepts that a just-removed key can
   briefly continue to verify.

14.3.  Servers That Do Not Implement This Specification

   A statement carries no client metadata, so an [RFC7591] server that
   verified one without implementing this specification would take every
   metadata value from the registration request, attaching the issuer's
   approval to an attacker's redirection URIs and keys.  Keeping
   statement signing keys in a dedicated statement key set, out of any
   jwks_uri, and away from statements of other profiles (Section 4,
   Section 10) means such a server finds no key that verifies a
   statement through the jwks_uri in an issuer's [RFC8414] metadata.  It
   is exposed only if its operator configures the statement key set in
   it.  For an issuer that is not an authorization server, that
   configuration is the only route to its keys, so the protection rests
   on operators recording the statement key set URL only in servers that
   implement this specification.

14.4.  Copied Statements and Public Clients

   A party holding a copied statement for a public client can open a
   pushed authorization request in the reviewed software's name.  It
   cannot receive an authorization code that another resource owner
   approves in a user agent the party does not control (Section 5.4.1),
   so other users are exposed only to a consent prompt carrying the
   reviewed software's name and branding.  Rate limits (Section 12.2)
   and the issuer's choice of audience and lifetime bound that exposure.

   A party that controls the user agent receives the code: an
   application embedding a user agent (Section 8.12 of [RFC8252]), or a
   holder authorizing with its own account.  It redeems the code with a
   PKCE verifier and key of its own choosing.  An admission under
   Section 5.4.1 therefore shows where codes are delivered, not which
   software holds the grant, and a tenant's required issuer (Section 4)
   cannot keep unreviewed software out for a user who chooses to run it.
   This is the client impersonation that Section 8.6 of [RFC8252]
   describes for public clients.  An attested-key extension (Section 11)
   would strengthen the binding by giving the instance a key a third
   party vouches for.

14.5.  Tenant Confusion at a Multi-Tenant Authorization Server

   A multi-tenant server that derives the tenant one way to check a
   decision and another way to scope a token lets a client reach one
   tenant's resources on another tenant's decision.  Section 3.2
   requires one tenant for both, selected by no value the client
   chooses.

   This specification defines no tenant parameter, and a Client ID
   Metadata Document URL is the same client_id in every tenant, so
   neither a client nor an issuer can verify that a server honored the
   tenant rule of Section 3.2.

   The aud_tenant claim names a tenant at the trusting authorization
   server, not which of the client's own customers is asking.  Software
   that acts for many customers under one client identifier and key
   presents the same statement and key for each, so a statement naming a
   tenant admits the software there on behalf of every customer it
   serves, and any of those customers can direct the software at another
   customer's tenant.  A statement attests software and cannot prevent
   this.  A deployment that needs a customer-to-tenant binding records
   it at the trusting authorization server.

14.6.  External Retrieval and Resource Exhaustion

   Runtime presentation can cause the authorization server to retrieve
   the Client ID Metadata Document, a jwks_uri it names, or the
   statements its software_statements_uri names (Section 5.3).

   These retrievals happen before any client is registered or any user
   has interacted, so an unauthenticated requester can cause them with
   one acceptable statement or, at a server that pulls statements, with
   none.  The bounds of Section 12.2 limit this work but do not prevent
   it.

14.7.  Expiry, Withdrawal, and Open Grants

   Expiry and withdrawal (Section 3.3) govern new admissions.  Neither
   revokes an issued access token.  A grant opened by a statement lasts
   for the life of its refresh tokens, whatever the statement's
   lifetime, unless the server requires a current statement on refresh,
   holds a refusal record, or finds the proven key gone from the
   client's document (Section 5.6.1).  Removing an issuer from trust
   configuration, or narrowing what it can attest, does not by itself
   end a grant or a registration ([REGISTRATION]) already admitted on
   one of its statements.  A server ends them by its own means, such as
   entering refusal records, revoking refresh tokens, or deleting
   registrations.

14.8.  Observable State

   A statement_required refusal at the authorization endpoint
   (Section 8.4) travels through the user agent, so anyone who can see
   the redirection learns that this client has no established standing
   at this server.  The disclosure is accepted because a client that
   cannot learn why it was refused cannot act.  The disclosure carries
   no detail of the server's issuer trust configuration, which
   Section 8.6 keeps from unauthenticated requesters.

15.  Privacy Considerations

   The privacy considerations of [CIMD] and Section 6 of [RFC7591]
   apply.

   A presentation or delivery reveals to the authorization server the
   client's issuer relationship and, if the statement carries an aud
   claim, the other authorization servers the client intends to use.
   Omitting that claim discloses nothing beyond the review.  Pushed
   authorization requests (Section 5.1.1) keep statements out of browser
   history, referrers, and front-channel logs.

   A central issuer also learns from renewals which of its statements
   are in active use, so issuance and renewal logs deserve the same care
   as the statements (Section 12.5).

   Retrieving the document tells its host that the server is resolving
   the client.  Pulling statements (Section 5.2) tells the host of
   software_statements_uri the same.  That host is an additional party
   only if the URL is on another origin.  Published statements are
   readable by anyone, so their aud and aud_tenant claims disclose which
   servers and tenants a review names.  A statement whose audience is
   sensitive is presented rather than published.
