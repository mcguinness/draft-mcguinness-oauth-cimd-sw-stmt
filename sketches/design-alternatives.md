# Design Alternatives for CIMD Software Statements

These simpler designs, none of which changes what a statement attests, were recorded for working-group discussion and are not part of any draft.

1. Issuer-hosted statements. The authorization server could obtain statements from the issuer, per client or as a signed list it synchronizes, instead of from the client. That would remove the `software_statement` parameter and `software_statements_uri`, and could replace the `iat` floor and refusal records derived from a withdrawal mechanism with rules for authoritative current responses, cache freshness, and failure handling, so that a stale response cannot restore a decision the server has seen replaced or withdrawn. It would require issuers to serve statements with high availability, would tell an issuer which servers resolve which clients unless lists are synchronized, and departs from the client-carried statement of RFC 7591.

2. Admission on every token request. The server could re-check a current statement and the served document on every token request instead of recording an establishment. That would remove the establishment's recorded statement and reviewed metadata, refresh replacement, and the pinned proven key, though state carried from a pushed authorization request, or a statement pulled at the authorization endpoint, to code redemption would remain. Every refresh would then need a current statement and the served document, within the reuse bounds of the statement draft's Retrieval section, and a grant would end when renewal lapses.

3. The public client's installation key. The server could rely on PKCE and the reviewed redirection URIs, which already bind a public client's presentation (the statement draft's Public Clients section), and leave refresh-token protection to RFC 9700. That would remove the key a public client binds at the pushed authorization request or authorization endpoint and proves at code redemption and on refresh. It would give up identifying the installation a grant belongs to.

4. Scope. Requiring a pushed authorization request for every reviewed redirect flow would remove the pull at the authorization endpoint, where a confidential client's key is set at code redemption (the statement draft's Pulled Statements section), at the cost of that path for clients that publish statements and make ordinary authorization requests. Admitting only confidential clients in the statement draft, with public clients in a separate profile, would remove a second binding model, at the cost of public clients with `https` redirection URIs.
