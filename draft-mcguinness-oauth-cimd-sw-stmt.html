Client ID Metadata Document Software Statement

Abstract

A Client ID Metadata Document carries a client's own claims, which can change at any time. This specification defines a software statement in which a trusted party records its review of the exact bytes of such a document, and how an authorization server enforces that review when it admits the client at request time, without a registration. The client presents the statement in a token or pushed authorization request, or publishes it where the reviewed document points. Possession of the statement alone does not complete a grant: the presenter is also bound to the reviewed document. Because the document remains the metadata, one review is portable across the authorization servers that trust its issuer. A companion specification covers RFC 7591 registration.¶

1. Introduction

A Client ID Metadata Document [CIMD] identifies a client by a URL and supplies its metadata from a document the client controls. That metadata is the client's own claim and can change at any time. An organization that reviews client software has no interoperable way to record its review of a particular version of the document, or to have an authorization server it has never dealt with enforce that review.¶

This specification profiles the software statement (Section 2.3 of [RFC7591]) for that purpose. A statement names the client by its document URL and binds the review to the document's exact octets by a digest (Section 3.1). A statement carried inside the document, as Section 4.3 of [CIMD] permits, cannot bind the review to the octets of the document that carries it (Section 3).¶

An authorization server that trusts the statement's issuer (Section 4) admits the client at request time on the reviewed document, and no other, without creating a registration (Section 5). The document remains the metadata and the statement records the decision, so one review is portable across every authorization server in the statement's audience.¶

This specification serves deployments in which a party other than the client decides which software can connect, such as a marketplace or registry that vouches for software to authorization servers it does not operate, or an enterprise that approves software for its users at a service run by someone else. It also serves server-hosted software, such as an agent, that obtains tokens with the client_credentials grant. An admitted client is treated as reviewed, rather than under the authorization server's policy for Client ID Metadata Document clients it has not reviewed. Admission grants no access to resources: the authorization server's own policy, and the resource owner's authorization where a grant involves one, still govern what it issues.¶

A native application whose redirection URIs another application on the device could claim, such as a loopback or private-use URI, gains only a record of the review: its presentations are review-only (Section 5.4.1) until an extension binds an installation key that a third party vouches for (Section 11).¶

A statement vouches for metadata, not for its presenter. It records approval of a client configuration, not of the software's code or behavior (Section 14.1). Possession of a statement alone admits nothing: the presenter is bound to the reviewed document (Section 5.4).¶

This specification does not define how a client obtains a statement. [REGISTRATION] defines consumption of the same statement in an [RFC7591] registration request. It builds on this specification, which does not depend on it. Section 7 relates this specification to other work.¶

1.1. Protocol Overview

The following non-normative sequence summarizes runtime admission:¶

  1. Using its Client ID Metadata Document URL as client_id, the client presents its statement in a token request or, for a redirect flow, a pushed authorization request, or publishes it at the software_statements_uri its document names (Section 5.1, Section 5.2).¶

  2. The authorization server validates the statement (Section 3.2), resolves the reviewed document (Section 5.5), and verifies the sender constraint against it (Section 5.4).¶

  3. The request proceeds under that document's metadata, without a registration.¶

  4. The state on which the rest of the grant depends persists as an establishment (Section 5.6).¶

2. Conventions and Definitions

The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED", "MAY", and "OPTIONAL" in this document are to be interpreted as described in BCP 14 [RFC2119] [RFC8174] when, and only when, they appear in all capitals, as shown here.¶

This specification uses terminology from [RFC6749] (OAuth), [RFC7591] (client metadata and software statements), and [CIMD] (Client ID Metadata Documents).¶

This specification defines the following terms.¶

Issuer:

The authorization server that signs a software statement.¶

Trusting Authorization Server:

An authorization server that consumes a software statement, at runtime under this specification or at registration under [REGISTRATION].¶

Runtime Presentation:

The consumption of a validated software statement presented in a token request or pushed authorization request, or pulled from where the client's document points (Section 5.2), without creating a client registration.¶

Establishment:

The durable state a successful runtime presentation creates for the grant it opens, or that a replacement accepted on refresh gives that grant, enumerated in Section 5.6.¶

Proven Key:

The key for which the presenter demonstrates possession during runtime presentation (Section 5.4).¶

Effective Expiry:

The earlier of a statement's exp and its iat plus the maximum statement lifetime the trusting authorization server honors for its issuer (Section 4). A statement is expired once its effective expiry has passed.¶

Refusal Record:

State an authorization server holds when it has learned that a statement ceased to be acceptable before its expiry, whether from a withdrawal mechanism it uses for the issuer (Section 3.3) or from its own operator.¶

Current Statement:

A statement whose effective expiry has not passed and that matches no refusal record. For a new admission or a replacement (Section 5.6.1, [REGISTRATION]), a statement superseded under the iat floor (Section 6) is also not current. On refresh, an establishment's recorded statement remains current after a later statement raises the iat floor (Section 5.6.1).¶

Review-Only:

Describes a presentation, or a pulled statement, that the authorization server evaluates but that admits nothing (Section 5.4.1).¶

iat Floor:

For a trusting authorization server, the iat claim value of the most recent statement it has accepted for a given iss and sub, kept per tenant on a multi-tenant server. For the floor, a statement is accepted once the server admits a client on it, applies it as a replacement, or registers a client with it. The server rejects a statement whose iat claim is earlier (Section 6).¶

3. The Software Statement

The software statement is a compact JWT [RFC7519] protected by JWS [RFC7515]. Although [RFC7591] permits a MAC, a statement issued under this specification MUST use an asymmetric digital signature, and the none algorithm and symmetric algorithms MUST NOT be used. Issuers and trusting authorization servers follow [RFC8725].¶

The JOSE header MUST include the kid header parameter, identifying the signing key in the issuer's statement key set (Section 10), and the typ header parameter with the value software-statement+jwt (Section 3.11 of [RFC8725]), which is the media type of Section 16.2 without its application/ prefix. Extensions can add claims. An incompatible revision would use a new typ value.¶

A statement asserts that its issuer evaluated the Client ID Metadata Document whose content the digest identifies, and vouches for that document to any party that accepts the issuer. The JWT payload contains the following claims.¶

iss:

REQUIRED. The issuer's issuer identifier, as defined by [RFC8414].¶

sub:

REQUIRED. The exact client identifier URL of the Client ID Metadata Document the issuer reviewed, not a client_id assigned through [RFC7591] registration.¶

aud:

OPTIONAL. One or more authorization server issuer identifiers ([RFC8414]) restricting which authorization servers can accept the statement. If the claim is absent, any authorization server that trusts the issuer for the subject can accept it (Section 4), and any holder of a copy can use it wherever statement_uses permits registration, which requires no key.¶

aud_tenant:

OPTIONAL. A tenant identifier at a trusting authorization server, as [IDJAG] defines the claim, naming the tenant in which the statement's decision applies. A statement whose decision is confined to one of a server's tenants MUST carry an aud claim naming exactly one authorization server and, unless that server confines the issuer to the tenant through its own trust configuration (Section 4), an aud_tenant claim naming the tenant. A tenant identifier is meaningful only at one authorization server.¶

The absence of aud_tenant does not mean that the statement applies in every tenant (Section 13.2).¶

statement_uses:

OPTIONAL. A JSON array identifying the permitted uses of the statement: registration ([REGISTRATION]) and presentation (Section 5). If the claim is absent, only presentation is permitted. A delivery renewing a registration ([REGISTRATION]) is a use at registration. A refresh replacement (Section 5.6.1) and a pulled statement (Section 5.2) are presentation.¶

iat:

REQUIRED. A NumericDate value, which MUST be an integer, giving the time the statement was issued. An issuer MUST NOT issue two statements for given iss and sub claims with the same iat claim, and MUST ensure that the iat claim values of its statements for a given iss and sub increase strictly (Section 5.6.1, Section 6, Section 12.5).¶

exp:

REQUIRED. A NumericDate value giving the expiration time.¶

jti:

REQUIRED. A unique identifier for the statement within the issuer's namespace.¶

cimd_digest:

REQUIRED. The metadata digest (Section 3.1) of the Client ID Metadata Document the issuer evaluated, binding the statement to that document's exact content.¶

status:

OPTIONAL. The status claim as [STATUSLIST] defines it, by which a statement locates itself in a Status List Token. Only a withdrawal mechanism that uses the claim processes it. This specification does not (Section 3.3).¶

A statement issued under this specification MUST NOT contain a claim named in the IANA "OAuth Dynamic Client Registration Metadata" registry, and a trusting authorization server MUST NOT take client metadata from a statement's claims: the reviewed metadata is the document the digest names.¶

[CIMD] permits a Client ID Metadata Document to carry a software_statement member. A trusting authorization server MUST NOT consume a statement of this profile from that member, and MUST NOT treat that member as satisfying any requirement of this specification. A statement cannot describe the document that carries it: its digest would have to cover its own bytes. A statement found in that member names an earlier version of the document. Statements of other kinds in the member are out of scope for this specification.¶

An authorization server implementing this specification MUST reject a statement of this profile in an [RFC7591] registration request with the unapproved_software_statement error code (Section 3.2.2 of [RFC7591]), unless it consumes the statement as [REGISTRATION] specifies. The server's configured statement key set (Section 4) verifies the statement, so a generic registration path would otherwise attach the issuer's review to metadata the request supplies (Section 14.3).¶

3.1. Metadata Digest

The metadata digest is the unpadded base64url-encoded SHA-256 hash [RFC6234] of the retrieved representation body after removal of content coding. The body is not transcoded, normalized, or re-serialized. Any byte order mark or trailing newline is included.¶

Retrieval for digest purposes follows [CIMD] and MUST NOT use content negotiation: the retrieving party sends the Accept header field that [CIMD] specifies for retrieving the document, or Accept: application/json if it specifies none, and no other variant selection. Equal digests show that the issuer and the trusting authorization server obtained the same octets, so any condition that makes retrieval depend on who is asking defeats the comparison.¶

A trusting authorization server MUST treat a response exceeding its configured size bound (Section 8.7 of [CIMD]) as a retrieval failure rather than digesting what it read. For a runtime presentation, retrying cannot succeed, so the request is rejected with invalid_client rather than temporarily_unavailable (Section 8), except on refresh-token use, for which Section 5.6.1 takes precedence.¶

A server MUST NOT compare a digest against any representation other than one it retrieved itself or stored under this section. A shared cache might hold a variant selected for another request. A 304 Not Modified response shows that stored octets, and their digest, are still current only if it carries a strong entity tag that matches the one stored with them under strong comparison (Section 8.8.3.2 of [RFC9110]). Otherwise, the server retrieves the body again.¶

3.2. Validating a Statement

Before accepting a statement, a trusting authorization server MUST ensure the following:¶

  • The typ JOSE header parameter has the value software-statement+jwt.¶

  • The signature verifies under a key trusted for the exact iss value, obtained as Section 4 requires.¶

  • Every required claim of Section 3 is present and of the correct type.¶

  • The statement is not expired, and its iat is not unreasonably far in the future according to the server's clock-skew policy.¶

  • If the statement carries aud, a value in it exactly matches one of the server's audience identifiers that its trust configuration permits the statement's issuer to name (Section 4).¶

  • If the statement carries aud_tenant, aud carries exactly one value and aud_tenant identifies the tenant this request belongs to, resolved before the statement is evaluated, by the server's own means or from a signed assertion it has validated, and never from a value the client chooses.¶

  • If the server requires a tenant-scoped decision for the request, the statement carries aud_tenant, or the server's trust configuration confines the statement's issuer to the request's tenant (Section 4).¶

  • If the statement carries statement_uses, the claim names the use being made of the statement, and a value the server does not recognize is treated as naming no use it serves. If the claim is absent, the use being made is presentation.¶

  • The sub claim is a client identifier URL conforming to [CIMD] and falls within the identifier scope for which this server accepts the issuer (Section 4).¶

  • Any claim the server does not recognize, and any client metadata claim, which Section 3 forbids an issuer to include, is ignored.¶

  • The JWT validation guidance in [RFC8725] has been applied.¶

A trusting authorization server that hosts more than one tenant MUST evaluate every tenant-specific check, such as the aud_tenant claim and a required issuer (Section 4), against the tenant that scopes what it issues on the statement, never selected by a value the client chooses.¶

A trusting authorization server MUST reject a statement for which it holds a refusal record (Section 3.3). A server that uses a withdrawal mechanism for the statement's issuer SHOULD consult it before accepting the statement for a new admission, within the caching and freshness rules that mechanism defines.¶

A trusting authorization server resolving the reviewed document MUST reject a document containing duplicate object member names. Parsers interpret such names differently despite an identical digest.¶

Rejections outside a registration endpoint use Section 8.¶

3.3. Withdrawal

An issuer can end a decision before the statement's exp by withdrawing the statement. Some status mechanisms call this revocation. This specification uses a distinct term because OAuth revocation ([RFC7009]) ends tokens, while a withdrawal revokes no issued token: a server holding a refusal record refuses new admissions and refresh under the statement (Section 5.6.1, Section 14.7).¶

How a trusting authorization server learns of a withdrawal is a withdrawal mechanism. This specification requires no withdrawal mechanism and defines none. Extensions define how a mechanism applies to these statements (Section 11).¶

A refusal derived from a withdrawal mechanism lasts until a later authoritative result from that mechanism supersedes it, or until an expiry the mechanism itself defines for the withdrawal. A server MUST NOT retain such a refusal once it is superseded or expired in that way. A failure to consult the mechanism, or cached evidence that has lapsed, neither supersedes nor expires a refusal.¶

A withdrawal constrains and never relaxes. A statement for which no withdrawal mechanism reports a withdrawal, or for which the server cannot consult the mechanism it uses (Section 13.4), is bounded by its effective expiry as it would be otherwise, and a server MUST NOT treat any withdrawal mechanism as grounds to accept a statement past its effective expiry.¶

An issuer that uses a withdrawal mechanism and issues a replacement narrower than the statement it replaces SHOULD withdraw the earlier statement. A replacement is narrower if the document it names no longer carries a key, redirection URI, or scope the earlier document carried, if its aud, aud_tenant, or statement_uses is narrower, or if its remaining lifetime is shorter.¶

What was removed might be why the replacement was issued. A trusting authorization server that has not yet seen the replacement, or at which it does not validate, would otherwise accept the earlier statement until it expires.¶

4. Issuer Trust Establishment

A trusting authorization server accepts statements only from configured issuers. Trust is established out of band, for example through a marketplace publisher program or shared enterprise operation. This specification defines no in-band issuer discovery or trust decision.¶

For each trusted issuer, a trusting authorization server records at least the following:¶

  • The exact iss identifier it will accept.¶

  • The source of that issuer's statement signing keys: the software_statement_jwks_uri in the issuer's authorization server metadata (Section 10), discovered from the configured iss as [RFC8414] describes, and never its jwks_uri.¶

  • The signing algorithms it will accept from the issuer.¶

  • The client identifier namespaces the issuer can attest through sub.¶

  • The audience identifiers the issuer can name.¶

  • Any tenant to which it confines the issuer's decisions.¶

  • The maximum statement lifetime it will honor, which sets each statement's effective expiry.¶

  • Its own policy on repeated consumption of one statement (Section 6).¶

These inputs, not the signature alone, define acceptance. A trusting authorization server MUST derive trust from this local configuration and MUST NOT derive it from an iss, jku, x5u, or other key-location value carried in a presented statement.¶

A server that records, for one of its tenants, client identifier namespaces for which a configured issuer's decision is required (Section 13.1) MUST NOT admit software in a covered namespace in that tenant without a current statement from the required issuer, whatever its policy for clients it has not reviewed. Without this rule, withholding the statement would restore access that the required issuer withdrew. The requirement is configured rather than inferred from the statements the server sees, so a holder cannot evade that issuer's withdrawal by presenting or publishing only a broader statement, such as a marketplace listing.¶

A required issuer configured for software whose documents are presented review-only (Section 5.4.1) excludes that software from the tenant.¶

4.1. Multi-Tenant Issuers

If an issuer reviews software for several customers whose decisions are each trusted independently, it MUST issue under a distinct iss value for each customer, so that each customer's decisions, keys, and iat floor (Section 6) stay separate. Under one iss, one customer's renewal would supersede another's review. A statement carries no claim naming the issuer's customer.¶

5. Runtime Presentation

A client presents its statement in a request (Section 5.1) or publishes it where its document points (Section 5.2).¶

5.1. Presentation Request

A client presents a software statement by including the following parameter in a token request or a pushed authorization request:¶

software_statement:

REQUIRED for presentation. The software statement (Section 3). It is consumed as a runtime presentation, a refresh replacement (Section 5.6.1), or, if [REGISTRATION] is implemented, a delivery under that specification. A request carrying the parameter in any other role is rejected with invalid_request.¶

The request's client_id is the client's Client ID Metadata Document URL. It MUST exactly equal the statement's sub claim. If the two differ, the authorization server MUST reject the presentation with the invalid_client error code. The effective client_id is the statement's sub, and the authorization server assigns none.¶

The request carries the proof that Section 5.4 requires. A successful presentation establishes the client for the request and for the grant state derived from it (Section 5.6).¶

At the token endpoint, a runtime presentation is valid on a request using any one of the following grants:¶

  • The client_credentials grant.¶

  • The JWT or SAML 2.0 assertion grant (Section 2.1 of [RFC7523] and Section 2.1 of [RFC7522]).¶

  • Another grant whose specification provides for runtime presentation under this specification.¶

Authorization-code redemption and refresh-token use continue an existing grant (Section 5.6, Section 5.6.1). A request that asks an authorization server to issue a software statement, rather than to consume one, MUST NOT carry the software_statement parameter.¶

An authorization server that does not implement this specification ignores the parameter (Sections 3.1 and 3.2 of [RFC6749]), so a client can present wherever its statement's audience allows.¶

5.1.1. Authorization Endpoint

Presentation in an authorization request MUST use a pushed authorization request [RFC9126]. A pulled statement needs no pushed authorization request (Section 5.2). The pushed authorization request endpoint processes the statement and its proof as Section 5.3 describes. The subsequent authorization request MUST use a client_id parameter exactly equal to the establishment's sub and MUST NOT include the software_statement parameter. A statement therefore never appears in a front-channel URL.¶

5.2. Pulled Statements

A client can publish its statements rather than present them. Its Client ID Metadata Document then carries the following client metadata member:¶

software_statements_uri:

OPTIONAL. URL, in a Client ID Metadata Document, at which the client publishes software statements about itself. The member has no meaning in a registration request. The URL MUST use the https scheme. A request to it returns a JSON object whose software_statements member is an array of statements (Section 3), each a string in JWS compact serialization. The metadata digest covers this member (Section 3.1), so changing where statements are found changes the document's digest, and statements over the earlier document no longer match.¶

An authorization server that supports pulled statements MAY retrieve this URL when it resolves the document of a client that presented no statement. In retrieving this URL, the server MUST send a GET request with Accept: application/json and MUST NOT automatically follow redirects. It MUST accept a new representation only from a 200 response with a JSON media type, and can instead reuse a stored representation that a 304 Not Modified response revalidates (Section 15.4.5 of [RFC9110]).¶

Both the document and this URL are retrieved before any statement exists to validate, so the ordering of Section 5.3 applies from the first statement verified onward.¶

The server considers only statements that meet all of the following conditions:¶

  • The sub claim equals the document's client identifier.¶

  • The statement validates under Section 3.2 and permits presentation (Section 3).¶

  • The cimd_digest claim equals the digest of the document the server resolved.¶

  • The iat floor of Section 6 does not supersede it.¶

The server ignores the rest.¶

If the server's trust configuration requires an issuer for this client (Section 4), it applies only that issuer's statement, and if none remains, the client is not reviewed. Otherwise, if more than one statement remains, the server keeps only the statement with the latest iat from each issuer and applies any one of those. A pulled statement the server does not apply does not advance the iat floor.¶

Having selected a statement, the server continues from step 4 of Section 5.3, with the pulled statement in place of a presented one and the document already resolved. The selection above satisfies the client_id rule of step 2.¶

The presenter of a pulled statement is bound as for a presented statement (Section 5.4), at the point the request allows, as follows:¶

  • At the token endpoint, the request's client authentication or DPoP proof binds the presenter.¶

  • At the pushed authorization request endpoint, a confidential client's authentication binds the presenter, and a public client whose request binds a key through a DPoP proof or dpop_jkt is subject to Section 5.4.1, including PKCE.¶

  • At the authorization endpoint, binding completes at code redemption, before any token is issued:¶

    • A confidential client authenticates at code redemption with a key the digested document carries, in its jwks or at its jwks_uri within the reuse bounds of Section 5.4, not one that only a later retrieval of the document carries, and that key becomes the establishment's proven key.¶

    • A public client's authorization request that binds a key through dpop_jkt is subject to Section 5.4.1, including PKCE, and redemption proves the bound key.¶

  • A public client opening a new grant at the token endpoint, or sending a pushed or ordinary authorization request that binds no key, has nothing to bind, so a statement pulled for it is review-only (Section 5.4.1), as is one pulled for a document whose redirection URIs that section does not accept.¶

  • Code redemption and refresh continue an establishment and keep the binding it already has (Section 5.6, Section 5.6.1), except that redemption sets the proven key of an establishment whose statement was pulled at the authorization endpoint for a confidential client.¶

If retrieval does not complete or no statement remains, the server applies its policy for Client ID Metadata Document clients it has not reviewed, subject to any required issuer (Section 4). If that policy or a required issuer (Section 4) requires reviewed software, the server rejects the request with temporarily_unavailable if retrieval did not complete and with statement_required if no statement remains. A retrieval failure is never a withdrawal.¶

When a refresh needs a replacement (Section 5.6.1) for an establishment created from a pulled statement, the server pulls again and applies the newest statement with the recorded statement's iss and sub as the replacement under that section. If the newest is the recorded statement itself, nothing is replaced, and the refresh is evaluated against the recorded statement as Section 5.6.1 describes. If the re-pull does not complete or yields no replacement, the refresh fails as Section 5.6.1 provides. A reviewed grant never continues under the policy for clients the server has not reviewed.¶

An authorization server advertises support through software_statement_pull_supported (Section 10).¶

5.3. Presentation Processing

On receiving a presentation, the authorization server proceeds as follows, rejecting as Section 8 defines at the first failure:¶

  1. Validate the statement (Section 3.2), completing every check that does not require a client-controlled network retrieval before performing any such retrieval.¶

  2. Verify the statement requirements of Section 3, the iat floor of Section 6, and the client_id rule of Section 5.1.¶

  3. Resolve the reviewed document (Section 5.5), which is the first step requiring a client-controlled retrieval.¶

  4. Verify the sender constraint against that document (Section 5.4), then evaluate the request against its metadata (Section 5.5).¶

  5. On success, create the establishment (Section 5.6).¶

Every retrieval this specification causes, of the Client ID Metadata Document, a jwks_uri it names, or the statements its software_statements_uri names, inherits the server-side request forgery protections of [CIMD]. A trusted signature does not make a URL safe: the authorization server MUST apply its URL, redirect, address-range, transport, and content-type policy independently to every referenced location.¶

A retrieval failure leaves the relevant metadata or proof unverified, so the authorization server MUST reject the request and MUST NOT fall back to a weaker proof. A failed pull of statements for a request that opens a new grant is the exception: it leaves the client unreviewed, as Section 5.2 describes.¶

5.4. Sender Constraint

A runtime presentation MUST be sender-constrained by a key the statement attests or, under Section 5.4.1, by the key the presenter binds there. The presenter proves possession of that key through the applicable client authentication method or a DPoP proof [RFC9449]. If a request carries both, the key its client authentication proves is the proven key. The proof MUST be bound to the current request and validated with the replay protections of that mechanism.¶

Except as Section 5.4.1 provides, the proven key MUST appear in the jwks or at the jwks_uri of the reviewed document (Section 5.5). If the reviewed document declares one or more client authentication methods ([CIMD]), the presenter MUST use one of them. The authorization server MUST reject a presentation without such a proof, or whose proven key the reviewed document does not carry.¶

This specification requires a reviewed document to declare its client authentication method, so that the issuer's review and the trusting authorization server's treatment of the client do not depend on a default. The authorization server MUST reject a presentation under a reviewed document that omits the token_endpoint_auth_method member. It treats a statement pulled for such a document as review-only (Section 5.4.1).¶

A document carrying a redirection URI another application could claim is presented review-only whatever its authentication method (Section 5.4.1), and the requirements above do not apply to that presentation. Two rejections still apply to such a document: a presentation under a document that omits token_endpoint_auth_method, as above, and a presentation that opens a new grant at the token endpoint from a client whose reviewed document carries no key material (Section 5.4.1).¶

A key at the document's jwks_uri is retrieved at presentation time. If that retrieval fails, the presentation is rejected with temporarily_unavailable. A server MAY reuse a retrieved key set only within ordinary HTTP caching bounds and a maximum reuse period of its own choosing, and MUST NOT let the client's cache directives alone determine how long a removed key continues to verify (Section 14.2).¶

5.4.1. Public Clients

Software distributed to end users cannot hold a key its reviewed document carries: a key shipped in every copy identifies the software, not the installation. Such a document declares token_endpoint_auth_method of none and carries no key material.¶

If the client's reviewed document declares token_endpoint_auth_method of none and none of its redirection URIs is one another application could claim (see below), a presentation at the pushed authorization request endpoint, or a statement pulled at that endpoint or at the authorization endpoint (Section 5.2), is bound instead by its reviewed redirection URIs. For such a presentation, the authorization server:¶

  • MUST require PKCE [RFC7636] with the S256 method.¶

  • MUST require the presenter to bind a key it holds, through the dpop_jkt parameter or, at the pushed authorization request endpoint, a DPoP proof (Section 10.1 of [RFC9449]), and records that key as the proven key of the establishment (Section 5.6).¶

  • MUST NOT require that key to appear in the reviewed document.¶

The reviewed redirection URIs, not the proven key, bind such a presentation (Section 14.4). The proven key identifies the installation the grant belongs to, and code redemption and refresh prove it (Section 5.6, Section 5.6.1).¶

A presentation is review-only if the reviewed document carries any redirection URI that another application on the same device could claim: a non-https URI, such as a private-use scheme or an http loopback redirection URI (Sections 7.1 and 7.3 of [RFC8252]), or an https URI whose host is a loopback address or localhost. One such URI makes every presentation and pulled statement for the document review-only, whatever authentication method the document declares. The application that claims such a URI receives the code, so neither the reviewed redirection URIs nor a key shipped in every copy of the software can bind the presenter.¶

A review-only presentation creates no establishment, admits nothing, and does not advance the iat floor of Section 6, since it changes nothing for the software's other instances. The authorization server proceeds as it would for the same Client ID Metadata Document client presenting no statement (Section 12.6).¶

The statement of a review-only presentation MUST NOT satisfy a policy requiring reviewed software. If the server's policy requires reviewed software, it rejects a review-only client with unauthorized_client.¶

An authorization server MUST reject, with the invalid_client error code, a presentation that opens a new grant at the token endpoint (Section 5.1) from a client whose reviewed document carries no key material. Such a presentation opens no redirect and has nothing to bind it. A statement pulled for such a client at the token endpoint is instead review-only (Section 5.2).¶

5.5. Reviewed Metadata

Having validated the statement, and before verifying the proof (Section 5.3), the authorization server MUST obtain the Client ID Metadata Document at the statement's sub, only by retrieval or from octets it has already digested for that identifier, and compare its digest with the cimd_digest claim. If octets it already holds do not match, it retrieves the document once more before treating the mismatch as a change, since a statement over an updated document would otherwise fail at a server still holding older bytes.¶

Octets the authorization server already holds serve for that comparison only within a maximum reuse period of its own choosing, as a key set does (Section 5.4). The authorization server MUST NOT let the client's cache directives alone determine how long held octets continue to match a statement. Without this rule, a key the document carries inline would continue to verify after the publisher removes it.¶

A match means the served document is the reviewed one, and its members are the client's metadata for the request. A mismatch means the document changed after review, and the authorization server MUST NOT treat the changed document as reviewed. It rejects the presentation with invalid_client or, by local policy, proceeds without the statement. If it proceeds, it applies its policy for Client ID Metadata Document clients it has not reviewed to the current document and creates no establishment for the statement.¶

The request is evaluated against the reviewed metadata as against any client's registered metadata ([RFC6749], [CIMD]): any requested grant type, response type, or scope MUST fall within it. A document that omits scope sets no ceiling on scope beyond the server's own policy.¶

5.6. Grant Lifecycle

A successful presentation creates an establishment comprising the following:¶

  • The validated sub.¶

  • The statement identity (its iss and jti), its iat and effective expiry, and any claim by which a withdrawal mechanism locates it, such as status.¶

  • The authorization server's own tenant the grant was opened for, if it hosts more than one.¶

  • The reviewed metadata and the digest it matched (Section 5.5).¶

  • The issuer trust decision.¶

  • The sender-constraint mechanism and proven key.¶

  • Whether the statement was presented or pulled (Section 5.2).¶

The establishment persists while the grant depends on it. The authorization server MUST bind the resulting request_uri, authorization code, refresh token, and other grant continuation state to the establishment, as applicable (Section 12.4).¶

A replacement accepted on refresh MUST apply only to the grant refreshed (Section 5.6.1). Any other grant, request_uri, or authorization code bound to the same establishment keeps the state its request was evaluated against.¶

A token request that redeems an authorization code opened by a presentation:¶

  • MUST have a client_id parameter exactly equal to the establishment's sub, even if the client authenticates.¶

  • MUST demonstrate possession of the establishment's proven key under the same sender-constraint mechanism or, for a confidential client whose statement was pulled at the authorization endpoint (Section 5.2), authenticate with the key that becomes the proven key.¶

  • MUST NOT carry the software_statement parameter.¶

A redemption carrying a statement is rejected with invalid_request. A wrong client identifier or failed key binding is rejected with invalid_grant. The prohibition on carrying a statement covers redemption of a code bound to an establishment. A registered client redeeming its own code can deliver a replacement statement under [REGISTRATION], which that specification calls a delivery and which is not a presentation.¶

Expiry after presentation does not by itself invalidate an establishment already bound. The authorization server controls continued use as Section 5.6.1 defines.¶

5.6.1. Refresh

On refresh-token use, the authorization server MUST verify possession of the establishment's proven key under the same sender-constraint mechanism. Except for an establishment created under Section 5.4.1, it MUST also verify that the document currently served at the establishment's sub still carries that key, in its jwks or at its jwks_uri, within the reuse bounds of Section 5.4, and rejects the refresh with the invalid_grant error code if that document does not carry the key or exceeds the size bound of Section 3.1, or with temporarily_unavailable if a retrieval needed to check the key did not complete.¶

On refresh-token use, the authorization server MAY, by local policy, additionally require a current statement, and SHOULD require one once the establishment's recorded statement has expired (Section 14.7). The recorded statement satisfies that requirement while it is unexpired and no refusal record covers it, even after a later statement has raised the iat floor of Section 6. A replacement is needed only once the recorded statement expires or a refusal record covers it.¶

If the authorization server holds a refusal record for the establishment's recorded statement, it MUST reject a refresh without a presented or pulled replacement satisfying this section, whatever its policy on requiring a current statement otherwise: a withdrawal ends grant continuation at once rather than waiting on local policy. To let a withdrawal reach open grants and not only new ones, a server that uses a withdrawal mechanism for the recorded statement's issuer SHOULD consult it for that statement at each refresh.¶

When a replacement is needed, the client presents it in the software_statement parameter of the refresh request, or, for an establishment created from a pulled statement, the server pulls one (Section 5.2). A statement with the recorded statement's iss and jti is not a replacement: if the client offers it again, the server rechecks it as the recorded statement, under the first two paragraphs of this section. The following requirements apply to the replacement:¶

  • It MUST validate under Section 3.2, including its audience if it carries one.¶

  • The iss and sub claims MUST equal those of the recorded statement.¶

  • The iat claim MUST be later than that of the recorded statement.¶

  • The cimd_digest claim MUST name the document currently served at that sub, which the server confirms by retrieval or by revalidating octets it holds.¶

  • The replacement MUST authorize the establishment's proven key (Section 5.4) or, for an establishment created under Section 5.4.1, name a document that still satisfies that section.¶

The refreshed access MUST fall within the metadata of the document the replacement names.¶

On success, the refreshed grant's statement identity, iat, effective expiry, reviewed metadata, and trust decision become those of the replacement (Section 12.4) in a single atomic update, and concurrent replacements resolve to the most recently issued statement. A refresh whose replacement fails these requirements, or that omits a replacement that is needed, leaves the grant's state unchanged and is rejected with statement_required, or with temporarily_unavailable if a retrieval needed to check the replacement did not complete for a reason other than the size bound of Section 3.1.¶

Refresh never rotates the establishment's key. A client that needs a new key performs a new presentation.¶

6. Repeated Consumption of One Statement

A statement attests client software, identified by sub, not its runtime instances. This specification defines no instance identifier. One unexpired statement is therefore consumable more than once: at each trusting authorization server in its audience and, if the server registers clients ([REGISTRATION]) and its policy permits, in more than one registration at that server.¶

A trusting authorization server MUST retain, per iss and sub claims and, on a multi-tenant server, per tenant, the iat claim of the most recent statement it has accepted, as its iat floor. It MUST reject a statement whose iat claim is earlier than the retained iat, whether it arrives as a replacement, a new registration, or a new presentation. A client holding a superseded, broader statement therefore cannot defer a narrowing by opening a fresh registration or establishment with it. The server retains the iat floor at least as long as the maximum statement lifetime it honors for that issuer.¶

Keeping the floor per tenant prevents an issuer's statements for different tenants from superseding one another (Section 14.5). A multi-tenant server also keeps any bound on establishments (Section 12.3) per tenant for the same reason.¶

The first presentation of a replacement that establishes the client supersedes its predecessor for new admissions by every instance of the software at that server (Section 13.3). Grants the predecessor already opened continue under Section 5.6.1.¶

Software whose instances authenticate as the client with keys of their own, which the reviewed document does not carry, can neither prove nor register those keys (Section 5.4, [REGISTRATION]) and depends on the attested-key extension of Section 11.¶

7. Relationship to Other Work

This section is non-normative.¶

7.1. Client Attestation

A software statement and a client attestation [ABCA] are both signed third-party assertions. A statement attests client software and the metadata its issuer evaluated. It is signed by an issuer trusted for a set of client identifiers and accepted wherever that issuer is trusted. A client attestation attests a running instance and the key it holds, and is presented with a proof bound to the request.¶

Neither assertion grants access nor substitutes for the other. Runtime presentation therefore always requires a sender constraint (Section 5.4). Binding a presenter attestation defined elsewhere is an extension (Section 11).¶

7.2. Identity Assertions

A statement records that a named party reviewed software, not that a particular customer currently permits that software to act in its tenant. A tenant-scoped decision (aud_tenant) authorizes no particular user or transaction. When a customer's identity provider mediates a grant, as with a cross-domain identity assertion [IDJAG], it already answers the customer's question per grant by issuing assertions only for clients the customer permits. A statement serves when the issuer is not in the request path, as in the following cases:¶

  • A publisher program vouches to servers it will never see.¶

  • A provider admits software it has never registered.¶

  • A customer wants a portable record of what its review covered.¶

7.3. OpenID Federation

A trust mark [OPENID-FED] is also a signed third-party assertion about an entity, but it is resolved through a federation that supplies key discovery, policy, and delegation, and in which both parties enroll. A statement needs no federation: a trusting authorization server configures its issuer directly (Section 4), and the statement binds the exact octets of the client's own document rather than metadata the federation resolves.¶

8. Error Responses

A rejection uses the error response and HTTP status codes specified for the endpoint where it occurs:¶

  • At the token endpoint, Section 5.2 of [RFC6749] applies.¶

  • At the pushed authorization request endpoint, Section 2.3 of [RFC9126] applies.¶

  • At the authorization endpoint, Section 4.1.2.1 of [RFC6749] applies.¶

At the token and pushed authorization request endpoints, an authorization server SHOULD respond with HTTP status code 503 to a request it rejects with the temporarily_unavailable error code. The status code lets a client distinguish a retrieval worth retrying from a condition that needs a new statement. [REGISTRATION] defines rejections at a registration endpoint and how registration validity is reported.¶

8.1. Requiring a Current Statement

This specification defines the following error code:¶

statement_required:

A current software statement is required and none was supplied or pulled, or the one supplied or pulled is expired, refused by a refusal record (Section 3.3), or superseded under the iat floor of Section 6. The code also applies when a statement offered as a replacement (Section 5.6.1, [REGISTRATION]) does not satisfy the requirements for one. Re-presenting the same statement cannot succeed. The client recovers by obtaining a statement issued more recently.¶

Whenever this specification requires a current statement on a refresh-token request, statement_required replaces invalid_grant. The distinct code keeps a client from reading the rejection as an invalid refresh token ([RFC9700]).¶

8.2. Presentation

A presentation rejected at the token or pushed authorization request endpoint for a reason this specification defines uses the following error codes:¶

invalid_client:

The statement or the client cannot be established, in any of the following cases:¶

  • The statement is malformed, or fails signature or claim validation (Section 3.2) for a reason other than expiry or a refusal record.¶

  • The statement is valid but not acceptable here: its issuer is not configured, its aud excludes this server, its sub is outside the issuer's scope, its aud_tenant is not this request's tenant or is absent when required, or its statement_uses excludes this use.¶

  • The request's client_id differs from the statement's sub (Section 5.1).¶

  • The reviewed document contains duplicate member names (Section 3.2) or exceeds the server's size bound (Section 3.1).¶

  • The document's digest does not match cimd_digest and the server does not proceed without the statement (Section 5.5).¶

  • The request fails the sender constraint, including a presentation under a document that omits token_endpoint_auth_method and one at the token endpoint under a document with no key material (Section 5.4, Section 5.4.1).¶

  • The server's bound on establishments is reached (Section 12.3).¶

statement_required:

The statement is expired, refused by a refusal record, or superseded, or a required statement is absent, including one from an issuer required for the tenant (Section 4).¶

unauthorized_client:

The request exceeds the reviewed document's grant types or response types (Section 5.5), the document carries metadata this server's policy refuses, or the client is review-only and this server requires reviewed software (Section 5.4.1).¶

invalid_scope:

The request exceeds the reviewed document's scope (Section 5.5), or the document carries a scope this server's policy refuses.¶

temporarily_unavailable:

A retrieval the presentation needs did not complete, for a reason other than the document size bound (Section 3.1).¶

invalid_request:

The request carries software_statement in a role Section 5.1 does not permit.¶

A request rejected for another reason, such as an assertion grant whose assertion is invalid (Section 3.1 of [RFC7523]), uses the error code its grant or endpoint assigns.¶

8.3. Code Redemption and Refresh

A token request that redeems an authorization code opened by a presentation is rejected with invalid_request if it carries software_statement, with invalid_grant if its client identifier or key binding fails (Section 5.6), and with invalid_client if the server's bound on establishments is reached (Section 12.3).¶

Under an establishment, a refresh-token request rejected for a reason this specification defines uses the following error codes:¶

statement_required:

A current statement or a replacement is needed (Section 5.6.1) and none is supplied or pulled, or the one supplied or pulled fails Section 5.6.1: it is malformed, invalid, not acceptable here, expired, refused, or superseded, or it names a document whose digest does not match, that contains duplicate member names, that exceeds the size bound, or that no longer satisfies Section 5.4.1.¶

invalid_grant:

The request does not prove the establishment's proven key, or the document currently served at the establishment's sub no longer carries that key or exceeds the document size bound (Section 5.6.1).¶

temporarily_unavailable:

A retrieval needed to check the replacement or the proven key did not complete, for a reason other than the document size bound (Section 3.1).¶

unauthorized_client or invalid_scope:

The refreshed access would exceed the reviewed document's metadata or this server's policy, as for a presentation.¶

invalid_request:

The request carries software_statement in a role Section 5.1 does not permit.¶

None of these rejections indicates refresh-token replay ([RFC9700]). A refresh-token request rejected for another reason, such as an expired or revoked refresh token, uses the error codes of Section 5.2 of [RFC6749]. This specification does not change how an authorization server detects refresh-token replay.¶

8.4. Authorization Endpoint

A statement is never presented at the authorization endpoint (Section 5.1.1) but can be pulled there (Section 5.2). There, if reviewed software is required (Section 5.4.1, Section 5.2), a review-only client is rejected with unauthorized_client, and a client whose pulled statements could not be retrieved is rejected with temporarily_unavailable.¶

Apart from those two cases, at the authorization endpoint, if the authorization server requires a statement for a client it has not admitted on one, it MUST return the statement_required error code in the authorization error response (Section 4.1.2.1 of [RFC6749]). The code tells the client to obtain a statement and return through the pushed authorization request endpoint. Without the code, a client cannot tell a missing review from a policy it will never satisfy.¶

The authorization server redirects with the error only after resolving the client's Client ID Metadata Document and validating the request's redirect_uri against it. If the authorization server cannot resolve the document, it MUST NOT redirect, and it reports the error to the resource owner instead.¶

An authorization request carrying the software_statement parameter (Section 5.1.1) is rejected with invalid_request in place of any other code of this section. The authorization server redirects with that error only after validating the request's redirect_uri: for a client identified by its Client ID Metadata Document URL, against that document as the preceding paragraph requires, and for a registered client, against its registered redirection URIs (Section 4.1.2.1 of [RFC6749]).¶

8.5. Proof Mechanism Errors

If the proof mechanism defines an error of its own for a proof it does not accept, such as invalid_dpop_proof for a DPoP proof that fails the checks of Section 4.3 of [RFC9449] or use_dpop_nonce for a nonce challenge (Section 8 of [RFC9449]), the request is rejected with that error in place of the code this specification assigns to a failed sender constraint.¶

A proof that its mechanism accepts but that proves a key other than the one this specification requires, such as a key the reviewed document does not carry or one other than the establishment's proven key, is not an invalid proof: it fails the sender constraint, and is rejected with the code this specification assigns to that failure.¶

8.6. Error Descriptions

These codes do not tell a client whether to seek a corrected statement or a different issuer. The authorization server can return non-sensitive diagnostics in the error_description parameter to a client it has authenticated, but MUST NOT reveal details of its issuer trust configuration (Section 4), such as the client identifier namespaces an issuer can attest, to an unauthenticated requester.¶

If a statement is refused by a refusal record rather than merely expired, and the client is authenticated, the authorization server ought to indicate that a statement issued more recently is required.¶

9. Examples

Both examples are non-normative.¶

9.1. Presenting at the Token Endpoint

The following is an example of a client presenting a statement at the token endpoint of a server holding no record for the client (line breaks for display purposes only). The reviewed document names a jwks_uri, the private_key_jwt authentication method, and the client_credentials grant type, so the client authenticates with a key that document carries. The client_id is the statement's sub.¶

POST /token HTTP/1.1
Host: as.example
Content-Type: application/x-www-form-urlencoded

grant_type=client_credentials
&scope=tools.read
&client_id=https%3A%2F%2Fclient.example%2Fapp
&client_assertion_type=urn%3Aietf%3Aparams%3Aoauth%3A
client-assertion-type%3Ajwt-bearer
&client_assertion=eyJhbGciOiJFUzI1NiIsImtpZCI6IjIwMjYtMDgifQ...
&software_statement=eyJ0eXAiOiJzb2Z0d2FyZS1zdGF0ZW1l...
¶

The authorization server validates the statement, retrieves the document its digest names, verifies the client assertion against a key from that document's jwks_uri, and checks that the requested scope falls within the document's scope. It keeps no registration.¶

9.2. Publishing a Statement for Servers to Pull

The following is an example of a Client ID Metadata Document that names where its statements are published:¶

{
  "client_id": "https://client.example/app",
  "redirect_uris": ["https://client.example/cb"],
  "token_endpoint_auth_method": "private_key_jwt",
  "jwks_uri": "https://client.example/jwks.json",
  "software_statements_uri":
    "https://client.example/statements.json"
}
¶

A request to that URL returns the statements, here one:¶

{
  "software_statements": [
    "eyJ0eXAiOiJzb2Z0d2FyZS1zdGF0ZW1lbnQrand0Iiwi..."
  ]
}
¶

An authorization server receiving an ordinary authorization request with this client_id resolves the document, retrieves the statements, and keeps the one from a trusted issuer whose cimd_digest matches the document it retrieved. It completes the binding when the client authenticates with private_key_jwt at code redemption (Section 5.2).¶

10. Authorization Server Metadata

This specification defines the following authorization server metadata [RFC8414] values:¶

software_statement_jwks_uri:

REQUIRED for an authorization server that issues statements under this specification. URL of a JWK Set containing only the keys with which it signs them. The URL MUST use the https scheme, and a trusting authorization server MUST validate the server's certificate when retrieving it.¶

The keys in this set MUST NOT appear in the JWK Set at the server's jwks_uri metadata value, and the server MUST NOT sign anything other than statements under this specification with them. As a result, a key that signs another artifact, such as a Status List Token or a software statement of another profile, cannot verify a statement (Section 14.3).¶

software_statement_signing_alg_values_supported:

REQUIRED for an authorization server that issues statements under this specification. A JSON array containing the asymmetric JWS alg values that the authorization server can use to sign them. The array MUST NOT contain none or a symmetric algorithm. An authorization server that only accepts software statements does not publish it.¶

software_statement_pull_supported:

OPTIONAL. Boolean value indicating whether the authorization server retrieves statements from a client's software_statements_uri member when admitting a client that presented none (Section 5.2). If omitted, the default value is false.¶

11. Extension Points

The following extensions are left to separate specifications:¶

  • Attested keys: a client attestation [ABCA], including one from an attester the reviewed document names, vouching for a key that document does not carry (Section 6).¶

  • Statement conveyance within a client attestation, rather than as a request parameter.¶

  • Runtime presentation on grants other than those Section 5.1 names, such as token exchange.¶

  • Partial review, by which an issuer vouches for particular members rather than a whole document (Section 3).¶

  • Withdrawal mechanisms (Section 3.3), such as Token Status List [STATUSLIST].¶

12. Implementation Considerations

This section gives guidance to implementers. It adds no requirement.¶

12.1. Caching and Reuse of Retrieved Content

A server can revalidate octets it holds with a conditional request rather than retrieving them again. Section 3.1 states when a 304 Not Modified response confirms them.¶

Successful retrievals can be cached within the document's caching directives. A failure is followed by back-off rather than caching, which [CIMD] forbids. A response from a software_statements_uri ought to be cached no longer than the document is, and can be revalidated with a conditional request, as the document can (Section 5.2).¶

12.2. Retrieval and Processing Bounds

An authorization server can bound the retrieval and processing work of Section 14.6 as follows:¶

  • Rate-limit presentations per statement identity, per subject, and per source, and pulls (Section 5.2) per client identifier and per source, before spending retrieval or storage on a new presentation.¶

  • Refuse a presentation that would create a new establishment, before spending retrieval or storage on it, once a bound on establishments (Section 12.3) is reached.¶

  • Bound JWT size and parsing work, concurrent retrievals, response size, and response time.¶

  • Bound the size of a software_statements_uri response and the number of statements examined separately from the document's. Several issuers' statements outgrow a document-sized bound, and a host can pad the array.¶

  • Discard pulled statements from unconfigured issuers before verifying any signature.¶

12.3. Bounding Establishments

A trusting authorization server can bound the number of establishments, and any registrations ([REGISTRATION]), derived from one issuer's statements about one piece of software, identified by iss and sub claims. How it counts toward a bound is local policy. Two choices keep a bound effective:¶

  • State that anyone holding a copy of a statement can create does not count: a pushed authorization request and its unredeemed code, which anyone holding a copy of a public client's statement can approve with their own account, or a registration under which no access token has been issued. Otherwise a holder of a copy could exhaust the bound for the software's other instances.¶

  • A count persists across replacements: an establishment created for a refreshed grant does not add to it, and one keyed on jti would reset at every renewal.¶

For software admitted under Section 5.4.1, whose every installation opens its own establishment, a server can also bound establishments per resource owner, so that one user cannot exhaust a bound the software's other users share.¶

A request refused at a bound is rejected with invalid_client (Section 8.2). Its statement is valid, so the authorization server ought to state that reason in error_description, and the client can retry once earlier establishments are released.¶

12.4. Grant State

An authorization server can reuse an establishment across presentations that resolve to the same sub, statement, tenant, sender-constraint mechanism, and proven key, with the statement presented for each or pulled for each, rather than creating one per request, and can discard it once no request_uri, authorization code, refresh token, or other continuation state references it (Section 5.6).¶

A server that shares an establishment among grants applies a replacement accepted on refresh by giving the refreshed grant its own establishment, so that no other grant or outstanding authorization code changes (Section 5.6.1).¶

12.5. Issuer Signing Nodes

An issuer with several signing nodes coordinates iat values across them, so that the values of its statements for a given iss and sub increase strictly whichever node signs (Section 3).¶

12.6. User Interface, Audit, and Logging

An authorization server ought not to present the review in a review-only presentation to the user as an assurance about the presenter (Section 5.4.1). It can record the statement's issuer for audit and inventory.¶

Authorization servers ought to avoid logging software statements, which are sensitive in transit and at rest. A statement names reviewed software and, if it carries an audience, that software's intended relationships.¶

13. Deployment Considerations

This section gives guidance to operators and issuers. It adds no requirement.¶

13.1. Configuring Issuer Trust

Trust configuration ought to constrain each issuer to the client identifier namespaces it is expected to attest, for example URLs under the domains of the software publishers it serves. Section 3.2 rejects a statement outside that scope. Without such a scope, a compromised or over-broad issuer can mint acceptable statements about any client software.¶

When a trusting authorization server configures an issuer whose decisions are confined to one of its tenants, as a customer's own issuer is, it ought to record with that configuration the client identifier namespaces for which the issuer's decision is required in that tenant (Section 4).¶

13.2. Audience and Tenant Claims

An issuer ought to name an audience and, for a statement whose statement_uses claim permits registration, to omit the aud claim only if it accepts that any server trusting the issuer can register the software on the strength of a copy ([REGISTRATION]).¶

An issuer ought to omit the aud_tenant claim from a statement whose review applies wherever its aud reaches, such as a marketplace listing. The claim is also unnecessary if the authorization server has one tenant, or if the server's trust configuration confines the issuer to a tenant, as it can for an issuer that does not know the tenant's identifier.¶

13.3. Statement Lifetime and Renewal

Short lifetimes tighten an issuer's control and increase renewal traffic. At a server that registers clients under [REGISTRATION], the lifetime also sets the registration's renewal cadence. A fleet of statements issued together expires together, so issuers ought to stagger expiries or renew ahead of the boundary.¶

Because an issuer reviews the document it retrieves, a changed document is always served before a statement over it exists. Until the new statement exists, a presentation under the earlier one fails the digest comparison (Section 5.5), and at registration a mismatch is fatal ([REGISTRATION]). The statement's lifetime bounds how stale an unobserved review can become.¶

Instances need the current statement from a shared source rather than a copy fixed at build or install time, because the first presentation of a replacement supersedes its predecessor for every instance (Section 6).¶

13.4. Withdrawal Practice

What a server does when it cannot consult a withdrawal mechanism it relies on is local policy (Section 3.3). Refusing makes issuer availability a precondition for every request the statement governs. Proceeding leaves a withdrawn statement acceptable until it expires.¶

A refusal that the server's operator entered, rather than one derived from a withdrawal mechanism, persists on the operator's own terms.¶

Withdrawal does not replace lifetime: an issuer chooses exp assuming no trusting authorization server uses a withdrawal mechanism.¶

14. Security Considerations

The security considerations of [CIMD] and Section 5 of [RFC7591] apply.¶

14.1. What a Statement Attests

A statement binds an issuer's review to the octets of a Client ID Metadata Document, which describes an OAuth client configuration, such as its redirection URIs, keys, grant types, and scope. It does not bind the software's code, dependencies, or behavior. Software can change while its document stays the same, and the statement remains acceptable until it expires or is withdrawn (Section 3.3). Assurance about the software itself rests on the issuer's review process and, where an extension provides one, an attestation of the running instance (Section 11). Any change to the document's octets, including one that changes no metadata value, makes statements over the earlier octets fail the digest comparison (Section 5.5).¶

14.2. Statement Theft and Replay

A copied statement admits nothing without the sender constraint (Section 5.4). Admitting only keys the reviewed document carries also prevents a downgrade to a key the issuer did not review. An extension admitting attested keys (Section 11) has to address downgrade itself.¶

Attesting a jwks_uri attests the location, not its contents: a compromised key host can add keys that satisfy the proof without a digest change. If that matters, an issuer attests jwks inline and accepts that rotation changes the digest. A server reusing a cached key set (Section 5.4) also accepts that a just-removed key can briefly continue to verify.¶

14.3. Servers That Do Not Implement This Specification

A statement carries no client metadata, so an [RFC7591] server that verified one without implementing this specification would take every metadata value from the registration request, attaching the issuer's approval to an attacker's redirection URIs and keys. Keeping statement signing keys at software_statement_jwks_uri, out of jwks_uri, and away from statements of other profiles (Section 10) guards against this. A server that discovers an issuer's keys through the jwks_uri in its [RFC8414] metadata finds none that verify a statement. A server is exposed only if its operator configures the statement key set in a server that does not implement this specification.¶

14.4. Copied Statements and Public Clients

A party holding a copied statement for a public client can open a pushed authorization request in the reviewed software's name. It cannot receive an authorization code that another resource owner approves in a user agent the party does not control (Section 5.4.1), so other users are exposed only to a consent prompt carrying the reviewed software's name and branding. Rate limits (Section 12.2) and the issuer's choice of audience and lifetime bound that exposure.¶

A party that controls the user agent receives the code: an application embedding a user agent (Section 8.12 of [RFC8252]), or a holder authorizing with its own account. It redeems the code with a PKCE verifier and key of its own choosing. An admission under Section 5.4.1 therefore shows where codes are delivered, not which software holds the grant, and a tenant's required issuer (Section 4) cannot keep unreviewed software out for a user who chooses to run it. This is the client impersonation that Section 8.6 of [RFC8252] describes for public clients. An attested-key extension (Section 11) would strengthen the binding by giving the instance a key a third party vouches for.¶

14.5. Tenant Confusion at a Multi-Tenant Authorization Server

A multi-tenant server that derives the tenant one way to check a decision and another way to scope a token lets a client reach one tenant's resources on another tenant's decision. Section 3.2 requires one tenant for both, selected by no value the client chooses. The aud_tenant claim makes that failure detectable: a statement naming a tenant cannot be used in another.¶

This specification defines no tenant parameter, and a Client ID Metadata Document URL is the same client_id in every tenant, so neither a client nor an issuer can verify that a server honored the tenant rule of Section 3.2.¶

The aud_tenant claim names a tenant at the trusting authorization server, not which of the client's own customers is asking. Software that acts for many customers under one client identifier and key presents the same statement and key for each, so a statement naming a tenant admits the software there on behalf of every customer it serves, and any of those customers can direct the software at another customer's tenant. A statement attests software and cannot prevent this. A deployment that needs a customer-to-tenant binding records it at the trusting authorization server.¶

14.6. External Retrieval and Resource Exhaustion

Runtime presentation can cause the authorization server to retrieve the Client ID Metadata Document, a jwks_uri it names, or the statements its software_statements_uri names. A trusted signature does not make a URL safe, so Section 5.3 applies the server's retrieval policy to every referenced location and rejects a request whose retrieval fails, except as Section 5.2 provides.¶

These retrievals happen before any client is registered or any user has interacted, so an unauthenticated requester can cause them with one acceptable statement or, at a server that pulls statements, with none. The bounds that Section 12.2 describes limit this work but do not prevent it.¶

14.7. Statement Lifetime

Expiry and withdrawal (Section 3.3) govern new admissions. Neither revokes an issued access token. A grant opened by a statement lasts for the life of its refresh tokens, whatever the statement's lifetime, unless the server requires a current statement on refresh, holds a refusal record, or finds the proven key gone from the client's document (Section 5.6.1). A narrowed review takes effect when the client publishes the narrower document and obtains a statement over it.¶

14.8. Observable State

A statement_required refusal at the authorization endpoint (Section 8) travels through the user agent, so anyone who can see the redirection learns that this client has no established standing at this server. The disclosure is accepted because a client that cannot learn why it was refused cannot act. The disclosure carries no detail of the server's issuer trust configuration, which Section 8 keeps from unauthenticated requesters.¶

15. Privacy Considerations

The privacy considerations of [CIMD] and Section 6 of [RFC7591] apply.¶

A presentation or delivery reveals to the authorization server the client's issuer relationship and, if the statement carries an aud claim, the other authorization servers the client intends to use. Omitting that claim discloses nothing beyond the review. Pushed authorization requests (Section 5.1.1) keep statements out of browser history, referrers, and front-channel logs.¶

A central issuer also learns from renewals which of its statements are in active use, so issuance and renewal logs deserve the same care as the statements (Section 12.6).¶

Retrieving the document tells its host that the server is resolving the client. Pulling statements (Section 5.2) tells the host of software_statements_uri the same. That host is an additional party only if the URL is on another origin. Published statements are readable by anyone, so their aud and aud_tenant claims disclose which servers and tenants a review names. A statement whose audience is sensitive is presented rather than published.¶
