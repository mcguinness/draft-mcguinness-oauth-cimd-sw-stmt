Client ID Metadata Document Software Statement Status

Abstract

This specification defines how the status of a software statement for a Client ID Metadata Document is published and checked. Token Status List supplies the authoritative status: an issuer publishes it, and a trusting authorization server resolves it on the list's own schedule and refuses a withdrawn statement. Optional Shared Signals events tell an issuer's trusting authorization servers that a status has changed, prompting them to check at once. An event indicates only when to check, so a server that misses every event reaches the same result on its ordinary schedule.¶

1. Introduction

[STATEMENT] lets an issuer withdraw a statement's decision before the statement's expiry but requires and defines no withdrawal mechanism. This specification defines one, and an optional event that prompts a trusting authorization server to consult it at once. Section 3 profiles Token Status List [STATUSLIST]: an issuer withdraws a decision by setting the statement's status, and a trusting authorization server learns of the change when it next resolves the list.¶

A withdrawal therefore takes effect only as quickly as trusting authorization servers resolve the list. As an optional addition, this specification defines a Shared Signals Framework [SSF] event by which an issuer tells the trusting authorization servers that have configured it ([STATEMENT]) that a status has changed, prompting them to resolve that status at once. An event carries no status, and the status list remains the authority on whether a statement stands (Section 7).¶

The requirements of Section 4 through Section 8 apply only to implementations that support the events. This specification defines no new endpoint, transport, subject identifier format, or trust establishment mechanism. [STATEMENT] does not depend on this specification.¶

2. Conventions and Definitions

The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED", "MAY", and "OPTIONAL" in this document are to be interpreted as described in BCP 14 [RFC2119] [RFC8174] when, and only when, they appear in all capitals, as shown here.¶

Transmitter, Receiver, Stream, and the delivery and configuration mechanisms are defined by [SSF]. Security Event Token (SET) is defined by [RFC8417]. Subject identifier formats are defined by [RFC9493]. Status List Token, and the validation that resolves a status, are defined by [STATUSLIST]. The terms Issuer, Trusting Authorization Server, Effective Expiry, and Refusal Record are defined by [STATEMENT], as are the software statement, its claims, its validation, issuer trust configuration, and withdrawal.¶

For the events defined here, the issuer acts as a Transmitter, and a trusting authorization server that has configured it acts as a Receiver.¶

3. Token Status List

An issuer can use Token Status List [STATUSLIST] as a withdrawal mechanism ([STATEMENT]) for its statements. A trusting authorization server can resolve those statuses for any issuer it has configured.¶

3.1. Status Publication

An issuer that uses Token Status List publishes the status of its statements as [STATUSLIST] defines, and each statement's status claim ([STATEMENT]) locates its entry in the issuer's Status List Token. An issuer that publishes status:¶

  • MUST publish status, and carry the status claim, for every statement it issues under a given iss from the point it begins publishing. Once statements issued before that point have expired, a trusting authorization server can read an absent claim as meaning the issuer publishes no status.¶

  • MUST NOT assign the same combination of status list URI and index to more than one statement, including across successive Status List Tokens published at that URI. Withdrawing a statement then affects no other.¶

  • MUST sign the Status List Token with a key published at the jwks_uri metadata value of its authorization server metadata [RFC8414], which [STATEMENT] keeps apart from its statement signing keys.¶

  • MUST include the exp claim in every Status List Token it publishes, to prevent an older token from standing in for a newer one indefinitely.¶

  • MUST give each Status List Token it publishes at a given list URI an iat claim value later than that of any token it published there before (Section 3.2).¶

3.2. Status Resolution

If a statement carries the status claim and the trusting authorization server resolves statuses for the statement's issuer, the server MUST reject the statement if its status is INVALID, and MUST apply its configured policy for that issuer to the statement if its status is SUSPENDED or any other value except VALID and INVALID.¶

A status of INVALID is a withdrawal, as is any other status except VALID when the policy configured for that issuer refuses the statement. On a withdrawal, the server holds a refusal record ([STATEMENT]). Token Status List defines no expiry for a withdrawal, so the refusal ends only when a later resolution returns a status that no longer refuses the statement.¶

Resolution follows [STATUSLIST]. In particular:¶

  • If the referenced index lies outside the list, the server rejects the statement as [STATUSLIST] requires, with the error code that the consuming specification, such as [STATEMENT], assigns to a statement refused by a refusal record.¶

  • The caching rules of [STATUSLIST] apply to resolution, and also apply when the server checks a recorded statement at refresh ([STATEMENT]).¶

  • A server SHOULD retrieve the list on the list's own schedule, within the expiration and caching bounds its exp and ttl claims set (Section 11.5 of [STATUSLIST]), rather than once per request (Section 11.1).¶

To prevent a host serving an older token from restoring a status the issuer has withdrawn, a server MUST NOT replace a Status List Token it holds with one whose iat claim is earlier, and MUST treat one whose iat claim is equal but whose contents differ as a resolution failure. Section 8.3 of [STATUSLIST] recommends rejecting a statement whose status the server cannot resolve. A statement the server accepts without a resolved status remains bounded by its effective expiry ([STATEMENT]).¶

A server MUST obtain a Status List Token's verification keys from the jwks_uri metadata value of the issuer's authorization server metadata [RFC8414], discovered from the configured iss, and never from the Status List Token itself.¶

4. Event Issuer Trust and Keys

A trusting authorization server MUST NOT accept an event from an issuer it has not configured. It MUST verify the SET using keys from the jwks_uri member of the issuer's Transmitter configuration [SSF], discovered from the issuer identifier it has configured, and never from a key-location value carried in the event. The SET's iss claim is that issuer identifier, which is also the iss claim value of the statements the event concerns.¶

An issuer MUST ensure that its Transmitter configuration's jwks_uri member differs both from the issuer's software_statement_jwks_uri ([STATEMENT]) and from the jwks_uri metadata value in its authorization server metadata [RFC8414], whose keys verify its Status List Tokens. A receiver MUST NOT create or keep a stream whose Transmitter configuration names either of those locations. An issuer MUST NOT publish at its Transmitter configuration's jwks_uri a key that also appears in the key set at either location.¶

A SET carrying an event defined here MUST use the explicit typ JOSE header parameter value secevent+jwt (Section 2.3 of [RFC8417]). Its aud claim MUST contain the audience of the stream that delivers it, which [SSF] lets the transmitter and receiver agree on. A receiver MUST NOT create or keep a stream whose audience does not identify it.¶

5. Subject Identification

The subject of every event defined here is client software. Events carry it in the sub_id claim of [SSF] using the uri subject identifier format of [RFC9493]. The uri member carries the Client ID Metadata Document URL [CIMD] exactly as it appears in the sub claim of the statements the event concerns.¶

A trusting authorization server MUST match the subject by exact comparison of the uri member against a statement's sub claim.¶

6. Event Types

The payload ([RFC8417]) of an event defined here has the following claims:¶

event_timestamp:

OPTIONAL. The claim defined by [CAEP], a NumericDate value that here gives the time at which the issuer changed the status the event reports. It is informational: a receiver does not use it to order, bound, or scope anything.¶

software_statement_jti:

OPTIONAL. The jti claim value of a single statement whose status changed (Section 7).¶

reason_admin:

OPTIONAL. An administrative message, as [CAEP] defines the claim.¶

6.1. Status Changed

The event type identifier is urn:ietf:params:oauth:event-type:software-statement-status-changed (Section 13.1).¶

The event reports that the issuer has changed the published status of one or more statements for the subject. A transmitter MUST NOT transmit the event until a Status List Token reflecting the change is retrievable at the status list URI, including through any caching layer it operates. A receiver resolving before then would fetch the state the event exists to correct.¶

The event does not say what the new status is, and a receiver MUST NOT infer one from it. A receiver that resolves a status of VALID after receiving an event has applied that event correctly.¶

The following is a non-normative example of the payload of a SET carrying this event for one statement:¶

{
  "iss": "https://issuer.example",
  "jti": "4d3559ec67504aaba65d40b0363faad8",
  "iat": 1767225600,
  "aud": "https://as.example",
  "sub_id": {
    "format": "uri",
    "uri": "https://client.example/app"
  },
  "events": {
"urn:ietf:params:oauth:event-type:software-statement-status-changed":
    {
      "event_timestamp": 1767225590,
      "software_statement_jti": "c2a907b34d28"
    }
  }
}
¶

7. Receiver Processing

A trusting authorization server that receives an event defined here MUST process it as follows:¶

  1. Verify the SET as [RFC8417] requires, including its typ JOSE header parameter, and verify that the SET's issuer is configured and that the keys verifying the SET were obtained as Section 4 requires.¶

  2. Reject an event whose aud claim does not contain the audience of the stream that delivered it (Section 4).¶

  3. Resolve the subject (Section 5).¶

  4. Resolve the status of the affected statements from the Status List Token each statement's status claim references, as [STATUSLIST] defines, using a copy that the status list URI served, or confirmed by revalidation, in response to a request begun after the event arrived, without waiting for the schedule that would otherwise apply, and apply the resolved status as Section 3.2 defines.¶

If step 1 or 2 fails, the receiver reports a SET error as [RFC8935] or [RFC8936] provides. Otherwise, it acknowledges the SET, whatever steps 3 and 4 produce. A receiver ignores any other member of the SET's events claim.¶

The affected statements are those the transmitting issuer made about the subject, never statements another issuer made about the same software. They are the statement the event's software_statement_jti claim names or, if the event names none, those the receiver holds or has cached a status for. An event about a subject for which the receiver holds no state requires nothing of it. A receiver ignores events for subjects outside the identifier scope for which it accepts the transmitting issuer ([STATEMENT]).¶

Revalidation suffices because a transmitter sends the event only once a token reflecting the change is retrievable (Section 6.1). One request begun after several events arrived serves every one of them that concerns the list it retrieves. An event is never grounds for refusal. Until the request succeeds, the copy the receiver holds remains in effect within its validity. If resolution does not complete, the receiver proceeds as it would had no event arrived: a refusal record it holds stands, and the statement remains bounded by its effective expiry ([STATEMENT]).¶

A receiver MUST treat an event it has already applied as successfully delivered and acknowledge it as [RFC8935] or [RFC8936] requires, rather than reporting a delivery error. Rejecting a retry can stall or disable a stream carrying later events. Duplicate detection is per transmitting issuer.¶

Two constraints bound every event:¶

  • A receiver MUST NOT let an event by itself create standing, extend a statement's lifetime, or otherwise increase what a client can do. A receiver MUST ignore any payload claim that would have such an effect.¶

  • A receiver MUST continue to resolve status as Section 3.2 provides, and to enforce statement expiry, independently of this mechanism. Stream loss, transmitter unavailability, or delivery failure then leaves both controls in force.¶

8. Stream Configuration

An issuer that supports the events defined here publishes Transmitter configuration metadata as [SSF] defines, discoverable from its issuer identifier. Stream creation, subject management, verification, and delivery follow [SSF].¶

A trusting authorization server that supports these events SHOULD create one stream per configured issuer that offers them (Section 10.1).¶

The subjects appropriate to a stream are those of the issuer's statements whose aud claim is absent or names the receiving authorization server. A transmitter SHOULD scope each stream to those subjects.¶

A receiver SHOULD request the event this specification defines, and SHOULD use the stream verification facility of [SSF] periodically.¶

9. Implementation Considerations

This section gives guidance to implementers. It adds no requirement.¶

9.1. Resolution in Response to Events

A receiver can bound the rate of the retrievals that events cause by deferring a retrieval briefly and coalescing events that concern the same status list URI, since one request begun after those events serves them all (Section 7). Its scheduled resolution continues regardless.¶

9.2. Event Logs

A receiver ought to treat event logs as sensitive at rest, as [STATEMENT] treats statements. A log of events is a record about client identifiers that can outlive the issuer's own published status, so a receiver ought to bound its retention.¶

10. Deployment Considerations

This section gives guidance to operators and issuers. It adds no requirement.¶

10.1. Stream Coverage and Monitoring

A stream can cover every subject appropriate to it (Section 8), or the receiver can add each subject through the subject management of [SSF] when it first admits that software. Admission checks and the receiver's own status resolution (Section 3.2, Section 7) remain independent of the subjects a stream covers, so a withdrawal whose event was transmitted before the subject was added to the stream is found at a later resolution.¶

A receiver ought to alert on stream loss rather than assume quiescence.¶

10.2. Resolution Schedule and Lifetimes

Because events can be suppressed, a deployment ought to choose a resolution schedule and statement lifetimes it would accept with no event stream (Section 7).¶

11. Security Considerations

The security considerations of [STATEMENT], [STATUSLIST], [SSF], and [RFC8417] apply.¶

11.1. Status Resolution Schedule

Because [STATUSLIST] aggregates many statements into one list, a retrieval tells the issuer only that some trusting authorization server is checking. Retrieving the list on its own schedule (Section 3.2) keeps the server's request timing from disclosing the client population it serves, and keeps each request a statement governs independent of issuer availability.¶

11.2. What an Event Cannot Do

An event names no status, so a forged, replayed, delayed, or reordered event cannot change whether any statement stands. Its only effect is a resolution the receiver would otherwise have performed on its own schedule.¶

The remaining exposure is resource cost: an attacker holding the issuer's SET signing key, or a misbehaving transmitter, can trigger resolutions (Section 9.1).¶

11.3. Status Remains the Authority

Because a receiver resolves status independently (Section 7), an attacker who suppresses events delays a withdrawal at most until the receiver's next scheduled resolution and, for new admissions, never beyond the affected statements' effective expiry (Section 10.2). Grants already open continue until a refresh at which the receiver holds a refusal record, which [STATEMENT] then rejects unless it carries an acceptable replacement.¶

The absence of events looks the same on a healthy stream and a suppressed one. Periodic stream verification (Section 8) makes the difference observable (Section 10.1).¶

11.4. Key Separation and Compromise

The distinct key sets of Section 4 separate SET keys from statement and Status List Token keys. With the keys separated, compromise of a SET key lets an attacker trigger resolutions and nothing more. Compromise of a statement signing key has wider effect, because statements grant standing and events do not.¶

12. Privacy Considerations

The privacy considerations of [STATEMENT], [STATUSLIST], [SSF], and [RFC8417] apply. Section 11.1 describes how the resolution schedule limits what retrieval discloses. A retrieval that an event prompts shows the issuer that the receiver holds a statement or a cached status for the event's subject.¶

Subject identifiers in these events name reviewed software and, in aggregate, describe an organization's approved software estate. For this reason, a stream is scoped as Section 8 provides. Event logs deserve the same care as statements (Section 9.2).¶

Because the events this specification defines create no durable receiver-side record, they add no negative state about a client identifier that outlives the issuer's own published status. A receiver that logs events creates such a record (Section 9.2).¶

13. IANA Considerations

13.1. OAuth URI Registry

[RFC8417] establishes no registry of event types, so this specification takes its identifier from the oauth sub-namespace [RFC6755] and requests registration of the following value in the IANA "OAuth URI" registry:¶

URN:

urn:ietf:params:oauth:event-type:software-statement-status-changed¶

Common Name:

Client ID Metadata Document Software Statement Status Changed Event Type¶

Change Controller:

IETF¶

Specification Document(s):

This specification, Section 6.1¶

13.2. SET Payload Claims

Under Section 2 of [RFC8417], the software_statement_jti payload claim of Section 6 is defined by this specification and need not be registered as a JWT claim. No IANA registry of SET payload claims exists, so no registration is requested.¶
