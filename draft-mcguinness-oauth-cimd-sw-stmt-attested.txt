 Client ID Metadata Document Software Statement Attested Instance Keys
          draft-mcguinness-oauth-cimd-sw-stmt-attested-latest

Abstract

   A companion specification defines a software statement that binds a
   review of client software to the exact octets of its Client ID
   Metadata Document (CIMD).  It does not, by itself, bind an
   installation of that software to a key.  This specification defines
   an instance-binding extension in which an independently trusted
   client attester attests an installation's key for the reviewed
   document.  The client proves that key through attestation-based
   client authentication when opening and continuing an authorization
   code grant.  When an attester can verify which software controls an
   installation's key, as on managed devices, this specification permits
   native applications, including command-line clients, to use loopback
   redirects while satisfying a policy requiring reviewed software.

1.  Introduction

   A native application's installations cannot safely authenticate by a
   private key distributed in every copy of the software.  Each
   installation can generate its own key, but possession of that key
   establishes continuity, not the identity of the software using it.  A
   copied Client ID Metadata Document (CIMD) URL [CIMD] and software
   statement can be presented with an attacker's own key.

   Section 5.6.3 of [STATEMENT] therefore treats as review-only a
   presentation under a document containing a redirection URI that
   another application on the same device could claim: the server
   evaluates the statement but admits nothing on it, and such a
   presentation cannot satisfy a policy requiring reviewed software.
   This excludes loopback redirects, even though they are an established
   response-delivery mechanism for native applications under [RFC8252].

   Existing mechanisms do not provide reviewed-software admission for
   loopback clients.  Loopback redirects with Proof Key for Code
   Exchange (PKCE) [RFC7636] protect an authorization code from
   interception, but any application can start a transaction with a
   native client's identifier, the client impersonation that Section 8.6
   of [RFC8252] describes.  Attestation-based client authentication
   [ABCA] alone shows that an installation holds a key an attester
   vouches for, not that the installation runs the software a statement
   issuer approved for a particular document.

   This specification defines an alternative binding made of three
   elements, which stay separate even when one organization operates
   both issuing roles:

   *  The software statement records approval of the software, as its
      publisher identifies it (Section 5), and its exact metadata.

   *  An instance attestation, from an independently trusted client
      attester under an evidence policy the authorization server
      accepts, associates an installation's key with that software and
      metadata.

   *  A proof under attestation-based client authentication demonstrates
      possession of that key.

   The callback delivers the authorization response but supplies no
   evidence of the presenter's software identity.

   This specification serves authorization code flows using pushed
   authorization requests (PAR) [RFC9126] and refresh of the resulting
   grants.  It defines neither registration nor new token-endpoint
   presentations for other grants.  [REGISTRATION] is unchanged: it
   rejects loopback redirects, so a document selecting this profile is
   never registered, whatever the statement_uses claim of a statement
   over it permits.

   The binding is only as strong as the attester's evidence that the
   software, not merely the device or the user, controls the key
   (Section 15.1).  Such evidence is available today mainly on managed
   devices, through an enterprise agent or launcher (Appendix A).  On an
   unmanaged desktop, or for an interpreted command-line client, an
   attester typically cannot meet the requirements of Section 5, and the
   client remains review-only under Section 5.6.3 of [STATEMENT].

   This specification extends [STATEMENT] and [LIFECYCLE], which do not
   depend on it, and relies on [LIFECYCLE] to keep each grant in step
   with the current review (Section 8).

1.1.  Protocol Overview

   The following non-normative sequence summarizes admission under this
   profile:

   1.  A publisher serves a CIMD that selects this profile and declares
       attestation-based client authentication and loopback redirects.
       A statement issuer signs a software statement over its exact
       octets.

   2.  An installation obtains an attestation from an accepted attester.
       The attestation names the client identifier URL, metadata digest,
       attested key, and evidence policy.

   3.  The installation sends a pushed authorization request with PKCE,
       the attestation, and a Demonstrating Proof of Possession (DPoP)
       proof.  It supplies the software statement or lets the server
       pull it.

   4.  The server validates both trust decisions (in the statement
       issuer and in the attester) and their bindings before returning a
       request_uri.

   5.  The user authorizes in an external browser.  The code returns
       over loopback and is redeemed with the PKCE verifier and the
       attested key.

   6.  Refresh requires the proven key, a current instance attestation,
       and a current software statement.  A different key requires a new
       grant.

2.  Conventions and Definitions

   The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT",
   "SHOULD", "SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED", "MAY", and
   "OPTIONAL" in this document are to be interpreted as described in
   BCP 14 [RFC2119] [RFC8174] when, and only when, they appear in all
   capitals, as shown here.

   This specification uses terminology from [RFC6749], [RFC7591],
   [CIMD], and [ABCA], the terms defined in Section 2 of [STATEMENT],
   and the terms defined in Section 2 of [LIFECYCLE].  An installation
   is a Client Instance as defined by [ABCA].

   This specification defines the following terms:

   Instance Attestation:  A Client Attestation JWT under [ABCA],
      profiled by Section 6.  It records an attester's association of a
      key with a client identifier URL and metadata digest under a named
      evidence policy.  An instance attestation is current while its exp
      has not passed and its attester and evidence policy remain
      accepted.

   Evidence Policy:  A versioned set of requirements for establishing
      the association between software, the attested key, and reviewed
      metadata.  It covers evidence collection, verification, freshness,
      and protection of key use.

   Attested Key:  The key an instance attestation's cnf claim names.

3.  Scope and Profile Selection

   An authorization server implementing this specification MUST support
   pushed authorization requests, PKCE with S256 [RFC7636], DPoP
   [RFC9449], and the authentication method of Section 6.2.

   Each installation holds its own credential, the attested key, so a
   client under this profile is a confidential client although it is a
   native application, as Section 8.4 of [RFC8252] contemplates for per-
   instance credentials.  A presentation processed under Section 7.1
   whose redirection URIs meet Section 4.1 is not review-only
   (Section 5.6.3 of [STATEMENT]).

   The client selects this profile by publishing the
   software_statement_instance_binding client metadata member with the
   value true in its reviewed document (Section 4).  A server creates a
   new establishment under the profile only if the server supports this
   specification, the reviewed document selects the profile, and all
   admission checks succeed.  The establishment's recorded binding then
   governs every continuation (Section 7.2).

   This specification permits only the authorization code grant opened
   through a pushed authorization request, and refresh of that grant.
   It does not authorize private-use URI schemes, localhost hostnames,
   non-loopback redirects, implicit responses, device authorization,
   client credentials, or assertion grants.  Other specifications can
   define additional bindings without changing the behavior of this
   profile.

3.1.  Required Binding

   When server policy requires this binding for a client identifier
   namespace or tenant, the server MUST reject a request that opens a
   grant there other than under Section 7.1, whatever artifacts it
   carries or omits.

4.  Client Metadata

   This specification defines the following member of a CIMD:

   software_statement_instance_binding:  OPTIONAL.  Boolean value.  When
      true, the client requires this profile for admissions under this
      document.  If absent or false, the document does not select this
      profile.  A value of any other type is invalid.

   A document selecting this profile MUST meet all of the following
   requirements:

   *  Its token_endpoint_auth_method is the single string
      attest_jwt_client_auth_dpop (Section 6.2).

   *  Its grant_types member explicitly contains authorization_code and
      MAY also contain refresh_token.  It contains no other grant type.

   *  Its response_types explicitly contains only code.

   *  Its redirect_uris is a nonempty array, every member of which meets
      Section 4.1.

   *  It contains neither the jwks nor the jwks_uri member.  Attested
      keys are authorized only through Section 6.1, not by document key
      material.

   The document MAY contain the software_statements_uri member defined
   in Section 5.5 of [STATEMENT].  Metadata governing requested access,
   such as scope, remains subject to Section 5.2 of [STATEMENT].  Every
   member, including the binding selection, is covered by the
   statement's digest.

4.1.  Loopback Redirects

   Every reviewed redirection URI MUST use http, have the host exactly
   127.0.0.1 or [::1], and contain an absolute path.  User information
   and fragments MUST NOT be present.  A reviewed entry MUST NOT contain
   a port: the client uses the port of its listener, which Section 7.3
   of [RFC8252] lets the server accept.  The document MAY list both
   address forms.

   The server MUST compare a requested redirect with a reviewed entry
   using exact string matching, except for the port variation permitted
   by Section 7.3 of [RFC8252].  No other component can vary: the
   address form, path, and any query remain fixed.  In particular, a
   wildcard path, a hostname resolving to loopback, an alternative
   numerical spelling of the address, and a different loopback address
   do not match.

   The authorization server MUST NOT fetch the redirection URI to test
   the client's listener.

5.  Attester Trust and Evidence

   An authorization server MUST establish attester trust independently
   of the request.  For each accepted attester it MUST configure:

   *  The exact attester iss identifier and how the attester's
      verification keys are resolved.  Section 10.8 of [ABCA] recommends
      that a profile fix key resolution.  Keys are resolved by one of
      the following:

      -  An x5c certificate chain ([RFC7515]) validated to a configured
         trust anchor, together with a configured mapping from the
         certificate to this attester, such as an exact subject or
         subject alternative name.  Sharing a trust anchor with another
         attester does not authorize a key for this attester's iss.

      -  A kid matched against a JWK Set configured for this attester.

   *  Accepted asymmetric signing algorithms.

   *  Client identifier namespaces for which the attester can issue
      instance attestations.

   *  Accepted evidence-policy identifiers and, for each, a finite
      maximum evidence age.

   *  Tenant restrictions and any requirements for a particular attester
      or policy within a tenant.

   *  Clock-skew and evidence-freshness requirements and any local
      denial rules for attested keys.

   The authorization server MUST NOT derive attester trust or keys from
   a statement's signature, the client document, or an iss, jku, x5u, or
   other key-location value in the attestation, except a jku naming the
   configured JWK Set. Retrieval from a configured key source is subject
   to the retrieval protections of Section 5.3 of [STATEMENT], and the
   authorization server MUST NOT reuse retrieved trust data, including
   an attester's key set, beyond a finite maximum reuse period of its
   own choosing.

   The server cannot observe how an attester reached its decision, so it
   relies on the evidence policy.  A server MUST NOT accept an evidence
   policy for this profile unless:

   *  Before issuing each instance attestation, the attester verifies
      control of the private key it is to attest through an
      authenticated, replay-resistant exchange bound to the submitted
      public key.

   *  The attester evaluates evidence about the software instance and
      protection of key use, and sets each attestation's exp no later
      than the time that evidence was collected plus the policy's
      maximum evidence age.  The attester rounds or randomizes exp
      (Section 11.1 of [ABCA]) only toward an earlier time, a constraint
      this profile adds.  A previous attestation is not evidence: a
      renewal rests on new evidence under the same bound.

   *  The attester establishes an authenticated association of the
      software, as identified by the evidence, with the client
      identifier URL and with control of the attested key.  It retrieves
      and validates the document under [CIMD], calculates its digest
      under Section 3.1 of [STATEMENT], and confirms that the
      association covers the document version the attestation names.
      Whoever controls the origin of the client identifier URL, or an
      authority that controller has explicitly delegated, authorizes the
      association, for example through a manifest served from that
      origin or signed under that controller's or delegate's authority.
      An enterprise inventory can authenticate or record such an
      authorization, but listing a package and someone else's client
      identifier URL together does not create one.  A URL, file path,
      digest, or publisher name asserted only by the requesting process
      does not suffice, and neither does user approval of a key, a
      publisher account login, possession of a shared embedded secret,
      or device integrity alone.  The metadata digest is not an
      executable digest.

   *  The policy defines what identifies the software, how evidence
      authenticates that identity and the attested key, how use of the
      key is restricted to the software instance the evidence covers, a
      finite maximum evidence age, and the treatment of updates,
      scripts, plugins, and other executable extensions.

   *  The policy's identifier denotes immutable policy semantics: a
      material policy change requires a new identifier.

   A server can use weaker evidence, or successful generic client
   authentication without every check of this specification, for other
   purposes but MUST NOT report either as satisfying this profile.

   Attestation acquisition and platform evidence formats are out of
   scope.  They require an interoperable agreement between the
   installation and its attester.  The wire format below does not by
   itself supply a software-verification mechanism.  Appendix A gives an
   implementation model and its prerequisites.

6.  Instance Attestation

   An instance attestation is a Client Attestation JWT (Section 4 of
   [ABCA]) with the following additional requirements.  Its typ JOSE
   header parameter MUST have the value cimd-instance-attestation+jwt
   (Section 13 of [ABCA]), which is the media type of Section 17.4
   without its application/ prefix.  Together with the document's
   selection of this profile (Section 3), its type tells an
   authorization server that this profile applies.  The attestation MUST
   be digitally signed using an accepted asymmetric algorithm.  A MAC or
   none MUST NOT be accepted.  Its header and claims MUST contain no
   duplicate member names.  Validation MUST apply [RFC8725].

   The attestation contains the following claims.  The sub, iat, exp,
   and cnf claims also retain the requirements of Section 4 of [ABCA].

   iss:  REQUIRED.  The attester's identifier, an HTTPS URL without a
      fragment.  It is matched exactly against the configured attester
      iss identifier (Section 5).

   sub:  REQUIRED.  It MUST be the exact client identifier URL.

   aud:  OPTIONAL.  If present, it contains the authorization server's
      issuer identifier ([RFC8414]).

   iat:  REQUIRED.  It is not an evidence timestamp, and an attester can
      round or randomize it as Section 11.1 of [ABCA] recommends.

   exp:  REQUIRED.  It MUST be later than the iat claim.  It bounds the
      age of the evidence behind the attestation, as the accepted
      evidence policy requires (Section 5).

   cnf:  REQUIRED.  The attested key ([RFC7800]), in the form Section 4
      of [ABCA] requires.

   cimd_digest:  REQUIRED.  The metadata digest defined in Section 3.1
      of [STATEMENT], computed over the document the attester evaluated.
      This claim has the same representation and comparison rules as in
      a software statement.  Its use here records the attester's
      software-to-metadata association, not a second software review.

   cimd_instance_policy:  REQUIRED.  A string containing an absolute URI
      identifying the evidence policy under which the attester attested
      the key.  The URI is an identifier, not a retrieval instruction.
      It MUST be compared exactly with an accepted policy identifier.

   An attestation is not tied to a statement's jti, so a statement
   renewed over unchanged octets need not cause re-attestation.

6.1.  Validation

   At each pushed authorization request, code redemption, and refresh,
   the authorization server MUST validate the instance attestation and
   its proof.  It MUST verify all of the following before accepting the
   binding:

   *  The attestation meets Section 6 and the applicable [ABCA]
      validation requirements.

   *  The signature verifies with a key authorized for the exact iss,
      for this artifact type and accepted algorithm.

   *  The attester and policy are currently accepted for this client
      identifier and tenant, and the key is not denied by local policy.

   *  The request's client_id, the software statement's sub, and the
      attestation's sub are exactly equal.

   *  The attestation's cimd_digest, the applicable software statement's
      cimd_digest, and the digest of the reviewed document are equal.

   *  The attested key and the key of the DPoP proof are equal under the
      key-comparison rules of Section 7.3 of [ABCA].

   A server MUST reject an attestation whose exp claim has passed or is
   later than the current time plus the maximum evidence age it accepts
   for the attester and evidence policy.  It MUST NOT reject an
   attestation only because its iat claim was rounded or randomized.

   On continuation, the proven key and the recorded attester, policy,
   and tenant constraints of Section 7.2 also apply.

   A server MUST NOT accept a software statement as an instance
   attestation, or an instance attestation as a software statement.  The
   statement issuer and the attester are separate roles: one entity can
   perform both, but neither role implies trust in the other, and
   statement signing keys never sign instance attestations (Section 4 of
   [STATEMENT]).

6.2.  Proof of Possession

   Clients MUST use the attest_jwt_client_auth_dpop method of [ABCA] at
   the pushed authorization request endpoint and on every token request
   under this profile.  The method sends the instance attestation in the
   OAuth-Client-Attestation HTTP header field and uses a DPoP proof as
   the proof of possession, in DPoP combined mode (Sections 5.2 and 7.3
   of [ABCA]).  This profile does not support the Client Attestation PoP
   JWT (Section 5.1 of [ABCA]): the client MUST NOT send the OAuth-
   Client-Attestation-PoP HTTP header field, and the server MUST reject
   a request under this profile that does.  A dpop_jkt parameter alone
   is not a proof.  The authentication method and its validation remain
   those defined by [ABCA].  This profile supplies the attestation's
   type and additional bindings.

   The authorization server MUST require a server-issued DPoP nonce at
   the pushed authorization request endpoint and on every token request
   under this profile.  It MUST reject replay of a proof within its
   acceptance window.  Nonce challenges do not consume a code, rotate a
   refresh token, create an establishment, or advance the iat floor.  A
   request rejected before the instance is authenticated, or rejected
   with use_fresh_attestation or temporarily_unavailable, has none of
   these effects either, so the client can retry with a fresh
   attestation.

7.  Runtime Admission

   This section specifies processing at the pushed authorization
   request, authorization, and token endpoints when a grant is opened
   under this profile.

7.1.  Pushed Authorization Request

   The client MUST start every grant under this profile at the pushed
   authorization request endpoint.  Its request MUST include client_id,
   response_type=code, redirect_uri, and a PKCE code_challenge with
   code_challenge_method=S256.  It MUST authenticate under Section 6.2.
   A request using a Request Object MUST meet [RFC9126] and MUST NOT
   provide conflicting parameter values.  The following checks apply to
   the effective authorization request.

   The client presents its software statement in the software_statement
   parameter (Section 5.4 of [STATEMENT]), or the authorization server
   pulls one (Section 5.5 of [STATEMENT]).

   Before responding successfully to a pushed authorization request, the
   authorization server MUST:

   1.  Validate request syntax and the client identifier, and resolve
       the applicable tenant.  If the request carries an instance
       attestation, authenticate the instance under Section 5,
       Section 6, and Section 6.2.  Checks needing no client-controlled
       retrieval precede such retrieval.

   2.  Validate the selected statement (Section 3.2 of [STATEMENT]) and
       apply the refusal records and iat floor (Sections 3 and 4 of
       [LIFECYCLE]).  If statements are pulled, step 3 resolves the
       document first, since the document names where statements are
       published, and Sections 5.3 and 5.5.1 of [STATEMENT] apply.

   3.  Resolve the CIMD (Section 5.3 of [STATEMENT]), perform the digest
       and metadata checks of Section 5.2 of [STATEMENT], enforce
       Section 4, and complete the cross-artifact checks of Section 6.1.

   4.  Validate the requested redirect under Section 4.1, require PKCE
       S256, and evaluate the request against the reviewed metadata and
       authorization policy.

   5.  Create the establishment (Section 7.2), bind the accepted request
       to it, and respond under [RFC9126].

   If any required check fails, the server MUST NOT fall back to review-
   only or unreviewed admission for the same request.  A request that
   carries no instance attestation for a document selecting this profile
   is an example: the server learns from the document (step 3) that this
   profile applies, then rejects the request with invalid_client.  If
   the instance authenticates (step 1) but no statement is presented or
   remains after selection, it returns statement_required.  A failed
   request MUST NOT advance the iat floor.

7.2.  Establishment

   An establishment records all state required by Section 5.7 of
   [STATEMENT] and, in addition:

   *  That this instance-binding profile governs the grant.

   *  The exact attester identifier and evidence-policy identifier.

   *  The attester trust decision.

   The proven key is the attested key, which is also the DPoP key.

   The client identifier, tenant, key, attester, policy, and binding
   profile MUST remain fixed for the lifetime of the grant.  Changing
   any of them requires a new grant opened through a pushed
   authorization request.  A fresh attestation that keeps these values
   can renew the grant's evidence, and a refresh replacement
   (Section 5.2 of [LIFECYCLE]) can update the grant's reviewed metadata
   only as Section 8 permits.  Neither operation changes these values.

7.3.  Browser Authorization

   The client MUST use an external user-agent under [RFC8252].  The
   browser authorization request MUST use the request_uri parameter from
   the pushed authorization response and the same client_id parameter.
   Besides the software statement, which Section 5.4.2 of [STATEMENT]
   excludes, it MUST NOT carry the instance attestation or an instance
   proof.  The server MUST use the parameters stored from the pushed
   authorization request and MUST NOT allow front-channel parameters to
   change the redirect, PKCE challenge, key binding, or tenant.

   When the client's CIMD selects this profile, the server MUST reject
   an authorization request without a request_uri from a pushed
   authorization request governed by this profile, even if it could pull
   a statement there.  Section 3.1 covers a server whose policy requires
   this binding.

   The server authenticates the resource owner and applies authorization
   policy independently of the software and instance checks.  It MUST
   return the authorization response with the issuer identifier in the
   iss parameter defined by [RFC9207].  The client MUST validate that
   identifier, and the state parameter if it sent one, against the
   transaction before redeeming a code.  Callback validation and OAuth
   security requirements in [RFC8252] and [RFC9700] continue to apply.

7.4.  Authorization Code Redemption

   The client sends grant_type=authorization_code, the code, the same
   client_id and redirect_uri, and the PKCE code_verifier.  It MUST
   authenticate with a current instance attestation and a fresh proof
   under the proven key.  It does not send the software_statement
   parameter, which Section 5.7 of [STATEMENT] prohibits on code
   redemption.

   Before issuing tokens, the server MUST verify the code and PKCE
   binding and every fixed establishment value in Section 7.2.  It MUST
   re-evaluate both trust decisions, require the recorded statement to
   be unexpired and not refused, and confirm that the current CIMD still
   matches the recorded digest and meets Section 4.  The server confirms
   the current document by retrieval or from octets it holds within the
   reuse bounds of Section 5.3 of [STATEMENT].  The attestation MUST
   match that digest and not be past its exp.  A server using a
   statement withdrawal mechanism SHOULD consult it at code redemption,
   within that mechanism's freshness rules, as Section 3 of [LIFECYCLE]
   provides for refresh.

   If the metadata changed or the recorded statement needs replacement,
   the client MUST start again with a new pushed authorization request.
   Code redemption cannot replace the governing review.  A raised iat
   floor alone does not invalidate a code already bound to an acceptable
   recorded statement.

   The server MUST issue access tokens, at redemption and on refresh
   (Section 8), bound to the proven key with a token_type of DPoP
   (Section 5 of [RFC9449]).  The expiry of each access token, whether
   the token is a JWT or an opaque reference, MUST NOT be later than the
   exp of the instance attestation accepted for the request that
   obtained it (Section 14.3).  A resource server that does not accept
   DPoP-bound access tokens cannot be used under this profile.

8.  Refresh

   Every refresh request MUST carry the original client_id and
   authenticate under Section 6.2 with a current instance attestation
   and a fresh proof under the establishment's proven key.  In place of
   the document-key check of Section 5.7.1 of [STATEMENT], the server
   MUST complete the checks of Section 6.1 other than the digest
   comparison, verify the refresh-token binding, and enforce the fixed
   values of Section 7.2 before it considers any replacement.

   On every refresh, the server MUST require a current software
   statement and re-evaluate its issuer trust decision.  It MUST also
   verify that the currently served document meets Section 4 and that
   its digest equals the cimd_digest of the attestation and of the
   applicable statement, which is the recorded statement or, if one is
   needed, the replacement.  If the document fails Section 4, for
   example by omitting the software_statement_instance_binding member or
   naming another authentication method, the refresh is rejected with
   invalid_grant without seeking a replacement.

   A replacement (Section 5.2 of [LIFECYCLE]) is needed when the
   recorded statement is expired, refused, or no longer matches the
   served document.  In place of the key bullet of step 3 of Section 5.2
   of [LIFECYCLE], a current attestation of the proven key, from the
   recorded attester under the recorded policy, MUST name the
   replacement's metadata digest.  A rejected refresh MUST NOT replace
   the recorded binding or rotate a refresh token.

10.  Error Responses

   This specification defines no new error code.

10.1.  Error Codes

   Under this profile, a pushed authorization request, code redemption,
   or refresh is rejected with the following error codes.  Other
   rejections, including proof errors (Section 6.5 of [STATEMENT]), use
   the codes that [STATEMENT], [LIFECYCLE], [ABCA], and [RFC9449]
   assign.

   invalid_client:  Any of the following, or invalid_client_attestation
      in its place (Section 7.4 of [ABCA]):

      *  The attestation is missing or unacceptable, or its attester or
         evidence policy is not trusted.

      *  The request carries the OAuth-Client-Attestation-PoP header
         field.

      *  A valid DPoP proof is under a key other than the attested key.
         This fails authentication, not the proof (Section 7.3 of
         [ABCA]).

      *  At the pushed authorization request endpoint, the request
         carries an instance attestation for a document that does not
         select this profile or violates Section 4.

   use_fresh_attestation:  An otherwise valid attestation that this
      profile treats as not fresh enough (Section 7.4 of [ABCA]): its
      exp has passed, or it names a digest other than that of the
      document currently served while that document matches the
      applicable statement.

   invalid_grant:  Any of the following:

      *  At code redemption or refresh, a validly authenticated instance
         does not match a fixed establishment value of Section 7.2,
         including an instance that authenticates under a key other than
         the proven key.

      *  At code redemption or refresh, the current document exceeds a
         configured size bound.

      *  At code redemption, the current document no longer matches the
         recorded digest.

      *  At refresh, the current document no longer selects this profile
         or meets Section 4.

   statement_required:  Any of the following:

      *  At code redemption, the recorded statement is expired or
         refused.

      *  At code redemption or refresh, the recorded statement's issuer
         is no longer trusted.

      *  At refresh, a replacement that Section 8 needs is not obtained.

10.2.  Error Precedence and Disclosure

   Servers MUST check basic request syntax before reporting errors
   requiring authentication.  They MUST authenticate the instance before
   reporting errors about a code, a refresh token, or the review
   governing the grant.  Within authentication, they MUST verify
   attester identity, signature, and policy before returning the
   use_fresh_attestation error code.  Nonce challenges MAY precede
   completion of authentication and MUST NOT reveal tenant trust
   configuration.  Within a stage, the order of Section 6 of [STATEMENT]
   applies, and the response does not disclose other failed checks.

   Details of configured issuers, attesters, evidence policies, and
   tenant restrictions MUST NOT be exposed in error descriptions to
   unauthenticated requesters, as Section 6.6 of [STATEMENT] requires of
   its issuer trust configuration.

10.3.  Authorization Endpoint

   At the authorization endpoint, when Section 7.3 or Section 3.1
   requires a request_uri from a pushed authorization request, a request
   without a valid one is rejected with invalid_request.  Before
   redirecting with an error, the server validates the redirection URI
   as Section 6.4 of [STATEMENT] provides.  An authorization request
   carrying an instance attestation or an instance proof is rejected
   with invalid_request.

11.  Examples

   The following examples are non-normative.  In the HTTP examples, JWTs
   and opaque protocol values are shown as placeholders in angle
   brackets.  The metadata digest below is computed over the UTF-8
   octets of the displayed client document, using LF line endings, two-
   space indentation, and one final LF after the closing brace.

11.1.  Reviewed Client Metadata

   The following is an example of a CIMD that selects this profile:

   {
     "client_id": "https://cli.example/client.json",
     "client_name": "Example CLI",
     "software_statement_instance_binding": true,
     "token_endpoint_auth_method": "attest_jwt_client_auth_dpop",
     "grant_types": ["authorization_code", "refresh_token"],
     "response_types": ["code"],
     "redirect_uris": ["http://127.0.0.1/callback"],
     "scope": "projects.read",
     "software_statements_uri": "https://cli.example/reviews.json"
   }

   The server retrieves a statement for this identifier and these exact
   octets.  The document's port-free callback entry permits a
   transaction-specific port under Section 4.1.

11.3.  Pushed Authorization Request and Code Redemption

   The following is an example of a pushed authorization request that
   the client sends after obtaining a DPoP nonce (line breaks for
   display purposes only):

   POST /par HTTP/1.1
   Host: as.example
   Content-Type: application/x-www-form-urlencoded
   OAuth-Client-Attestation: <instance-attestation>
   DPoP: <proof-for-PAR-with-server-nonce>

   client_id=https%3A%2F%2Fcli.example%2Fclient.json
   &response_type=code
   &redirect_uri=http%3A%2F%2F127.0.0.1%3A51004%2Fcallback
   &scope=projects.read
   &code_challenge=<S256-challenge>
   &code_challenge_method=S256
   &state=<transaction-state>

   Here the server pulls the software statement.  It binds the accepted
   request, key, attester, policy, and tenant to its returned
   request_uri.  After authorization in the browser, the client receives
   a code at http://127.0.0.1:51004/callback and validates the response
   issuer and state.  The following is an example of the request that
   redeems the code (line breaks for display purposes only):

   POST /token HTTP/1.1
   Host: as.example
   Content-Type: application/x-www-form-urlencoded
   OAuth-Client-Attestation: <current-instance-attestation>
   DPoP: <new-proof-for-token-endpoint-with-server-nonce>

   grant_type=authorization_code
   &client_id=https%3A%2F%2Fcli.example%2Fclient.json
   &code=<authorization-code>
   &redirect_uri=http%3A%2F%2F127.0.0.1%3A51004%2Fcallback
   &code_verifier=<PKCE-verifier>

   The server verifies the proven key and all continuation checks.  It
   does not accept another installation's valid attestation for this
   code.

11.4.  Refresh and Replacement

   The following is an example of a refresh request (line breaks for
   display purposes only):

   POST /token HTTP/1.1
   Host: as.example
   Content-Type: application/x-www-form-urlencoded
   OAuth-Client-Attestation: <current-instance-attestation>
   DPoP: <new-proof-for-token-endpoint-with-server-nonce>

   grant_type=refresh_token
   &client_id=https%3A%2F%2Fcli.example%2Fclient.json
   &refresh_token=<refresh-token>

   If the recorded statement has expired, a server that supports pulled
   statements pulls a current replacement, as Section 5.2 of [LIFECYCLE]
   provides for any establishment.  If the replacement names changed
   metadata, the attestation needs to name that same new digest while
   retaining the proven key and the recorded attester and policy.  If
   the attestation does not, the refresh fails without changing the
   binding.

12.  Authorization Server Metadata

   This specification defines the following authorization server
   metadata [RFC8414] value:

   software_statement_instance_binding_supported:  OPTIONAL.  Boolean
      value indicating whether the authorization server supports this
      specification.  If omitted, the default value is false.  Support
      does not promise acceptance of any particular client, statement
      issuer, attester, evidence policy, or tenant.

   A supporting server MUST publish its
   pushed_authorization_request_endpoint metadata value, include
   attest_jwt_client_auth_dpop in the
   token_endpoint_auth_methods_supported metadata value, advertise S256
   in the code_challenge_methods_supported metadata value, and publish
   the dpop_signing_alg_values_supported ([RFC9449]) and
   client_attestation_signing_alg_values_supported (Section 8 of [ABCA])
   metadata values.  It MUST support [RFC9207] and publish the
   authorization_response_iss_parameter_supported metadata value as
   true.  As a server implementing [LIFECYCLE], it also publishes
   software_statement_replacement_supported as true (Section 9 of
   [LIFECYCLE]).

   A client determines support from
   software_statement_instance_binding_supported, not from the generic
   method advertisement.  This profile requires pushed authorization
   requests for its clients even when the server serves other clients
   without them.  It does not require the server's global
   require_pushed_authorization_requests value to be true.

13.  Implementation Considerations

   This section gives guidance to implementers.  It adds no requirement.

13.1.  Bounding Establishments and Pending Requests

   An authorization server can bound establishments as Section 11.3 of
   [STATEMENT] describes, and also per resource owner and tenant, so
   that one installation cannot exhaust the capacity available to other
   installations.  It can limit pending pushed authorization requests
   separately from any bound on establishments, and its rate limits can
   account for client, attested key, tenant, and authenticated resource
   owner as available.

13.2.  Signing Brokers

   A signing broker ought to expose constrained operations rather than
   arbitrary signing: it produces proofs for the authorization server
   only within its own processing of an OAuth transaction, and proofs
   for resource requests only for resource endpoints the caller is
   authorized to reach and only with that caller's own access token.  A
   broker that handles authorization for another process ought to bind
   the authenticated caller, intended authorization server, callback,
   PKCE verifier, and resulting grant to one local session
   (Section 15.1).

13.3.  User Interface, Audit, and Logging

   A server ought not to present assurances stronger than the accepted
   evidence policy supports (Section 5).

   Authorization servers ought to avoid logging complete attestations,
   verifiers, codes, and refresh tokens.  Audit records can retain the
   trust decisions, policy identifier, digest, and appropriately
   protected key identifiers without retaining credentials.

14.  Deployment Considerations

   This section gives guidance to operators and issuers.  It adds no
   requirement.

14.1.  Revocation and Enforcement Latency

   This specification defines no attestation or instance revocation
   protocol.  Without one, an instance attestation's exp bounds
   acceptance of evidence that has become stale without the server
   learning of it.  A deployment can use independently established
   revocation mechanisms or local denial lists.  A deployment that
   requires prompt enforcement needs short token lifetimes or
   independent token revocation, because withdrawal of a review
   (Section 3 of [LIFECYCLE]), removal of trust, and denial of an
   attested key do not revoke access tokens already issued.

14.2.  Attester Enrollment

   An attester ought to limit enrollment and renewal so that one
   approved installation cannot obtain unlimited keys to evade per-key
   controls, such as denial of an attested key (Section 6.1).

14.3.  Evidence Age and Token Lifetime

   Because an access token expires no later than the attestation
   accepted for it (Section 7.4), a client holding a refresh token
   refreshes, with a fresh attestation, at least as often as its
   attester's maximum evidence age allows, and a client without one
   starts a new authorization request at the pushed authorization
   request endpoint.

15.  Security Considerations

   The security considerations of Section 13 of [STATEMENT], Section 12
   of [LIFECYCLE], Section 12 of [ABCA], [CIMD], [RFC8252], and
   [RFC9700] apply.

15.1.  Software Evidence and Key Use

   A valid signature proves that an accepted attester made an assertion
   but does not improve the evidence behind it.  An attester accepting
   self-reported executable hashes would let a copied statement and an
   arbitrary key satisfy the binding.  The evidence and mapping
   requirements in Section 5 prevent that substitution only when the
   deployment enforces them.

   A key's non-exportability does not prove which process can use it.
   An acceptable evidence policy therefore requires key storage and any
   signing broker to restrict use to the software instance the policy
   covers (Section 5).  A general signing service reachable by arbitrary
   local processes would let unreviewed software authenticate through an
   approved installation (Section 13.2).  Remote attestation of a device
   without an application-to-key binding likewise does not prove which
   process can use the key.

   This profile cannot ensure benign user intent, prevent an approved
   application from being used as a proxy, or preserve an assurance
   after compromise of the platform on which its evidence depends
   (Section 13.3).  Plugins, scripts, dynamic libraries, debuggers, and
   injected code can change the effective software identity and require
   explicit treatment in the evidence policy (Section 5).

15.2.  Loopback and Transaction Theft

   An attacker can attempt to occupy a loopback port, intercept a
   response, or initiate its own authorization transaction using the
   published client identifier.  PKCE and proof of the proven key
   protect redemption of an intercepted code.  Admission of a new
   transaction additionally requires an acceptable instance attestation.
   PKCE or an unattested DPoP key alone supplies no software identity.
   A DPoP proof does not sign the request body: TLS, not the proof,
   protects the redirection URI, PKCE challenge, and statement a request
   carries.

   The client binds its listener only to the selected loopback
   interface, opens it before sending the pushed authorization request,
   and closes it when the transaction completes or is abandoned.  It
   keeps its verifier and transaction state confidential and
   unpredictable, as their respective specifications provide.  A
   launcher handling authorization for another process acts as the
   signing broker of Section 13.2.

15.3.  Downgrade Prevention

   A requester can try to avoid this profile by omitting every review
   artifact, by presenting a statement over an earlier document, or by
   opening a grant another way.  Because Section 3.1 bases a server's
   requirement for this binding on its own policy, withholding an
   artifact does not avoid it.

   Existing grants retain their recorded binding (Section 7.2).  A
   server implementing only [STATEMENT] continues to reject clients that
   select this profile where review is required (Section 5.6.3 of
   [STATEMENT]).

15.4.  Artifact Substitution and Key Separation

   The distinct attestation type, digest binding, subject equality, and
   fixed establishment values prevent a generic attestation or one for
   another reviewed document from being substituted, and key separation
   keeps a statement signing key from also signing an attestation
   (Section 6.1).

   Attester authorization is scoped independently to client identifier
   namespaces and tenants.  An over-broad attester can undermine the
   binding for every namespace for which it can issue instance
   attestations.  A statement issuer and an attester that collude, or
   that are both compromised, can make false assertions within the
   authority the server has assigned them.

15.5.  Freshness and Availability

   Short attestation lifetimes limit stale evidence but make attester
   availability important.  The maximum evidence age (Section 6) and the
   trust-data reuse bound (Section 5) limit how long stale evidence or
   trust data is accepted.  A fresh proof demonstrates current access to
   a key, not that software was re-evaluated at proof time.

   An access token cannot outlive the attestation accepted when it was
   issued (Section 7.4), but it can outlive a review withdrawn or
   attester trust removed after issuance (Section 14.1).

   Metadata digest binding can require coordinated publication of a new
   document, review, and attestation (Section 8).  During an incomplete
   transition a request fails: Section 5.2 of [STATEMENT] does not treat
   the changed document as reviewed, and this profile does not fall back
   (Section 7.1).

15.6.  Resource Exhaustion

   Attestations do not remove the need for bounded document retrieval,
   statement selection, proof replay caches, and pushed authorization
   request storage (Section 11.2 of [STATEMENT], Section 13.1,
   Section 14.2).

16.  Privacy Considerations

   The privacy considerations of Section 14 of [STATEMENT], Section 13
   of [LIFECYCLE], and Section 11 of [ABCA] apply.

   An attested key reused at multiple authorization servers can
   correlate installations across them.  Clients SHOULD use separate
   attested keys for separate authorization servers where the evidence
   mechanism permits, and SHOULD avoid adding stable installation
   identifiers unless needed by the deployment.  This profile does not
   require a globally stable instance identifier or an attestation
   audience.

   An attester might learn the target authorization server from
   enrollment traffic, key-scoping choices, or timing even when no
   audience is carried.  Deployments ought to minimize evidence and
   identifier disclosure to both attesters and authorization servers.
   An evidence-policy identifier can reveal enterprise management
   practices, so it ought to identify policy semantics without embedding
   user or device identifiers.

   Instance attestations and proofs never appear in browser URLs
   (Section 7.3).  Logs and audit records can link installations to
   people and devices (Section 13.3).

   extension involved in processing the request, so this specification
   requests no change to the registrations of the error codes it uses
   there.

Appendix A.  Managed Command-Line Client Deployment

   This appendix is non-normative.  A managed desktop can implement the
   evidence boundary with a trusted launcher or enterprise agent and an
   enterprise attestation service.  Other mechanisms are possible if
   they meet Section 5.

   The enterprise enrolls the launcher through an authenticated
   management channel.  It records a manifest, authorized by the
   controller of the client identifier URL's origin or its delegate,
   that associates a signed package or exact artifact with that client
   identifier URL.  It approves the manifest for the applicable evidence
   policy.  The launcher uses platform facilities to authenticate the
   actual calling process and validate that association.  It does not
   trust a process's own claim about its executable path or hash.

   The launcher creates or provisions the installation's key in
   protected storage and obtains an attestation through an authenticated
   exchange with the enterprise service.  That service verifies the
   evidence, the binding to the key, and the document digest before
   issuing the attestation.  The service's signing key is distinct from
   the attested key and is accepted through the authorization server's
   attester trust configuration.

   For each authorization transaction, the launcher performs the OAuth
   exchange on behalf of the verified caller, as the signing broker of
   Section 13.2.  It re-checks caller authorization when the key is
   used, including refresh, and protects returned tokens from other
   processes.

   An implementation needs to address changes between checking software
   and using the key, dynamic code loading, and the ability of an
   executable the evidence policy covers to proxy requests for others.
   Platforms without reliable process identity and key-use isolation
   cannot obtain this profile's assurance by running the launcher with
   more privileges.  A script-based command-line client might require an
   execution environment whose policy covers its interpreter, script,
   and dependencies, or a narrower assurance than verified executable
   identity.

A.1.  macOS Example

   This example uses macOS 27 or later on Apple silicon, with a launcher
   application for which App Attest is available [APPLE-WWDC26].

   Software identity:  The publisher signs each release with an Apple-
      issued developer certificate and one signing identifier.  A
      manifest served from the client identifier URL's origin names the
      publisher's Team ID and that identifier, covering each such
      release.

   Key isolation:  The launcher creates a P-256 key in the Secure
      Enclave, from which key material cannot be transferred
      [APPLE-ENCLAVE].  It keeps the key in a keychain access group that
      only its own provisioning profile authorizes, so the client cannot
      use the key directly.

   Caller identification:  The client connects to the launcher over XPC,
      and the launcher sets a code-signing requirement naming an Apple-
      issued certificate chain, the publisher's Team ID, and the
      client's signing identifier, which the system enforces on the
      connection [APPLE-XPC].  The launcher never relies on a process ID
      or a reported path.

   Code injection:  The client runs under the hardened runtime
      [APPLE-RUNTIME], and the evidence policy requires that its
      signature carry no entitlement that disables library validation,
      allows DYLD_ environment variables, or permits debugging.  The
      client then loads only libraries signed by Apple or by its own
      team.

   Launcher authentication:  The launcher registers an App Attest key,
      which Apple certifies as belonging to the launcher
      [APPLE-APPATTEST], and ties it to the managed device with a
      single-use secret delivered through managed app configuration,
      which macOS delivers only to an app with a matching code
      signature.  Each later report, carrying the installation's public
      key and the client's signing identity, bears an App Attest
      assertion.

   Evidence and renewal:  No Apple attestation covers the installation's
      key, so the enterprise service relies on the authenticated
      launcher's report that the key is in the Secure Enclave and usable
      only by the launcher.  Before the evidence reaches the maximum
      evidence age, the launcher re-checks the device's management state
      and the client's signature and obtains an attestation on that new
      evidence.

   Unsupported case:  A script run by a signed interpreter with
      unrestricted imports is not covered, because the verified
      signature is the interpreter's.  Such a client remains review-only
      under Section 5.6.3 of [STATEMENT].
